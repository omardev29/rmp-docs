Ownership

Everything the framework hands you is owned by something that releases it at the right moment, and you never free anything yourself. A texture lets go of the GPU when the last copy of it goes; an object is freed by its scene; a scene by the stack; a callback by the object that holds it. There is no Unload to remember, no delete to write, and no order to get right on the way out.

The framework holds itself to it. No owning raw pointer appears in its headers or its sources, and no bare new, delete, malloc or free: tools/ownership_check.sh rejects them, and its list of exceptions only ever gets shorter. The two left are where raylib's C interface hands a buffer across and frees it itself.

What owns what

Inside the framework, the choice of how to hold something follows one order of preference, from first choice to last:

FormWhen
a valuewhatever fits: a Vector2, a Shape, a behavior, an options struct
T &something that certainly exists and keeps its identity for the length of the call
rmp::Handle<T>an object that can die, kept across frames
std::unique_ptr<T>sole ownership of something polymorphic or large
T *only when it can be null and cannot outlive what it points at; it never owns

The last row is a promise about the API: a raw pointer in a signature of the framework never owns what it points at, and its comment says so. get<B>() returns a behavior or nullptr; scene() returns the scene the object is in; RayQuery::ignore names an object a ray should pass through. None of them is yours to free. Where the framework does take ownership of something, it takes a std::unique_ptr, so the hand-over is written in the signature.

Assets

An rmp::Texture — like a Font, Sound, Music, Shader or RenderTexture — is a counted reference to one loaded resource. Copying it is one more reference; the last one to go unloads it. Loading the same name twice gives the same texture back with the count at two, which is what lets a hundred enemies share one sprite without anyone deciding who owns it.

rmp::Texture _rabbit;

void _ready() override { _rabbit = rmp::assets::load_texture("rabbit.png"); }
void _draw() override { DrawTexture(_rabbit, 100, 100, WHITE); }

It converts to the raylib type it wraps, so every raylib function takes it. But only a variable converts. A temporary does not, because the texture would be unloaded at the end of the line and the raylib struct you kept would point at nothing:

Texture2D player = rmp::assets::load_texture("player.png");
DrawTexture(player, 0, 0, WHITE);

Ownership is also what makes the way out safe. A texture belongs to the GPU context, and the context belongs to the window: unloading a texture after CloseWindow() is a write to something that no longer exists. Because every texture is held by something with a lifetime — a scene, an object, a global — the framework can release them in an order that works: the scenes and their objects first, then the globals, then whatever is still loaded, and only then the window.

Objects, and the handle that outlives them

A scene owns its objects. spawn() makes one, the scene keeps it, and what you get back is a reference that is good for the rest of the frame, because an object that is destroyed is only freed when the frame ends.

Kept until the next frame, that reference can dangle. What you keep instead is a handle:

class Turret : public rmp::Object {
public:
    rmp::Handle<rmp::Object> target;

    void _update(float delta) override {
        (void)delta;
        rmp::Object *aim = target.get();
        if (aim == nullptr) return; // it died, or there never was one
        rotation = Vector2Angle({ 1, 0 }, Vector2Subtract(aim->position, position)) * RAD2DEG;
    }
};

A handle is the object's slot and that slot's generation. When the object dies the generation goes up, so the handle answers nullptr from then on — and it stays dead even after the slot holds a new object, which is the classic bug of keeping an index. Checking a handle is an integer comparison. A handle can be typed, handle<Goblin>(), so the field you read after the check needs no cast.

Scenes and globals

The scene stack owns its scenes. RMP_GAME makes the first one, and change(), push() and replace() make the next ones with std::make_unique and move them in on the same line, so no code of yours ever holds a scene by pointer.

rmp::global<T>() is the state that outlives a scene change: one instance per type, made the first time it is asked for, owned by the framework and destroyed on the way out — in reverse order of first use, after the scenes and before the window, so a global can hold a texture.

Callbacks: why not std::function

A function you hand to the framework — an on_collision, an on_click, the on_ fields of the behaviors — is kept in an rmp::Callback, not a std::function, and there are two reasons.

The first is ownership. std::function has to be able to copy what it holds, so a lambda that owns something only it should own cannot go into one:

#include <functional>
#include <memory>

std::function<void()> on_win = [save = std::make_unique<int>(3)] { (void)save; };

A Callback moves and never copies, so the same lambda is fine:

auto &coin = spawn({ .position = { 400, 225 }, .size = { 16, 16 } });
auto bonus = std::make_unique<int>(10);
coin.on_collision([bonus = std::move(bonus)](rmp::Object &self, rmp::Object &) {
    score += *bonus;
    self.destroy();
});

The second is cost: <functional> is expensive to include, and every file with an object in it would pay for it. A Callback is what the framework actually needs — the captured state behind a shared pointer that carries its own destructor, and one function pointer to call it — and nothing else. Setting it again replaces what it held, and destroys what that captured.

Behaviors

A behavior added to an object belongs to the object. add<B>() moves it into storage that never moves it again, and the reference it returns, like the pointer get<B>() returns, stays good for as long as the behavior is attached. Removing the behavior, or destroying the object, runs its _end and frees it. A behavior's type is never erased into a void * you would have to delete: the storage holds it in a shared pointer that knows its destructor.
