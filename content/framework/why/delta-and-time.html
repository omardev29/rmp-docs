Time is a parameter

Every update hook is handed the time the frame took, in seconds, as a parameter called delta. Nothing that moves the game reads the clock for itself: one function reads it, and hands that number out. It is a small decision with two large consequences: the framework can be tested without a window, and a game written with it plays the same at any frame rate.

class Bullet : public rmp::Object {
public:
    float seconds_left = 2.0f;

    void _update(float delta) override {
        seconds_left -= delta;
        if (seconds_left <= 0) destroy();
    }
};

A scene's _update(delta), an object's _update(delta), a behavior's _update(self, delta) and the on_frame(delta) of a game with its own entry point all get the same number, and it is always called delta — not dt, not deltaTime — so the most common parameter in a game has one name everywhere you read it.

Where the clock is read

Once a frame, in one function of src/rmp/app.cpp, which asks raylib for the frame time, corrects it, and hands it to the frame. Every entry point — the desktop loop, the browser's callback, iOS's — goes through that function, so the correction applies to all of them, and to a game that writes its own frame as much as to one that uses scenes.

Nothing downstream asks raylib what time it is. The scene stack passes delta to the scenes, the scenes to their objects, the objects to their behaviors; the integrator moves an object by its velocity times delta; the camera's smoothing, an animation's frame timing, a Timer, a Tween are all driven by the number they were handed.

So it can be tested

A test of the framework creates a scene, spawns objects into it and runs a frame of exactly 1/30 of a second, with no window and no GPU, and checks where everything ended up. It can do that because time arrives as an argument: a function that read the clock itself would give a different answer every run, and a test that fails one time in twenty teaches everyone to ignore red.

The rule is checked. tools/seam_check.sh fails the framework's tests if any file under src/rmp/ or include/rmp/ calls GetFrameTime(), GetTime(), reads the keyboard, the mouse or the gamepad, asks for the screen size, or uses raylib's random numbers — except a short list of files that are the seams themselves, each with the reason it is allowed. The same goes for the other things that change between two runs. Input is sampled in one place, into a snapshot a test can replace. Randomness comes from rmp::random, one generator with a seed: a test keeps the fixed default and gets the same sequence every time, while a shipped game is seeded from the wall clock when it starts, and current_seed() tells you which run you are in.

The UI is the one part that keeps a clock of its own, for the timing of its transitions and of a held arrow key. It reads raylib's frame time for those, and the layout tests run it in a mode where that time is 0, so a layout comes out the same on every run.

So it plays the same at any frame rate

A speed times delta is a distance, whatever the frame rate. That is the whole trick, and the framework is built so you get it without thinking about it:

  • Velocity is integrated for you. Set velocity in units per second and the object moves the same distance in a second at 30 or 240 frames.
  • Forces and impulses are two calls. apply_force is meant to be called every frame, and is scaled by delta; apply_impulse is meant to be called once, and is not. An impulse applied every frame would go twice as fast at 120 frames a second as at 60 — which is exactly the bug the two names exist to prevent.
  • The camera's smoothing is a rate. The usual position += (target - position) * 0.1f, run once a frame, follows twice as fast at 120 frames a second as at 60. The camera instead covers 1 - exp(-smoothing * delta) of the distance each frame, which comes to the same fraction in a second at any frame rate.

The framework checks this on a real game: the bot that plays the platformer example plays it to the flag at 60 frames a second and again at 240, and jumps from its moving platform at both.

[app] max_delta

Real elapsed time has no ceiling. Drag the window, stop at a breakpoint, let the disk stall, and the next frame time comes back as half a second. A bullet at 900 units a second then moves 450 units in one step — through the wall and out the other side, without ever overlapping it.

So the delta the game is handed is clamped to [app] max_delta, a twentieth of a second unless you change it. A frame that really took longer arrives as a twentieth of a second, and the game runs a moment of slow motion instead of teleporting. Nobody minds a hitch; everybody minds falling out of the world.

[app]
max_delta = 0.05

0 switches the clamp off and hands the real time through, which makes a stalled frame the game's problem. Sensible values are between a sixtieth and a tenth of a second, and configure.py refuses the ones that cannot be meant — longer than a second, which clamps nothing, or shorter than a frame at 240 Hz, which would clamp every frame:

[app]
max_delta = 0.001

It also refuses a frame cap that cannot coexist with the clamp: with [window] fps at 15, every frame is longer than a twentieth of a second, and the game would run at three quarters speed forever — the config pipeline shows that refusal.

The clamp is half of the answer to tunnelling. The other half is the swept test in the collision pass, which catches a fast object crossing a thin one between two frames even at a perfectly normal frame rate, where no clamp applies.

The frame with no time in it

The first frame of a game reports a frame time of 0, and a delta of 0 or less is never integrated at all. That matters more than it sounds: a push given in _ready() with apply_force waits in the object for the first frame that has time in it, instead of being spent on a frame that could not move anything. A negative frame time, which a clock that went backwards across a suspend could produce, is handed to the game as 0.

Note

raylib's GetFrameTime() is still there, and your own code can call it. It is the raw number: unclamped, and different from the delta the rest of the frame was given. Use delta.
