The repository

The framework is one repository, omardev29/raylib_multiplatform. It is also the template every game is made from, so it holds two kinds of thing side by side: what a game gets, and what only the framework needs to check itself. Knowing which is which is most of knowing where a change goes.

The repositories beside it

raylib_multiplatform
The framework: the library, its tests, its examples, its tools and its CI. Every code change goes here.
rmp-docs
This site, checked against one commit of the framework. Keeping the docs true is about it.
raylib-build-image
The build image every Linux job runs in, and the Alpine image the musl build is started on. A new tool for CI is a new image, and a new digest in the framework.

The framework's CLAUDE.md also names files beside the checkout: the maintainer keeps it inside a folder of plans and progress notes. That folder is not part of the framework. No build, test or workflow of the framework reads it, and a change to the framework never needs it.

What lives where

PathWhat it is
include/rmp/The public headers, one per module, and nothing else: no umbrella header, so a game includes the modules it uses. include/rmp/generated/ is written from the .toml and never committed.
src/rmp/The library's implementation, compiled once into rmp, which the game and every example link. src/rmp/ui/ is the UI, the one place Clay is allowed; src/rmp/internal.h holds the seams — the clock, the reports, the resources root.

examples/One mini-project per example, by area — scenes/, input/, ui/, assets/, ads/, platform/, games/ and plain_c/. Each is built and booted by CI; most are played by a script.
tests/The unit tests (tests/*_test.cpp, doctest, no window), the UI layout and render tests, the e2e scripts and their goldens (tests/e2e/), the properties, fuzz targets and mutation floors, the Python tests of the tools, and tests/game/, the tests every game is given.
tools/tools/rmp.py, which is rmp; tools/configure.py, which turns the .toml into every build system's input; the gates, mostly tools/*_check.sh; and the lists the gates hold the tree to.
cmake/What CMakeLists.txt includes: the sanitizers, the game's tests, the web build's helpers. cmake/generated/ is written from the .toml.

TECHNICAL.md has the whole tree, file by file, and a test fails when it names a file that is gone or misses a public header or a source of src/rmp/. Architecture has how the modules depend on one another.

build/

Every build goes into a folder of its own under build/: build/debug for rmp test and rmp run, build/release, build/lint for the compile database clang-tidy reads, build/examples-check for the examples and their scripts, build/coverage, build/fuzz, and the rest that BUILD_DIRS in tools/rmp.py lists with what writes each one. build/ itself is never a build: CMake refuses to configure there, and a workflow, a tool or a page that names a folder of build/ that list does not have fails a test. A new folder is a new line in that list.

rmp clean

deletes every build and everything generated from the .toml; the next command that needs them makes them again.

What a game gets: the manifest

A game made with rmp new is a copy of the framework, made from an explicit list in tools/rmp.py: INCLUDE names what a game needs, and FRAMEWORK_ONLY names what it does not, each entry with the reason. The longest pattern that matches a path decides. It is a list of what goes in, not of what stays out, because an exclude list fails in silence: the next gate or fixture added to the framework would ride along into every game, and nothing would say so.

So every file the framework tracks has to be in one list or the other. A new file that is in neither fails rmp test rmp, and the question it forces is the right one: does a game need this? A game needs it when its build, its tests or its CI use it; otherwise it goes in FRAMEWORK_ONLY, with a reason a reader will understand.

rmp new --list

prints what a new game gets, without making one.

Some files are the same in both and behave differently. .github/workflows/ci.yml is copied byte for byte, but for the block of triggers [ci] on_push writes; the framework's own jobs — its tests, its examples, its lint gates — are skipped in a game by a condition the first job computes, never cut out of the copy. A step that names a file a game does not get must be one of those skipped in a game. And every commit of the framework is proved to make a working game: the rmp_new job makes one and runs that game's own checks on it.

What a new file needs

The checks hold the tree to a few lists, so a new file is not finished until it is on the ones that concern it. Each line below is a test that fails without it.

A new…Needs
file of any kindits entry in INCLUDE or FRAMEWORK_ONLY in tools/rmp.py, as above
source in src/rmp/its line in TECHNICAL.md's tree; its line in tools/coverage_floor.txt, in the same commit; and its place in exactly one of the mutation floor files under tests/mutation/floors/
public header in include/rmp/to be a module a game can choose to use, with a name; its line in README.md and in TECHNICAL.md's tree; its line in tools/header_budget.txt, measured in the build image; to include rmp/config.h and compile on its own; and for each public function, a test that calls it, and a property that holds it or, written by hand for a reviewer to read, a line in tests/property/waivers.txt
