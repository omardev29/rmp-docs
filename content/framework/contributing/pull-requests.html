Pull requests

main is changed only by pull request. Every change, from a person or from an agent, goes up on a branch of its own, is checked by CI there, and is merged when every check main requires is green — and, when it changes the public API or the .toml, when Omar has approved it.

From a branch to main

  1. Start from an up-to-date main, on a branch named for the change: 
    git switch main
git pull --ff-only
git switch -c save-reads-any-locale
    An agent works in a git worktree of its own as well, so that two tasks on one machine never share a checkout.
  2. Make the change, with its test seen red first, and run the ladder.
  3. Push the branch. The first push sets its upstream: 
    rmp push
  4. Open the pull request, on GitHub or with gh. Its description starts from the template, below; fill it in. 
    gh pr create --base main --template .github/pull_request_template.md
  5. CI runs the fast lane on the branch merged into main, and again on every push to the branch. A red check is fixed on the branch, with the debug lane when a platform is involved: CI.
  6. When every required check is green, and the approval is there if the change needs one, it is merged.

Agents in the cloud

Much of the work is done by Claude Code in the cloud: many agents at once, at any hour, each on a branch of its own, each opening a pull request like anybody else. They reach GitHub through Claude's own GitHub connection, not through a token from somebody's machine. They follow the same process to the letter — the ladder, the template, nightly-finding issues first — and what one could not run where it ran, it says under Not verified instead of leaving it out.

The template

.github/pull_request_template.md is the description every pull request starts with. It asks for what a reviewer needs to trust the change without running it again:

What changed, and why
The change in a few sentences, and the reason for it: the bug and how it showed, or the game that needs the feature. For a feature, how it answers the three questions of the three-function menu.
The ladder
Which stages ran, and where: on the laptop, and in the pinned build image. Name a stage that skipped, and why.
Seen red first
For each new test and gate, the mistake it was seen to fail on, and the line it failed with.
Not verified
What the change could affect that nothing here ran: a platform only the full matrix builds, a check only the image has. An honest list is worth more than a green one; it says where the next person should look.
The checklist
Each box is ticked, or says why it does not apply:
  • rmp fmt check, rmp lint and rmp test pass;
  • rmp test examples, when the public API or an example changed;
  • rmp test sanitize, when the change parses, casts or frees;
  • rmp test fuzz, when a parser changed;
  • rmp test coverage in the build image, when src/rmp/ changed;
  • the docs updated, and FRAMEWORK_REF bumped, when a page of this site is no longer true: a pull request of the site's own, whose FRAMEWORK_REF moves to this change once it is merged — Keeping the docs true;
  • no secret anywhere in the change;
  • the commits plain, below.

The checks main requires

A pull request merges only with these checks green. They are the fast lane's jobs, by the names GitHub shows them under:

config, lint, tidy, examples, e2e, coverage, deep, docs, rmp_new, linux / x64, windows / x64, web / build, android / build and api.

docs is green even when this site no longer passes against the change: it warns there, so that the framework is not held up by its documentation, and a release tag is what it blocks. The warning is still a job to do, on the docs, before the next release. The full matrix is not required on a pull request; it runs at the end of a larger piece of work and on every tag.

A change to the API needs Omar's approval

The API is what the rule above every other protects: every public header is something a game's author has to know exists, every function in it is one more thing to read, and every key of the .toml is a promise to every game made from the framework. So a change to either is Omar's decision, made on the pull request.

The api job of .github/workflows/ci.yml holds it. It runs on pull requests only — on a push, a tag or a run started by hand it does nothing and passes — and it looks at what the pull request changes:

  • any file under include/ — today, the public headers include/rmp/*.h — in any way, a comment included: a comment in a public header is the reference a game's author reads;
  • a key of the .toml: one of DEFAULTS in tools/configure.py added, removed or renamed, or its default changed — a default is what every game that does not set the key gets — or a key of the framework's own raylib_multiplatform.toml.

When it finds one, it puts the label api-change on the pull request and fails, with a message that says what changed and who approves it, unless the pull request also carries the label api-approved. Only Omar adds that label: the job reads the pull request's events to see who added it, and refuses it from anybody but the repository's owner. It is judged by the base branch's own copy of tools/api_change.py, so a pull request cannot change the judge it is judged by. Once he has, the api job is run again — the next push to the branch runs it, or the failed jobs are re-run — and it passes:

gh run rerun "$RUN" --failed

Before you open one, the same script says what your branch would be labelled, against origin/main, and changes nothing:

python3 tools/api_change.py

Make the decision easy: say in the description what a game's code looks like before and after, and how the change answers the three questions. A change that makes the three-function menu longer will not be approved however it is argued.

nightly-finding issues first

Every night the deep campaign fuzzes every fuzz target and runs the properties at a random seed, and every Sunday it runs mutation testing. What it finds is an issue labelled nightly-finding: one per signature — the same crash found again is a comment on its issue, not a second one — with the one command that plays it again and a link to the run that keeps the input. A bug found that way is real and has not been fixed yet, so those issues are taken before any other work:

gh issue list --label nightly-finding

Taking one is the seen-red protocol with the evidence handed to you:

  1. Play it again with the command in the issue, in the build image, and see it fail.
  2. Make it a case that runs on every push: a fuzz input goes into tests/fuzz/regressions/<target>/ under a name that says what it is; a property's counterexample becomes a named doctest case in the module's own tests; a Hypothesis failure becomes an explicit example.
  3. Fix it, and see that case pass.
  4. Open the pull request with Fixes # and the issue's number in its description, so merging it closes the issue. If the same signature is found after it was closed, a new issue says it came back.

Properties, fuzzing and mutation has each kind in detail.

Commits

A commit message is plain text in English: no Co-Authored-By line, and no trailer of any other kind. An agent working for Omar commits in his name, which is the git identity his machines already have.

The subject says what is true after the commit, and the reason when it fits, rather than naming a kind of change — not fix: save but something of the shape a save reads 0.5 back under a German locale: every number is converted in the C locale. A body, when there is one, says what was seen red and how. Where a change moves a number that is written down — a coverage floor, a size budget, a header's cost, the lint debt — the new line goes in the same commit as the change that earned it, so the history says why every number is what it is.

What needs a person

Everything else is done without asking. Omar is asked for:

  • a change to the public API or to a key of the .toml, through api-approved, above;
  • an architectural decision: what the framework is, rather than how one piece of it works;
  • a serious problem;
  • anything on GitHub itself: its settings, labels, branch protection and secrets, and anything wrong with it.
