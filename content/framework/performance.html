Performance

The framework sits on raylib and draws everything through it, so a frame can never be faster than raylib makes it. What the framework decides is how much it adds on top, and how much work it saves the game from doing at all. This page goes through both: the abstractions that cost nothing, the few that cost a function call, the places where the framework does less work than a hand-written raylib game would, and where OpenGL by hand still wins.

The rule: you pay for what you use

"Zero-cost abstraction" means two things here, and the framework holds both.

  • What you do not use costs nothing. The framework is a static library compiled with -ffunction-sections -fdata-sections and linked with --gc-sections and link-time optimisation in release. The linker takes only the objects something references and throws away every function nobody calls. A game that never touches rmp::ui ships no UI code; a game that never loads an Aseprite file ships no Aseprite reader. The strongest form of the rule is "a 2D game pays nothing for 3D": not one byte of the 3D renderer, the physics or raylib's model loaders reaches a 2D binary.
  • What you use costs about what you would have written yourself. A helper is not worth having if writing the raylib calls by hand would be faster. Where an abstraction does cost something, it is one indirect call or one lookup, said below.

What compiles to nothing

AbstractionWhat the compiler makes of it
Options structs with designated initialisers ({ .speed = 320 }) A plain struct built on the stack. No builder, no map of names, no allocation.
The math types (Vector2 and friends from raylib-cpp, the operators of rmp/math.h) Header-only and inline: a + b * delta is the same instructions as Vector2Add(a, Vector2Scale(b, delta)).
RAII ownership (rmp::Texture, rmp::Sound, the scenes and objects) A destructor that calls the Unload* you would have called. No reference counting, no garbage collector, no pause.
No exceptions No unwinding tables on the hot path, no try anywhere in the library: a failure is a return value, a report once, or a default. No exceptions says why.
Behaviors that leave out a hook Hooks are found at compile time with requires. A behavior with no _draw has a null entry in its table of hooks, and the frame never calls it.
Hot reload in a release, or off the desktop changed() is a constant false; no file is ever watched.
Configuration The .toml becomes #defines at configure time (the config pipeline). Nothing is parsed when the game starts.

What costs a call, and why it is worth it

  • A behavior's hook is one indirect call through a table of function pointers built for its type at compile time. That is the price of a virtual function, without a base class or a vtable pointer in the behavior. A hook the behavior does not define is not called at all.
  • rmp::Callback, what every on_click and on_hit is, is one call through a function pointer over the lambda you gave it. It is move-only on purpose, so it carries none of std::function's copying machinery.
  • A handle (rmp::Handle, rmp::Ref) checks a slot and a generation number before it hands you the object: two loads and a compare, in exchange for never reading an object that was destroyed.
  • An action by name (rmp::input::pressed("jump")) is a lookup in a small table, so the same name works for a key, a button and a touch.

Where the framework does less work than a hand-written game

The map draws only what the camera sees

A naïve tilemap draws every tile every frame. Scene hands Tilemap::draw() the camera's view, and only the tiles inside it are drawn: LDtk layers through chunks of 16×16 cells, Tiled layers through their range of cells. Nothing is baked into a render texture, so the map stays exact at any zoom and costs no video memory. Measured on a 400×400 map: 87 ms a frame drawn whole, 0.25 ms culled, with the same pixels (ui_render_test checks that). See Tilemaps.

Collisions: a grid, and no tile colliders

Objects go through a uniform grid sized to the objects themselves, so each one is tested only against its neighbours instead of against everything (the O(n²) a beginner writes). The map's solid tiles are never turned into colliders: when the map is read, every source of solidity is folded into one table, and an object is moved in steps of at most half a cell and pushed out by bisection against that table. A map of any size adds the same few lookups per moving object. Fast objects use a swept test, so they cannot pass through a wall between two frames.

The UI allocates nothing per frame

rmp::ui is immediate mode on top of Clay, a layout engine written in C. Clay works in one arena reserved once; every string the UI is given in a frame goes into a bump arena that is reset at the next begin(). A menu redrawn every frame makes no heap allocation. Fonts are baked once per size, and a glyph is added to the atlas only the first time a text uses it.

The binary

  • Size is budgeted. Every binary a release ships has a line in tools/size_budget.txt, and CI fails a growth of more than 10 % that nobody wrote down. A 2D game's release is a few hundred KB packed.
  • No iostreams in the library. One std::ifstream once added 19 % to the Linux binary and 18 % to the web's .wasm; files are read with C's stdio now, and a check refuses an iostream header in the library.
  • Hardening costs little. FORTIFY_SOURCE, the stack protector and stack-clash protection together cost 2.0 % of the binary. PIE costs 5.5 % and stays on for security reasons (Security says why).
  • Debug is slow on purpose. The framework's own Debug runs under ASan and UBSan, about three times slower. A game's Debug has no sanitizers unless the game asks for them, and on x86-64 Linux it can compile its C with tcc to build in a fraction of the time. Measure performance in a release.

In practice: for a 2D game a frame costs what the same game written well in raylib costs, often less, because the culling, the grid and the arenas are things a game written in a hurry does not have. The framework never adds a draw call of its own beyond what it draws for you.

Where OpenGL by hand still wins: tens of thousands of moving sprites, particles that should live on the GPU, or a renderer built around instancing. raylib's batch rebuilds its vertex buffer on the CPU every frame, and the framework does not change that. A game that needs more can still call rlgl or OpenGL directly inside an object's _draw(): the framework does not stand in the way of either.
