The config pipeline

A game built for {{count:targets}} targets goes through four build systems: CMake, Gradle, Xcode and GitHub Actions. Each of them needs the same handful of facts — what the game is called, its identifiers on the stores, its window, which targets to build — and left to themselves they would each keep their own copy and drift. So there is one file you write, raylib_multiplatform.toml, one program that reads it, tools/configure.py, and everything the build systems read is generated from the two.

One file

The .toml is grouped by what each section is about:

[project]
name = "space_rocks"

[window]
title = "Space Rocks"
width = 960
height = 540

[app]
max_delta = 0.05

[targets]
enabled = ["desktop", "web", "android"]

A key you leave out takes its default, so a game's file holds only what it changes. Configuration lists every key with its default and what it is for — and that page is itself generated from configure.py --print-schema and the comments of the framework's own .toml, so it cannot describe a key that does not exist.

Never

Put a secret in it. The .toml is committed, and some of its values end up in the shipped binary. Signing keys, store tokens and passwords live in the CI's secrets, which the workflows read and the .toml never mentions. Even [resources] rres_password is obfuscation and says so: it is inside the binary that uses it.

Refused before anything compiles

Before configure.py writes a single file it checks every value: its type, its range, the values it may take, and the combinations that cannot work together. A mistake stops there, in well under a second, with the line of the file it is on, what is wrong, and what to write instead. The build never sees it.

[project]
name = "my game"

The wrong type is caught the same way. An array where a number goes would otherwise reach a generator as something it cannot format:

[window]
width = [800]

And so are two values that are each fine on their own and wrong together. A frame cap of 15 frames per second makes every frame longer than the default [app] max_delta, so the game would be handed less time than really passed, every frame, forever:

[window]
fps = 15

The rule behind it is strict on purpose: a configuration mistake that reaches the compiler is a bug in configure.py, not in the configuration. A mistake found twenty minutes into a CI run on somebody else's machine costs twenty minutes and an explanation; the same mistake found here costs a second and points at the line. And a refusal is only kept honest by a test that feeds it the value it refuses: those live in tests/configure_test.py.

One more check is kept for releases. When a game is released — by rmp deploy, or by a version tag pushed to its repository — configure.py also refuses an Android application id or an iOS bundle id that is still a placeholder under com.example., the kind rmp new writes, for a platform the game is built for. A Google Play application id can never be changed once it is published, so this is the one mistake worth stopping a release for, and the one not worth stopping a debug build for.

Who runs it

You never have to. CMake runs it at the start of every configure, before project() — the project's name comes out of it — and configures again by itself when the .toml changes. Every rmp command that builds goes through CMake, so rmp run after an edit to the .toml picks the edit up.

Gradle and XcodeGen never run CMake, so the CI jobs for Android and iOS run python3 tools/configure.py themselves before they start. The BSD jobs build inside virtual machines that have no Python at all; there CI generates everything on the Linux runner first and the files travel into the machine with the rest of the checkout. A CMake configure that finds no Python 3.11 or newer falls back to what was generated last time, and says loudly that edits to the .toml will not be seen.

A run writes a file only when its content changed, so configuring again after touching nothing rebuilds nothing.

The manifest is generated rather than templated through Gradle for a reason worth knowing: Gradle's placeholders can change the value of an attribute but cannot remove an element, and a permission is exactly an element you either ask for or do not.

The version is not in the .toml. A release takes it from its git tag — v1.2.3 is version 1.2.3, and Android's version code is computed from it so it always goes up — and every other build is 0.0.0-dev. A tag that is not vMAJOR.MINOR.PATCH is refused rather than published under a made-up number.

The generated header

The values a game can use at run time — the window's size and title, the input dead zone, the volumes the audio buses start at, the save settings, [app] max_delta — are written to include/rmp/generated/config.h as macros. Every public header of the framework includes it through rmp/config.h, so whichever header you were including anyway, they are there:

const float centre_x = RMP_WINDOW_WIDTH / 2.0f;
const float centre_y = RMP_WINDOW_HEIGHT / 2.0f;
TraceLog(LOG_INFO, "%s starts at %.0f, %.0f", RMP_WINDOW_TITLE, centre_x, centre_y);

They are macros and not C++ constants because a game in plain C uses them too, and C has no namespaces to put a constant in. Each one is named after its key: [window] width is RMP_WINDOW_WIDTH. Macros lists all of them, read from configure.py --print-defines.

The values that only a build system needs — the store identifiers, the targets, the backend — never reach the header. A game cannot read what it has no use for, and a value read in two places is a value that can disagree with itself.

Questions it answers

The same program answers the questions the CI and the tools ask, so none of them parses the .toml on its own:

  • --check validates and writes nothing.
  • --print-targets, --print-families and --print-matrix tell the CI which targets are enabled and which jobs to run for them; a family with no enabled target is skipped whole.
  • --print-schema and --print-defines describe every key and every generated macro, which is where this site's Configuration and Macros pages come from.
  • --config checks another file instead of the project's: every .toml block on this site goes through it, and a block that shows a refusal prints the message configure.py really gives, as on this page.

Nothing generated is committed

Every file in the table is ignored by git, and the framework's own CI fails if one is ever tracked. Generated files that are committed go stale the first time somebody edits the source and forgets to regenerate; files that are written on every configure cannot. rmp clean deletes them with the build directory, and the next configure writes them again.
