Ten years and more

The framework is meant to be usable long after anyone works on it every day, on desktop Linux above all. This page is about that horizon: which parts last because of what they are, which parts rot on a schedule or by accident, what has to be kept somewhere of your own, and how much of the machinery around the code one person needs to run.

What lasts

The source
C++20 for the framework, C for raylib and the libraries it vendors. Compilers keep accepting the standard a project asks for: CMAKE_CXX_STANDARD is 20, written down, so a newer compiler's default does not change what the code means. The libraries are committed, not fetched: nothing has to still exist upstream.
The build
CMake with a recent minimum, 3.30, so the policies it relies on are new ones that later versions keep; no FetchContent, no package manager. And a generator that uses Python's standard library only (Python).
The binaries already shipped
A Linux release asks for an old glibc on purpose, through zig, and glibc keeps its old symbols; it opens X11 and OpenGL through the system's libraries. On a Wayland desktop it runs through XWayland, and [linux] wayland = true builds GLFW's Wayland backend in as well. On a machine with no desktop at all there is the DRM target. A web build is WebAssembly and WebGL, which browsers do not drop.
The knowledge
The reasons are written beside the code: CLAUDE.md (the rules and every mistake that has cost time once, with how it was found), the skills under .claude/skills/, TECHNICAL.md, the comments at each patch site, every PATCHES.md, and this site, checked against the code.

A desktop Linux build, decades from now

Two ways to build, and both should keep working:

With the archived image

Exact: the same compilers, the same libraries, the same checks CI ran, bit for bit. It needs a container engine that can still run an x86-64 or arm64 Linux image, and the archive below. Load it, then run the ladder in it as Setting up describes, with --network=none: nothing in it needs the network.

With the system's own tools

What will exist then: the distribution's compiler, CMake and Python. The framework needs

  • a C and C++20 compiler, GCC or Clang;
  • CMake 3.30 or newer and Ninja;
  • Python 3.11 or newer, with nothing installed;
  • the X11 and OpenGL development headers — Wayland's too with [linux] wayland = true, or libdrm, gbm, EGL and GLES for the DRM target.

Then a clone and rmp build release. That binary asks for the glibc of the machine that built it; for one that also starts on older distributions, build it as CI does, with tools/linux_build.sh, which uses zig to aim at the floor [linux] glibc sets. What can go wrong is small and visible: a new compiler's warning in a framework check built with warnings as errors (a game's build is not); a deprecation in CMake; a Python that removed a module. Each one is a red with a line number, not a mystery. What will not match is exactness: the e2e shots and the coverage floors were measured in the image, and are reported, not enforced, outside it.

Try it before you need it

The image path is proved every day by CI. The system path is proved by nothing, and it is the one that will be left. Once a year, build and run rmp test in a container of the newest release of a mainstream distribution, with its own packages — the canary's job for the far future. A red there is the cheapest one you will ever fix.

What to archive

Keep these in a place you control, outside GitHub, and add to it every time a pin moves:

  1. Every image the framework has pinned, with its index, so its digest still means the same bytes. skopeo copies a multi-architecture image to a file and back without changing a digest: 
    DIGEST=$(sed -nE 's/^build_image_digest +//p' thirdparty/FROZEN_VERSIONS.md)
skopeo copy --all --preserve-digests \
    "docker://ghcr.io/omardev29/raylib-build@$DIGEST" \
    "oci-archive:raylib-build-${DIGEST#sha256:}.tar"
    The same for run_alpine_digest and ghcr.io/omardev29/raylib-run-alpine. Each build image is around ten gigabytes per architecture; they compress well. To serve one again, copy it back to any registry with the same command reversed, and point the digest's places at that registry.
  2. Every repository, whole: git clone --mirror of the framework, the image repository, this site, and the raylib-iOS fork the submodule points at — a commit only the fork has is the one thing no other copy holds.
  3. The signing material: the Android upload keystore and its passwords, Apple's certificates. They are not in any repository, on purpose; a lost Android upload key cannot be replaced by you.
  4. A released build of each game, every target, as the release attached it: the proof of what worked, to compare against.

The image is the important one. It is the only copy of every file it was built from that sits in one place: the Ubuntu packages at that snapshot, CMake, zig, Emscripten, the Android SDK and NDK, the Gradle home, LLVM and Mull, the locked Python tools. With it, every Linux, web and Android build can be repeated with no network; without it, a rebuild depends on every one of those addresses serving the same bytes years later.

Without GitHub

The workflows are GitHub's format and run only there. Everything they check, though, is a stage of rmp test or a script under tools/ that runs on a laptop or in the image: every stage has a step in CI, and a test holds the two to each other. So if GitHub's CI went away, the checks would not: the ladder in the image is the same set, run by hand. What would be lost is what only a hosted runner gives — macOS and Windows machines, the BSD virtual machines, the scheduled campaign — and the installer's and this site's addresses.

With one person

The framework was built by many agents at once, and its rules and gates are what let them work without stepping on each other. One person keeping it alive needs less of that machinery each day, but not less of the gates: they are what make a change safe to merge after a year away, when nobody remembers the caveat that a gate encodes. What changes is how much of it runs, and when.

Three things make the time go furthest:

  • Few, large maintenance sessions. Once a year, the round; otherwise, a dependency only when a game needs it. Every bump between them is risk with no game asking for it.
  • The nightly issues first. The campaign opens one issue per new signature, with the command that replays it. One found and fixed is a crash a player never meets.
  • Best effort where it is written down. The BSDs are best effort; a red BSD job after a green fast lane is a platform-specific bug, fixed once, and never a reason to hold the rest. What a target ships, or dropping one, is Omar's decision and nobody else's.

And when a gate is wrong — a test that reads a workflow's text after the text moved for a good reason — fix the gate, with the test that shows it was wrong. A gate turned off to get green stops protecting the next person, who after a year away is you.
