The yearly round

A pinned build does not change by itself. What changes is around it: a store that will not accept an app built with last year's SDK, a runner that no longer has the Xcode the framework pins, a BSD release whose packages are gone. None of them breaks the code. Each of them breaks a job, or a publication, on a date somebody else chose.

Desktop Linux, the web and the BSDs' code have no store and no yearly gate. A Linux release built years ago still starts on a new distribution: it asks for an old glibc on purpose, and glibc keeps its old symbols.

The canary

Pinning hides that the world moved. Every Monday the framework's repository runs the same reusable workflows as CI against the floating versions — the image's :latest, the newest macOS and Windows runners, the newest Xcode and Mesa — and its report leads with what moved between the pin and what it found, then the error. A red canary is the yearly round arriving early: it says which pin will break, before anyone needs to publish.

After a red canary, autofix.yml starts an agent on the failing family's own runner that proposes a fix as a draft pull request. It can change the versions block, not the workflows — the token it has cannot push to .github/workflows — which is why every floating pin lives in thirdparty/FROZEN_VERSIONS.md. Its pull request is a proposal; it goes through review like any other.

Scheduled workflows stop

GitHub disables a repository's scheduled workflows after 60 days with no activity in it. A framework left alone for a season stops running its canary, its nightly campaign and this site's daily drift check, and nothing says so. When you come back, re-enable them in the repository's Actions tab, and run the canary by hand first: it says what moved while nobody was looking.

Once a year

  1. Read the last canary run and its upstream report: what is newer than every pin, and what fails with it.
  2. The Android set, if a game is to be published or updated on Google Play in the coming year: the target API the Play Console asks for, and the AGP, Gradle and NDK that support it. One pull request in each repository, in order.
  3. Xcode, if the App Store's requirement moved: the new version on the pinned runner, or the runner that has it; the iOS simulator job; the fork, if it needs a change.
  4. The runner labels GitHub has announced it will retire.
  5. Dependabot's pull requests for actions and Playwright, in both repositories, merged once their runs are green.
  6. The BSD releases, when a pinned one has lost its packages.
  7. The full matrix once, after the bumps, on main: gh workflow run ci.yml -f full=true. A release tagged from it is a known-good point to come back to.
  8. Archive the image digests pinned that year (Ten years and more).

Everything else waits for a reason. A dependency that is old and works is not a task.
