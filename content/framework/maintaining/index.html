Maintaining

These pages are for whoever keeps the framework working after it is written: the person who bumps a dependency, rebuilds the build image, answers a store's new requirement, or comes back to the repository after a year away and needs it to build again. Contributing says how to make a change; Maintaining says what changes on its own, where every version is held, and what to do about each one.

The framework is built to need little: every dependency it compiles is a copy in the repository, every tool CI uses is pinned to a version and a checksum, and a check fails when two places that hold the same version disagree. Pinning stops the world from breaking a build. It does not stop the world from moving, and the pages here are about the places where it moves anyway.

In short

WhatMoves on its own?What it costs
The C and C++ code, raylib and the vendored librariesNo: they are copies in the repositoryNothing until you choose to upgrade one. A new compiler can bring new warnings.
The Linux, web and Android toolchainNo: one image, named by its digestA rebuild when you want a newer tool; the image itself stays usable as long as a copy of it exists.
The Windows and macOS runners, XcodeYes: GitHub retires runner images and the Xcode versions on themA pin bump when a pin disappears, every year or two.
Android: SDK, NDK, AGP, GradleYes: Google Play raises the target API every yearA bump of the whole set, and an image rebuilt for it, once a year to keep publishing.
iOS: Xcode, the raylib-iOS fork, ANGLEYes: the App Store requires a recent XcodeA new Xcode, and the fork made to build with it, once a year to keep publishing.
The BSDsYes: their package mirrors are rolling and old releases lose themA version bump when a release ages out; best effort.
PythonSlowly: the generator and rmp use the standard library onlyLittle. The test tools in the image are a lock regenerated with the image.
GitHub ActionsYes: actions are pinned by commit, but runtimes are deprecatedDependabot's monthly pull requests, read and merged.

The order in which the cost arrives is the order of the list: the desktop builds keep working for years with no change at all; the stores ask for a change every year whether the game changed or not. The yearly round puts dates on it.

Where every version lives

One file holds the list: the versions block of thirdparty/FROZEN_VERSIONS.md. It is not documentation that can drift: tools/versions_check.sh parses it and compares every value with the file that really controls it — the Gradle files, the Gradle wrapper, every workflow that names the image — and, inside the build image, with the manifest the image carries. rmp test config runs it. A bump starts there, and the check names every other place that has to follow.

Before a maintenance session

  1. Read Setting up if the machine is new: Python 3.11 or newer, CMake, Ninja, the pinned clang tools, and Docker or podman for the image.
  2. Run rmp test on an untouched main first. A red before you change anything is the world having moved, and the stage that is red says where.
  3. Look at the last canary run and its upstream report: it says what is newer than every pin, and what breaks with it (the canary).
  4. Open issues labelled nightly-finding come first, as in any other session.
  5. One dependency per pull request. A bump that moves two things at once cannot be bisected when the matrix goes red twenty minutes later.
