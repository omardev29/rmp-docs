Macros

The preprocessor runs before the compiler knows what a type, a scope or a namespace is: a macro is text pasted into every line after it, in every file that includes it, raylib's and the C library's included. So the rule is short. A macro is for what nothing else in the language can do, and everything else is a constexpr constant, a function or a template. Every macro that is written is named RMP_.

This page is the rule as it applies to any code written here. The framework's own macros — the entry point, the values of the .toml, the said-once warning — are explained one by one in why the framework has the macros it has.

A constant is constexpr

A constant made with #define has no type, so 3 is whatever the expression around it makes of it, and no scope, so it replaces that word everywhere after it — in your files and in every header included after it. A constexpr constant has both, and is just as known when the program compiles:

#define RMP_LIVES 3

constexpr int LIVES = 3;

In a header, a constant at namespace scope is inline constexpr, one object for the whole program; const has why.

A function is a function

A function-like macro pastes its arguments in as text: the one below, handed i++, increments twice; an argument of the wrong type is an error inside the expansion; and a debugger cannot step into it. A constexpr function does the same work at compile time when it can, and is a function the rest of the time:

#define RMP_SQUARE(x) ((x) * (x))

template <class T> constexpr T square(const T x) { return x * x; }

static_assert(square(3) == 9);

When a macro is the right tool

Four things no function can do, and they are the four the framework's own macros do.

Code at file scope. A program's entry point is a main() on a desktop, a function handed to the browser on the web and three extern "C" functions on iOS. No function can define a function, so the entry point is a macro, and a game writes it once:

RMP_GAME(MainMenuScene);

The call site. A function receives a value; it cannot see how the call was spelt, and it cannot give each place that calls it a variable of its own. A macro can do both. This one prints the expression it was handed as well as its value, through the # operator, which turns an argument into a string:

#define RMP_SHOW(value) TraceLog(LOG_INFO, "%s = %d", #value, value)
const int lives = 3;
RMP_SHOW(lives);

The framework's said-once warning is the other half of the same case: every place RMP_REPORT_ONCE is written gets a static variable of its own, whose address is the key that makes it say its line once, and only a macro can declare one there.

Conditional compilation. The same source is built for every target, and some of it only makes sense on one of them. That is an #if on a macro the platform defines:

#if defined(PLATFORM_WEB)
const int touch_target = 44;
#else
const int touch_target = 32;
#endif
DrawRectangle(0, 0, touch_target, touch_target, RED);

A value from the .toml. What raylib_multiplatform.toml says reaches the code as macros, RMP_WINDOW_WIDTH and the rest, because a game in plain C reads them too and because #if can test them. The .toml writes them; a game only reads them:

const Vector2 centre{ RMP_WINDOW_WIDTH / 2.0f, RMP_WINDOW_HEIGHT / 2.0f };
DrawCircleV(centre, 8, RED);

Checked by cppcoreguidelines-macro-usage, in the framework and in the examples. It refuses a macro that could be a constant or a function, and lets through one that uses # or ##, which nothing else can do. The framework's own macros are named to it one by one, in its AllowedRegexp, so a new macro in the framework is a question for whoever reviews it, not something that slips past. clang-tidy's suggestion to turn the .toml's values into an enum, modernize-macro-to-enum, is switched off for them: the C entry point reads them too.

Every macro starts with RMP_

The preprocessor has one namespace, shared by raylib, the C library, every vendored library and the game, and two macros of the same name are one silently replacing the other. So every macro written here starts with RMP_; names that start with two underscores, or with one and a capital letter, belong to the compiler and the C library:

#define NAME_OF(x) #x

#define RMP_NAME_OF(x) #x

Checked by readability-identifier-naming, which is given RMP_ as the macros' prefix, in the framework and in the examples, and by rule R5 of tools/naming_check.sh in every branch of every #if. A vendored library's own switches keep their names, in the one file of the framework that configures it, and the script lists each of those by file.

A name that no longer exists is 0

An #if on a macro nobody defines is not an error: the name is 0. When a macro is renamed, every test of the old name keeps compiling and quietly takes the other branch. The CMake option is PRODUCTION_BUILD, and what the code sees is RMP_PRODUCTION_BUILD; written the CMake way, this draws the frame rate in every build, a release included:

#if !PRODUCTION_BUILD
DrawFPS(10, 10);
#endif

#if !RMP_PRODUCTION_BUILD
DrawFPS(10, 10);
#endif

Checked by rule R7 of tools/naming_check.sh, which keeps the list of retired names, in every branch of the framework and the examples. For RMP_PRODUCTION_BUILD the framework goes further: every build system defines it, and src/rmp/app.cpp refuses to compile if one forgets.

A constant is never named like a macro

The other direction of the same collision: a constant called PI compiles until the file includes raylib.h, which defines PI as a number, and then the declaration is a number followed by an equals sign:

constexpr float PI = 3.14159265f;

Here the error is immediate. With a macro that only some platforms define — MIN and MAX on the BSDs, DEBUG in Android's debug build — it compiles everywhere except there. Naming has the rule and the list; rule R6 of tools/naming_check.sh refuses a constant named like any macro the vendored headers or the C library define.

No header makes you write one

Outside the entry point, nothing in the API asks for a macro. rmp::ui sits on Clay, whose API is macros, and hands a game functions that take a lambda instead; the rule has how. A game that wants Clay's macros can include Clay and use them.
