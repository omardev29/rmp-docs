Pointers and RAII

No raw pointer: not in what the framework hands a game, not in its own sources, not in its tests or its examples. And nothing freed by hand: whatever is owned is owned by something that frees it when it goes. The two rules are one idea from two sides — every thing has an owner you can see, and everything that refers to it says how.

Why no raw pointer

A pointer asks whoever reads it three questions — may it be null, who owns what it points at, how long does that live — and its type answers none of them. Each form below answers all three, so a signature written with them needs no comment to be used right. Google's guide allows a pointer for an optional argument or a result that may be missing; this framework does not, and has a type for each of those cases instead.

A reference, for what is there

void reset(int *score) { *score = 0; }

void reset(int &score) { score = 0; }

The framework's API reads the same way. A spawned object always has its scene, so scene() is a Scene &; a control that edits a value takes it by reference, as slider does.

std::optional, for an answer that may not be there

const Door *first_open(const std::vector<Door> &doors) {
    for (const Door &door : doors) {
        if (!door.locked) return &door;
    }
    return nullptr;
}

#include <optional>

std::optional<Vector2> first_open(const std::vector<Door> &doors) {
    for (const Door &door : doors) {
        if (!door.locked) return door.position;
    }
    return std::nullopt;
}

std::span, for the caller's elements

A pointer and a count are two arguments that have to agree, and nothing makes them. A std::span is the two in one, from a std::array, a std::vector or a list written in place.

float average(const float *values, const int count) {
    float sum = 0;
    for (int i = 0; i < count; ++i) sum += values[i];
    return count > 0 ? sum / static_cast<float>(count) : 0;
}

#include <span>

float average(std::span<const float> values) {
    float sum = 0;
    for (const float value : values) sum += value;
    return values.empty() ? 0 : sum / static_cast<float>(values.size());
}

It works the other way too: raycast_all writes every hit along a ray into a span of yours, as many as it holds, and says how many it wrote.

std::array<rmp::RayHit, 8> hits{};
const int count = raycast_all({ .from = { 0, 200 }, .to = { 800, 200 } }, hits);
DrawText(TextFormat("%d in the way", count), 10, 10, 20, WHITE);

rmp::Ref, for something that may be missing

An rmp::Ref<T> is empty, or refers to something; it owns nothing, and asking it is an if. It is what get<B>() hands back, empty when the object has no B, and what Handle::get() hands back, empty once the object is gone. Keep it within the frame; across frames, keep the handle.

rmp::behavior::Health *health_of(rmp::Object &object) {
    if (auto health = object.get<rmp::behavior::Health>()) return &*health;
    return nullptr;
}

auto &player = spawn({ .size = { 26, 26 } });
player.add<rmp::behavior::Health>({ .hp = 3 });

if (auto health = player.get<rmp::behavior::Health>()) health->heal(1);

Reaching into an empty one without asking is a mistake in the game, and the framework says so once, in the log; the line that forgot the if then writes to a stand-in made for the purpose instead of taking the game down. [dev] strict stops a debug build there instead.

It is a type of the framework's own because the standard library's spelling, std::optional<std::reference_wrapper<T>>, costs <functional> in every file with an object in it, and reads health->get().hp.

In a public header

Everything a game can name — every function, field, variable and alias in include/rmp/ outside a detail namespace and outside a private member — is read by tools/pointer_check.py: clang dumps each header's declarations and the script refuses a pointer, a C string, or an alias that hides one. Reading the declarations and not the text is the point: a comment is not a declaration, a private member is not public, and using SampleFn = ... is seen through.

#pragma once

#include <string_view>

namespace rmp {
class Object;

Object *find(std::string_view name);
} // namespace rmp

#pragma once

#include <string_view>

namespace rmp {
class Object;
template <class T> class Ref;

Ref<Object> find(std::string_view name);
} // namespace rmp

Where a pointer is allowed

Nowhere but here, and each place for a reason:

  • A type of a C library the framework speaks to — Clay, cJSON, cute_tiled, cute_aseprite, rres. Their API is pointers, and that is not a choice the framework made.
  • An extern "C" function and its parameters: a fuzzer's entry point takes its input as a pointer, because that is its C interface.
  • operator->, which the language requires to return one. It is how health->hp reads, on a Ref and on a Handle.
  • Inside rmp::Ref: its one member is the optional reference, so that nothing else has to hold one.
  • C: the resource packer, the plain C example and the sanitizer hooks are C because they have to be, and C has nothing else.

raylib is not on the list. A raylib function that takes an address takes it in a call, and an address in a call is not a pointer anybody declared:

Camera3D camera = { .position = { 10, 10, 10 }, .up = { 0, 1, 0 }, .fovy = 45 };
UpdateCamera(&camera, CAMERA_ORBITAL);

The rule is newer than some of the code. In the public headers, the pointers a game cannot reach — in a detail namespace or a private member — are listed in tools/pointer_ratchet.txt, each with its reason, and the list only shrinks: a new one fails until it is replaced or written down, and a line that matches nothing any more fails too.

Everywhere else — the framework's sources, its tests, its examples — what the code still owes the rule is counted, file by file, in tools/lint_debt.txt. rmp lint fails a pointer that is not owed there, and a count that grew; the counts only go down.

RAII: the owner frees it

What is owned is a value or a std::unique_ptr, and it is freed by its destructor: no new, no delete, no malloc, no free. A delete nobody wrote cannot be forgotten, and one nobody wrote cannot run twice. The order of the way out is the order the owners go, which is what makes it safe to free a texture before the window that its memory belongs to.

Two files of the framework allocate with the C allocator, and tools/ownership_check.sh names them with the reason: raylib's file-loading callback and the resource pack's reader hand raylib bytes that raylib frees itself, with UnloadFileData(). That is raylib's C interface, not an ownership the framework chose, and the list only shrinks.

int wave_hp() {
    auto *boss = new Enemy();
    const int hp = boss->hp;
    delete boss;
    return hp;
}

int wave_hp() {
    const Enemy boss;
    return boss.hp;
}

When it has to be on the heap — something polymorphic, or too big to move about — it is a std::unique_ptr, made with std::make_unique, and the hand-over is written in the signature. That is how a scene is made: change() makes the next one with std::make_unique, and the stack owns it from there.

#include <memory>

struct State {
    virtual ~State() = default;
    [[nodiscard]] virtual float speed() const = 0;
};

struct Walking : State {
    [[nodiscard]] float speed() const override { return 120.0f; }
};

std::unique_ptr<State> first_state() { return std::make_unique<Walking>(); }

A raylib resource has an owner too

raylib hands out textures, sounds and fonts that are freed by a matching Unload. In a scene, an object or an example, a forgotten one is a leak and a second one is a double free, so a raylib Load* or Unload* appears only in the few files of the framework that own what it makes. A game loads through rmp::assets, which hands back a handle that frees the resource when its last copy goes:

const Texture2D rabbit = LoadTexture("rabbit.png");
DrawTexture(rabbit, 100, 100, WHITE);
UnloadTexture(rabbit);

const rmp::Texture rabbit = rmp::assets::load_texture("rabbit.png");
DrawTexture(rabbit, 100, 100, WHITE);

Ownership has what owns what in the framework — assets, objects and their handles, scenes, globals, callbacks — and why a callback is an rmp::Callback and not a std::function.

What you open closes itself

RAII is not only for memory. A container of the UI is opened by the function that takes its body and closed by a guard in that same function. The body is a lambda, so a return in it ends the body and not the container, and the guard closes the container even if the body throws: one left open would spoil the whole frame.

rmp::ui::panel([&] {
    rmp::ui::text("Paused");
    if (rmp::ui::button("Resume")) resume();
    if (rmp::ui::button("Quit")) quit();
});
