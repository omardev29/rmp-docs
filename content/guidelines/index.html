Guidelines

How C++ is written here: in the framework, in its examples, and in a game that wants to read like them. In the framework and the examples the rules on these pages are mandatory, and a tool holds every one a tool can tell apart from its mistake; in a game they are advice, and the game decides how much of the tooling it takes. When a question has more than one good answer, three sources decide it, in this order.

Who decides

  1. The API is as simple as possible for whoever uses it. This outranks every other rule. A main menu is three functions, and a rule that would make it longer loses, whatever else it buys. The three-function menu says why.
  2. The rules on these pages, each with its reason: the naming table, the layout, const, no raw pointer, and nothing owned by hand, text in and out, the C++ written where C would also compile and macros — and the framework's own decisions in why it is built this way, such as one header per module and no exceptions.
  3. Google's C++ Style Guide, for everything the first two leave open. Where the framework has decided otherwise its decision holds, and Google's guide, and where this one differs lists each place with its reason.

Every rule, and what holds it

A rule written only in a document is kept until the day somebody has not read it. So wherever a mistake can be described precisely, a tool refuses it: a check of clang-tidy, which rmp lint runs; a gate, which is a stage of rmp test; clang-format; or the compiler. Shown, and checked like the code

Each rule is shown in code, and the code on these pages is checked the way the framework's own is. A block that shows the right way is compiled against the framework's headers, and passes, with nothing to say, clang-tidy with the framework's .clang-tidy, clang-format with its .clang-format, and its text gates: tools/naming_check.sh, tools/style_check.sh, tools/ownership_check.sh and, for a block that is a public header, tools/pointer_check.py. A block that shows the wrong way says what refuses it, and the build of this site runs that tool on it and fails if it stays quiet; what the tool printed is under the block, from that run, never typed. A block that does not compile at all is shown with what the compiler said.

What a game gets

A game made with rmp new gets two things from these pages, and the rest is advice:

  • .clang-format, so rmp fmt lays out the game's code the framework's way, and rmp fmt check refuses a file that is not. Neither runs unless the game runs it: its rmp test and its CI leave the layout alone.
  • -Werror=reorder-init-list, which the framework's library hands every target that links it: under Clang, designated initialisers out of declaration order are an error, as they already are under GCC and MSVC.

Its own code is also compiled with the warnings the framework's is: -Wall -Wextra under GCC and Clang, with -Wno-missing-field-initializers, because leaving fields of an options struct out — { .width = 8 } — is how the API is written. That is every build CMake makes, the desktop's and the web's; Android's and iOS's own projects build without them. They stay warnings: a newer compiler on its author's machine must not stop a build that was fine yesterday. A game can configure with -DRMP_WERROR=ON to make them errors, as the framework's own checks do. The vendored libraries are included as system headers, so the warnings are about the game's code and not about theirs.

It does not get the framework's .clang-tidy, its text gates or its cppcheck: rmp lint is a command of the framework's own repository, and in a game it says so and stops.

Switching on the framework's clang-tidy

There is no setting in the .toml for it. A game that wants the framework's checks on its own code copies the framework's .clang-tidy into its root and runs clang-tidy itself. The game already has what clang-tidy needs: its CMakePresets.json is the framework's, and the lint preset writes the compile database without building anything.

cp ~/.local/share/rmp/.clang-tidy .
cmake --preset lint
clang-tidy -p build/lint --experimental-custom-checks --warnings-as-errors='*' \
    --exclude-header-filter='.*/(include/rmp|src/rmp|thirdparty|generated|build)/.*' \
    src/main.cpp src/scenes/*.cpp
  • The .clang-tidy is the one of the framework rmp runs from: the clone rmp install made, in ~/.local/share/rmp on Linux and macOS and in %LOCALAPPDATA%\rmp on Windows.
  • --experimental-custom-checks runs the two queries of the framework's own, the raw pointer and the constant in a header; without it clang-tidy skips them and says nothing. The framework pins clang-tidy 22.1.8, in thirdparty/FROZEN_VERSIONS.md, and its file is written for that one.
  • --warnings-as-errors='*' makes a finding fail the run, which is what a check is for. The framework's file says WarningsAsErrors: '' because rmp lint counts its warnings against a list of what the framework still owes.
  • --exclude-header-filter keeps the framework's copy in include/rmp/ and src/rmp/ out of the report: the framework answers for those files, and its lint still owes some of them a few raw pointers.

clang-tidy then says nothing about the game rmp new writes, and refuses a C cast added to its main menu the way the framework's lint would.
