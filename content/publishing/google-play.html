Google Play

Google Play takes a signed Android App Bundle — an .aab, not an APK, and not the debug build. CI builds, signs and verifies one on every run. With your upload key in four repository secrets, it signs with that key and a release tag attaches the bundle to the GitHub release, ready to upload in the Play Console. Nothing is uploaded to Play for you.

The application id is permanent

Once an app is published on Google Play, its application id can never change: not renamed, not moved. A different id is a different listing, without the installs and reviews of the old one. It is [android] application_id:

[android]
application_id = "com.yourname.yourgame"

Letters, digits and _, at least two parts separated by dots, each starting with a letter; no -, which Apple's bundle ids allow and Android's do not. rmp new writes com.example. followed by the game's name, and every com.example. id is treated as a placeholder: rmp deploy refuses to tag a release under one, and so does CI when a tag is pushed by hand — refusing to build a release with placeholder identifiers. Only you know whether the id you replace it with is one you want to live with.

Signing

Play needs the bundle signed with your upload key. You make it once, keep it, and hand it to CI as secrets.

  1. Make an upload keystore, and keep it somewhere you will not lose it:

    keytool -genkey -v -keystore upload.jks -keyalg RSA -keysize 2048 -validity 10000 -alias upload

    Turn on Play App Signing in the Play Console, so Google can reset your upload key if you do lose it.

  2. Add four repository secrets, with exactly these names, under Settings → Secrets and variables → Actions:

    SecretValue
    ANDROID_KEYSTORE_BASE64the keystore file, base64-encoded on one line: base64 -w0 upload.jks
    ANDROID_KEYSTORE_PASSWORDthe keystore's password
    ANDROID_KEY_ALIASthe key's alias — upload above
    ANDROID_KEY_PASSWORDthe key's password
     
    base64 -w0 upload.jks | gh secret set ANDROID_KEYSTORE_BASE64
gh secret set ANDROID_KEYSTORE_PASSWORD
gh secret set ANDROID_KEY_ALIAS
gh secret set ANDROID_KEY_PASSWORD

  3. Optionally, name the key. Set the repository variable ANDROID_SIGNER_CN to the CN of your upload key's certificate. Without it, CI can only check that the bundle is not signed with its throwaway key — which every wrong key passes too. With it, CI checks the bundle is signed by that one.

Never

Never commit the keystore, and never write its passwords in raylib_multiplatform.toml or anywhere else in the repository. Whoever has the upload key and its passwords can publish as you.

What CI does with them

The bundle is built and signed on every run, secrets or not — it is the one artifact you cannot afford to test for the first time on release day. What the secrets change is which key signs it:

Signed withArtifact of the runOn the release
No signing secrets (the default)a throwaway key made for that runandroid-unsigned-aab, a file ending in -NOT-FOR-PLAY.aabnever
ANDROID_KEYSTORE_BASE64 setyour upload keyandroid-release-aabyes, on a tag

Either way the bundle is then checked, not trusted: jarsigner -verify -strict has to verify it, and the certificate that signed it is read back and compared — a run with your key fails if the bundle carries the throwaway signature, if jarsigner reports errors in the signer's certificate, or, with ANDROID_SIGNER_CN set, if the signer is anyone else. A further step reads the compiler commands Gradle used for the bundle and fails unless the game was compiled as a release.

The release build is minified, its unused resources removed, and it is not debuggable.

Signing on your own machine

The same bundle can be built locally with Gradle. The signing configuration reads the key from the environment, never from a file in the repository:

export ANDROID_KEYSTORE_FILE=/path/to/upload.jks
export ANDROID_KEYSTORE_PASSWORD=...
export ANDROID_KEY_ALIAS=upload
export ANDROID_KEY_PASSWORD=...
cd raymob && ./gradlew bundleRelease

The bundle is written to build/outputs/bundle/release/ inside raymob/app/. Without ANDROID_KEYSTORE_FILE it comes out unsigned, which is fine for a look and refused by Play. rmp android builds the debug APK, which is what you install on your own phone with adb install -r.

The version code

Play orders the builds of an app by its version code, and refuses an upload whose code is not higher than the last one it took — for good: a code once uploaded is spent. The code comes from the tag, MAJOR * 1000000 + MINOR * 1000 + PATCH, so it rises with every version you tag in order (Releases and versions has the limits). A pre-release shares its version's code: v1.2.0-rc1 and v1.2.0 are both 1002000, so upload one of them, not both. Builds that are not tags have code 1 and are not for Play.

Uploading

The framework uploads nothing to Play: the bundle is on the GitHub release, and the Play Console is where it goes from there.

gh release download v1.2.0 --pattern '*.aab'

Upload it to a track in the Play Console — an internal testing track first is the quick way to put a release on your own phones before anyone else gets it — and promote it from there.

What Play asks of the build

  • A recent target SDK. The app targets and compiles against API 36, which Play requires of new apps and of updates from 2026-08-31. Play raises that requirement about once a year, and meeting it means moving the Android SDK, the NDK, the Android Gradle plugin and Gradle together, as one set.
  • 16 KB pages. The native code is built with NDK r28, whose default is the 16 KB ELF page alignment Play requires alongside that target.
  • The oldest Android is [android] min_sdk, 24 by default (Android 7.0), between 21 and 36.
  • Who is offered the app. [android] gl_version is the OpenGL ES version the app requires, ES30 by default: devices without it are not offered it. [android.features] does the same for a gyroscope or an accelerometer the game cannot do without; false still declares the sensor, as optional.
  • What it asks for. Every permission is visible on the listing. [android.permissions] has internet and vibration, both off by default; internet is turned on regardless when AdMob is in the build.
  • How Play files it. [android] category, "game" by default.

Ads, and the Data safety form

[android.admob] enabled is true in the .toml a new game starts with, with Google's official test ad ids. With it on, the Android build carries the Google Mobile Ads SDK, the AD_ID permission, and the duty to declare advertising-id collection in Play's Data safety form — and the INTERNET permission with it. A game without ads should turn it off; its rmp::ads calls, if it has any, still compile and do nothing:

[android.admob]
enabled = false

A game with ads replaces the three test ids with its own before it publishes. Showing ads to players in the EEA or the UK requires a Google-certified consent platform, and the framework does not ship one: with ads on, that traffic is served badly or not at all until the game adds it.

Real devices on Firebase Test Lab

CI never starts the Android build itself: an emulator inside a runner with no acceleration is slow, and fails for reasons that have nothing to do with the game. Firebase Test Lab installs the APK on a real phone in Google's lab, lets its robot explore the game for up to five minutes, and reports whether it started and kept running.

It is optional, and off until it is configured:

[deploy.firebase]
project_id = "your-gcp-project"
device     = "model=MediumPhone.arm,version=33,locale=en,orientation=portrait"

project_id is a Google Cloud project id — lowercase letters, digits and hyphens — and empty means off. device is the device to run on, in gcloud's notation; the line above is the default. Google retires device models every few years, so check that the one you name still exists with gcloud firebase test android models list.

[deploy.firebase]
project_id = "My Game"

Setting it up, once:

  1. Create or pick a Google Cloud project, and give it Blaze billing: Test Lab has no free quota.
  2. Enable its APIs: gcloud services enable testing.googleapis.com toolresults.googleapis.com.
  3. Create a service account with the roles roles/cloudtesting.testAdmin and roles/cloudtoolresults.testAdmin.
  4. Create a JSON key for it, and store the whole file as the secret GCP_SA_KEY.
  5. Optionally, set the repository variable FIREBASE_RESULTS_BUCKET to a Cloud Storage bucket, and give the service account roles/storage.objectAdmin on it: the results are written there and fetched back into the run.

The repository variables FIREBASE_PROJECT and FIREBASE_DEVICE are read too, and when set they win over the .toml.

Test Lab runs on full runs only — a tag, or a run started by hand with full — after the Android build. It sends the debug APK and refuses anything else: the robot taps whatever it finds, ad banners included, and the debug build shows Google's test ads, where a release build would send invalid clicks to your real ad units. The results are kept with the run for seven days as firebase-testlab-results. A failure there fails its own job and does not hold back the release.

There is no iOS equivalent here: Test Lab needs a signed .ipa for iOS, and that needs an Apple developer account.
