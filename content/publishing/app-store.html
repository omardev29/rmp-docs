The App Store

CI builds the iOS engine and a simulator build of your game, and checks the app it made. It does not archive, sign or upload anything to Apple, and that is deliberate: an app a phone will install has to be signed, and signing needs an Apple developer account and credentials that do not belong in CI. The step from a working build to TestFlight and the App Store is made in Xcode, on a Mac, from a project the framework generates.

What CI builds

iOS is in the full matrix: it builds on a tag, and on a run started with full, on a macOS runner with its Xcode version pinned. The job:

  1. builds raylib.xcframework, for devices and for the simulator, from the raylib-iOS fork pinned as the submodule thirdparty/raylib-ios — upstream raylib has no iOS backend, and the fork draws through ANGLE, OpenGL ES on top of Metal;
  2. generates the Xcode project from raylib_multiplatform.toml;
  3. builds the app for the simulator, without signing;
  4. checks what it built: the executable is a Mach-O, the bundle's Info.plist has a readable bundle identifier, and your resources/ folder is inside the bundle.

Two files go to the release from it: ios-raylib-xcframework.zip, the engine, and ios-app-simulator.zip, the app. The app is a debug build for the simulator, unsigned; it runs in the iOS Simulator and cannot be installed on a phone.

Starting the app in the simulator is part of the job and switched off: the simulator on the pinned runner does not come up reliably, and a step that is known not to work is off rather than allowed to fail quietly. Set the repository variable IOS_SIMULATOR_TEST to true to try it; it then installs the app, runs it, and requires the same boot and render markers as every other platform.

Trying the simulator build

On a Mac with Xcode, from the release's ios-app-simulator.zip:

unzip ios-app-simulator.zip
xcrun simctl boot "iPhone 16"
open -a Simulator
xcrun simctl install booted my_game.app
xcrun simctl launch --console booted com.yourname.yourgame

What CI does not do, and why

Archiving, signing, TestFlight and submitting to the App Store are not automated. Apple only installs a signed app on a device, and signing takes a paid Apple Developer account, a provisioning profile and a certificate. Those cannot live in a public repository, and the framework does not ask for them as secrets either: the release path that touches Apple's credentials runs in Xcode, on your Mac, under your account.

For the same reason the iOS app is never run on Firebase Test Lab: Test Lab needs a signed .ipa for iOS.

Onto a phone, and to the App Store

On a Mac with Xcode and an Apple developer account, from your game's folder:

  1. Fetch the fork. A game made with rmp new has the submodule registered and not checked out, since only iOS needs it:

    git submodule update --init

  2. Build the engine, the same way CI does:

    cd thirdparty/raylib-ios/projects/scripts
chmod +x build-ios-xcframework.sh
./build-ios-xcframework.sh
cd ../../../..

  3. Set your team in the .toml, rather than in Xcode, so it survives the next time the project is generated. [ios.settings] is copied into the Xcode project as build settings, word for word:

    [ios.settings]
DEVELOPMENT_TEAM = "ABCDE12345"
CODE_SIGN_STYLE  = "Automatic"

  4. Generate the project and open it. tools/configure.py writes ios/project.yml, and XcodeGen turns that into the Xcode project — CI uses the XcodeGen version pinned in thirdparty/FROZEN_VERSIONS.md:

    python3 tools/configure.py
cd ios && xcodegen generate
open my_game.xcodeproj

  5. Run it on your phone: select the device and press Run.

  6. Archive it for TestFlight and the App Store from Xcode, with Product → Archive, and upload the archive from there.

The Xcode project is generated, so a change made to it by hand in Xcode is gone the next time it is generated; whatever the project needs belongs in [ios], [ios.settings] or the rest of the .toml.

What is different on iOS

  • The game cannot quit itself. Apple's guidance is that an iOS app that terminates itself appears to the player to have crashed, and App Review rejects that. rmp::app::quit() logs a warning and does nothing on iOS, so the same source ships everywhere and a Quit button is simply inert on a phone. Hide it there if a dead button bothers you:

    #if !defined(PLATFORM_IOS)
if (rmp::ui::button("Quit")) rmp::app::quit();
#endif

  • raylib is prebuilt. The app links the fork's raylib.xcframework, so [raylib] disabled_modules changes nothing on iOS.

  • No ads. rmp::ads does nothing on iOS; ads are implemented for Android only.

  • The frame is paced by the display. [window] fps is ignored on iOS.

Keeping up with Xcode

Apple requires submissions to be built with a recent Xcode and SDK, and raises that bar about once a year. Building with a newer Xcode means updating the raylib-iOS fork and the ANGLE it bundles to one that supports it, and moving the Xcode pin in thirdparty/FROZEN_VERSIONS.md, which is where CI reads the runner and the Xcode version from.
