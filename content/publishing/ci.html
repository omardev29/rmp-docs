Continuous integration

Every game made with rmp new carries the framework's CI, and it runs as soon as the game's repository is on GitHub. A push builds the targets that catch most mistakes, starts the game and looks at the pixels it draws, in about ten minutes; a tag builds every target the game enables — all {{count:targets}} of them unless it switches some off — and publishes the release. Building is the easy half: the point of the pipeline is that a game which compiles and draws nothing is a red run.

When it runs

EventWhat runs
A push to main, a pull requestThe fast lane: linux-x64-glibc, web, windows-x64 and android, and the lint job. Nothing at all with [ci] on_push = false.
A tag starting with vThe full matrix — every target [targets] enables — then the GitHub release, then itch.io.
Started by handThe fast lane, or the full matrix with full, or exactly the groups and targets targets lists, separated by commas.

A push or pull request that changes only Markdown files or LICENSE runs nothing. A target switched off in [targets] is never built, on any event.

gh workflow run ci.yml -f full=true      # every enabled target, without a tag
gh workflow run ci.yml -f targets=drm    # one group or target, built in full
gh workflow run ci.yml -f targets=linux-x64-glibc,windows-x64,macos

targets narrows what the .toml enables and can never add to it. It takes one group or target, or several separated by commas, and builds what they come to together, each in full. A name that does not exist, one whose targets the .toml all switched off, one given twice and an empty one between two commas each stop the run in its first job, saying which item it was: a run that asked for a platform and quietly did not build it would be a green that proved nothing about it.

The last line above is how to check a fix for a red fast lane on just the platforms it involves, before the next push.

A third input, image_digest, builds with another build image than the pinned one, to try a new image before committing to it.

A new push to a branch cancels that branch's run still in progress — a run of a commit nobody wants any more is minutes wasted. A tag's run is never cancelled. To push without killing a run you are waiting for, use rmp push: it asks gh for the CI runs that have not finished, refuses while there is one and names it, and rmp push force pushes anyway.

The check needs gh, installed and signed in. Without it, or when gh cannot list the runs, rmp push says so in one line and pushes without checking — and a run in flight is cancelled all the same.

Only when you ask: [ci] on_push

Running on every push is what keeps a mistake from waiting for the release to be found, and for a public repository it costs nothing. A private repository pays in Actions minutes, from a monthly allowance, and a fast lane on every commit can spend it. One line of the .toml turns those runs off:

[ci]
on_push = false

Then a push to a branch starts no run, and neither does a pull request. A tag v* still builds every target and releases — which is what rmp deploy pushes — and gh workflow run ci.yml runs the fast lane whenever you want it, or the full matrix with -f full=true. true, the default, is the table above.

It is applied by writing the workflow, not by a condition inside it. GitHub reads a workflow's on: before any of its expressions runs, so a run that should not exist cannot skip itself from the inside; it can only not be started. So tools/configure.py writes the push and pull_request triggers of .github/workflows/ci.yml from this line, on the next build, between two marker lines:

on:
  # BEGIN generated by tools/configure.py from [ci] on_push: edit the .toml, not this block
  # [ci] on_push = false: no run on a push to a branch, and none on a pull
  # request. A tag v* still builds every target and releases, and
  # `gh workflow run ci.yml` runs the fast lane by hand.
  push:
    tags: ['v*']
  # END generated from [ci] on_push
  workflow_dispatch:

Nothing else in the file is generated, so a game that turns pushes off still has the framework's ci.yml in every other line. Commit ci.yml with the .toml: GitHub runs the workflow that is committed, not the one on your disk. A ci.yml whose triggers say something else than the .toml is refused, at the .toml's line, by rmp test config and by the first job of CI, which only compares and never writes:

[ci] on_push = false, and the triggers in .github/workflows/ci.yml are not the ones it writes.

rmp push knows: with on_push = false a push starts no run and so cancels none, and it pushes without asking gh. Unless ci.yml has changes that are not committed yet — the commit being pushed may still have the old triggers, and then it checks as it always does.

What each target gets

A target is booted when CI starts the game, lets it draw a bounded number of frames, and checks what it printed. It is checked statically when CI inspects the file it built without running it — its format, its architecture, what it links.

Next to the platforms, the lint job runs on every push. In a game it checks the workflows (actionlint, with shellcheck over every script in them), validates the configuration, compares every pinned version across the files that state it, checks the size budget when the game has one, checks every licence, runs the game's own tests in tests/game/ — and says it skipped them when there are none — and draws a frame with raylib's software renderer, in a debug build that runs under whatever [dev] sanitize lists. In the framework's own repository it also runs the framework's tests and gates, and jobs of its own run clang-tidy over its code, build and boot every example, play the examples that have a script, measure what the framework's tests reach, make a game with rmp new to test it — and a copy of that game in plain C, made the way examples/plain_c says, booted and its release started from the project folder and from another — and check this documentation against the commit. A release of the framework waits for every one of those jobs; in a game they are skipped, and the release does not wait for them.

What booted means

Every booted target but the web runs with RAY_TEST_MAX_FRAMES set, which makes the game draw that many frames and exit. The web test cannot set it: it opens the page with ?ray_test_save=1, which asks the game for the save round trip the other targets do under that variable, lets it run for fifteen seconds, screenshots the canvas, and closes the browser — the game itself never exits. The game prints markers. The boot marker is printed on every launch that opens a window, a player's included; the frame read-back and the frame count happen only under RAY_TEST_MAX_FRAMES, and in a normal run, with the variable unset, they do not exist. Every booted target requires the first marker with assets_failed=0 — the Linux runs, musl and DRM among them, Windows, macOS, the BSDs, the web, and the iOS simulator when it is on — and the runs on Linux, Windows, macOS and the BSDs require all three; the web test reads the boot marker from the browser's console and measures the canvas itself:

RAY_TEST_BOOT_OK assets_failed=0
A window opened, and every asset the game asked for was found and decoded: a file that is there and cannot be read as an image, a sound, a song or a font counts as failed, the same as a missing one. Neither stops a game from starting, which is why the count is part of the marker.
RAY_TEST_RENDER_OK
A frame was read back, and the share of its pixels that differ from its most common colour is in a sane range. A broken shader or a lost texture still boots and still exits cleanly; a blank frame does not pass this.
RAY_TEST_DONE_FRAMES
The game drew every frame of its budget without dying: a crash in the middle of a run fails here. It is printed at the end of the last frame, before the game shuts down, so a crash while it shuts down comes after it.

A crash on the way out — in the game's stop hook, or as the window closes — comes after every marker, and only the exit code catches it. So does a leak, which LeakSanitizer reports as a sanitized debug build exits. These runs read the exit code, and fail on anything but 0: the Linux x64 and ARM64 boots and their archives started from another folder, the RISC-V archive under QEMU, the Windows boot, both starts on Alpine, the DRM boot, the software-rendered runs on macOS and the BSDs and in the lint job, the release started from another folder on macOS and the BSDs, and rmp test smoke and rmp test render. The software-rendered runs and the two rmp test stages fail on a sanitizer's report as well. The iOS simulator's boot is the one that does not: the app is launched in the background and its log read, so a crash after its last frame passes there.

The markers come from tests/smoke_test.h, which every game carries. The share of pixels is the gate everywhere because GPUs and software renderers disagree on the details of a frame; where the frame is drawn by raylib's own software renderer it is identical on every system, and the framework's own CI compares it with a recorded hash as well. A game has no recorded frame, so its software render checks the boot, the pixels and that every frame of the budget was drawn.

What no job checks

  • windows-arm64 and linux-arm64-glibc-drm are never run, and linux-riscv64-glibc runs only under an emulator, which is not a RISC-V machine.
  • On macOS and the BSDs, what is booted is a software-rendered build of the game, not the executable that ships; the shipped one is checked statically.
  • A binary compressed with UPX is started only on linux-x64-glibc, linux-arm64-glibc, linux-x64-musl, linux-x64-glibc-drm and linux-riscv64-glibc, whose jobs start the archive they ship — the five [upx] compresses by default. On a target added to [upx] enabled beyond those, it is only verified with upx -t.
  • iOS is not started unless you turn the simulator test on, and Android is not started unless Firebase Test Lab is configured.
  • Nothing here plays your game. A game that boots and draws and is broken from its second screen on passes every gate. Test your game on the platforms you ship.

The size budget

A release is kept as small as it can be, and without a number written down nothing would notice it growing by a third between two releases. So every release job — Linux, Windows, macOS, the BSDs and the web, and Android once per ABI of the bundle — runs tools/size_check.py on its binary as soon as it is final, and holds it to its line in tools/size_budget.txt: the size as the linker wrote it and, for a target [upx] compresses, the size of the copy that ships. Within 1.5% of the line, either way, it passes and says nothing. Past that it passes with a warning that names the new number, in the log and on the run's summary page, where a passing job's log is never read. Past 10% it fails. Over is a growth nobody wrote down; under is a stale line, which would let the next growth through without a word. Growing is allowed: the line is where it is written down, in the commit that grows it.

# binary               kind    unpacked    packed
linux-x64-glibc        elf      1310720    389120  # measured at 1a2b3c4
windows-x64            pe       2293760         -  # measured at 1a2b3c4

That is how a game's budget reads. Each line is a binary, what kind of file it is, its size unpacked, and its size packed or - where UPX does not apply, with the commit it was measured on. Every check prints the line it measured in that same format, pass or fail, so one run's log is all an update needs:

gh run view 12345678 --log | python3 tools/size_check.py --update -

A game starts without a budget: rmp new does not copy the framework's, whose sizes are its own demo game's. A game's release jobs measure all the same, print each line and say the game has no budget, and the lint job says so too instead of failing. To start one, run the full matrix once — a tag, or gh workflow run ci.yml -f full=true — then create an empty tools/size_budget.txt, fill it from that run's log with the line above, and commit it. From then on the game is held to it exactly as the framework is: the lint job checks the file on every push — a line for every binary an enabled target ships, none for one nothing ships, a packed size exactly where [upx] compresses — and every release job holds its binary to its line.

What is pinned

A green run should mean the same thing in six months as today, so what a build depends on is pinned wherever it can be:

  • The build image, by digest. The Linux builds, the web and Android builds, the lint job and the itch.io upload run inside ghcr.io/omardev29/raylib-build, named by its sha256 digest and never by a tag, which could be moved. The image carries the compilers and tools those jobs use — CMake, Ninja, Emscripten, the Android SDK and NDK, zig, UPX, butler, actionlint and shellcheck, LLVM 18 with the runtimes the sanitizers need, cppcheck, and the Python test tools — so none of them is fetched while a job runs. It is built for x86-64 and ARM64, each on a runner of its own architecture, and each is checked before the image is published. Its own packages come from a dated Ubuntu snapshot, and the build jobs print the image's manifest as their first step, so a log says which toolchain produced it.
  • Gradle, from the image. The image also carries a Gradle home warmed for the framework's Gradle wrapper, its Android build plugin and the AdMob SDK, and the Android job runs Gradle with --offline from it: the job downloads nothing, and a library the image lacks fails the build at once, by name. --offline does not reach the wrapper, so a step first checks, by the wrapper's own rule, that the Gradle it asks for is in the image, and fails naming it when it is not. A game that adds a Gradle dependency of its own sets [android] gradle_offline = false: Gradle then downloads what the image lacks, and the job says so in a warning. rmp android on your machine is never offline.
  • The runners and Xcode. Runner images by explicit label, never -latest, and on macOS an explicit Xcode version, with a step that fails and lists what is installed when the pinned one is gone. A label fixes the operating system, not every tool GitHub installs on it: the Windows jobs build with the compilers the runner image carries. The windows-x64 job builds with whichever compiler CMake finds first on the runner's PATH, and prints which one built the .exe; the windows-arm64 job builds with the newest Visual Studio the runner has, and has no such step.
  • Every download the other jobs make — Ninja and XcodeGen on macOS, Mesa and UPX on Windows — at a fixed version, checked against its sha256; Pillow, which the Windows jobs install to make the icon, comes from PyPI with pip --require-hashes, so no other file is accepted. Chromium itself, for the web test, comes through Playwright, pinned by package-lock.json.
  • The Alpine the musl build is started on is the framework's own image, ghcr.io/omardev29/raylib-run-alpine, by digest: Alpine itself pinned by its digest, with the virtual X server, Mesa and the X libraries an Alpine desktop gives the game, and checked when it is built by drawing on it. The job downloads nothing into it, and every container it starts runs with the network off. No workflow takes an image from Docker Hub. Every container that starts a game, here and in the DRM job, has an init as its first process, so that a game that hangs is ended by its step's timeout instead of holding the job until the job's own limit: a program that is a container's first process ignores a SIGTERM it has no handler for.
  • Every GitHub Action, by the full commit it resolves to, with the tag in a comment beside it.

The versions live in thirdparty/FROZEN_VERSIONS.md, the first job reads them from there and hands them to the others, and tools/versions_check.sh — part of rmp test config and of the lint job — fails if any two places disagree. A game keeps the pins it was made with; they change when the game changes them.

The exception is the BSDs. Their virtual-machine images and package mirrors move from day to day, and neither offers a snapshot to pin to, so those jobs install whatever the mirror serves that day. When a BSD job fails after the rest of the run passed, and nothing you changed explains it, suspect the mirror first. The arm64 machines are emulated on an x86-64 runner, which makes their jobs the slowest of a full run, and each BSD job is allowed two hours.

Two other exceptions are narrow. The job that boots DRM installs the kernel's extra modules on its runner when the virtual display driver is missing from it, after the binary it tests has already been built: it is the one place a Linux job downloads.

And the web test installs the system libraries Chromium needs with playwright install --with-deps, which takes them from the runner's Ubuntu package mirror at whatever version it serves that day; nothing pins or checksums them. The game it tests is built before, in the image.

The canary

Pinning stops the world from breaking a build, and it also stops anyone from noticing that the world moved. The framework's own repository runs a canary every Monday: the same workflows against the newest build image, the newest runner images, the newest Xcode and the newest Mesa, to find what the next bump of the pins will break before anyone needs it. It runs only in omardev29/raylib_multiplatform, and rmp new does not copy it into a game: a game's CI never runs it.

The runtime tests say which marker is missing. Locally, rmp test smoke builds the game, boots it for a few frames and makes the same two checks:

rmp test smoke
rmp test render

and stops with FAIL: the game did not boot, or an asset failed to load or FAIL: the game booted and drew nothing when one of them is not there. rmp test render builds the game for raylib's software renderer, with no window and no GPU, and runs exactly the check the macOS and BSD jobs run.

Some jobs leave something to look at: the web test uploads its screenshot of the canvas as web-canvas-capture when the frame was wrong, and the Windows test tries Mesa's llvmpipe, softpipe and d3d12 drivers in turn and says which ones failed before it gives up. A yellow warning on the itch.io or Firebase job is not a failure: it is the job saying what is not configured, and skipping.
