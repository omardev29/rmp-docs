Troubleshooting

Each entry here is a problem that really happens, with what the framework prints when it does. A message set like rmp: not inside a project is the framework's own words, checked against its source; a line of the log that starts with INFO: or WARNING: is raylib's log, which the framework writes into too.

Most of the framework's warnings about a game are said once, however many frames they happen in. With [dev] strict = true the first one stops a debug build instead, in the debugger, at the line that caused it, saying [dev] strict = true: the diagnostic above is fatal in a debug build. Fix it, or set strict = false in raylib_multiplatform.toml. A release build never stops for one.

Before anything builds

Python is missing, or too old

rmp and the configuration need Python 3.11 or newer, because they read the .toml with the library that version added. The launchers ask every Python they find for its version, rather than taking the first one, because the obvious one is often wrong: the python3 macOS ships is older than 3.11, and on Windows python3 can be the Microsoft Store's placeholder. A Python older than 3.11 is passed over like a missing one, and when none will do, the launcher says rmp: needs Python 3.11 or newer on PATH …. Only tools/rmp.py started directly with an older Python gets as far as saying rmp needs Python 3.11 or newer; this is …, with its version and its path.

CMake needs it too: cmake --preset debug runs tools/configure.py before anything else, and stops when it can find no Python 3.11 and nothing has been generated yet. When the files were generated before, it warns and builds with them — but then edits to the .toml are not picked up until a Python is there again.

A tool is not on the PATH

rmp says which one: FAIL: cmake is not installed, or not on PATH. A game needs CMake, Ninja and a C++ compiler; on Linux, the X11 development libraries as well.

rmp does nothing outside a game

rmp: not inside a project means there is no raylib_multiplatform.toml in the folder or above it. rmp works from anywhere inside a game; rmp new my_game makes one.

The .toml is refused

tools/configure.py reads the .toml before anything is compiled, and refuses a value it cannot build — or a pair of values it cannot honour together — with the file, the line, and what to write instead. This one asks for a frame rate the clamp on the frame time would turn into slow motion:

[window]
fps = 15

The message is the fix. rmp test config, or python3 tools/configure.py --check, checks the file without building anything. A key the framework does not know is refused as well, so a misspelt key cannot be silently ignored, and so is a value of the wrong type — a list where a string goes, the commonest being a stray pair of brackets — or an empty one where the key needs something, each at its line:

[window]
orientation = ["landscape"]

A release is refused

A tag builds a release, and a release under a placeholder identity is refused: refusing to build a release with placeholder identifiers, naming the Android application id or the iOS bundle id that still says com.example.. A Google Play id can never change once published, so it is checked before the first release rather than after it. Set real ids in the .toml. A tag that is not a version — v1.2.3, optionally with a pre-release part — is refused as well; see Releases.

Building

Switching between a debug and a release build

The debug and release builds share build/, and a CMake cache keeps the compiler it was first configured with — the one [dev] compiler chose, for a debug build — so a release configured on top of a debug cache would be built with your development compiler instead of the one CI ships with. rmp handles it: when build/ was configured as the other build type, it deletes it and starts again, saying removing build/ -- the compiler is cached and would carry over.

With CMake's presets used directly, the release configure stops instead, explaining that the directory was configured by the debug preset and that a release build must not inherit its compiler. rmp clean — or deleting build/ — and configuring again is the fix.

A link error about the entry point

A program has exactly one entry point: RMP_GAME or RMP_ENTRY_POINT, once, in one file. The symbol rmp_entry_point_is_declared_exactly_once exists so that the link error points at the cause either way. Two entry points define it twice, and the linker names it as a duplicate. A program with neither has no main(), and the linker names it as undefined, next to main: the framework's own code asks for it, so the error says what was forgotten instead of only that there is no main.

A handle that will not convert

This does not compile, on purpose:

Texture2D picture = rmp::assets::load_texture("rabbit.png");

The rmp::Texture the loader returns is a temporary that would release the texture at the end of the line, leaving picture pointing at a texture that had already been unloaded. Keep the handle — rmp::Texture picture = … — and hand it to raylib where raylib wants a Texture2D; it converts there.

Compiling the framework outside its build

RMP_PRODUCTION_BUILD is not defined: the build system has to pass it (0 or 1) comes from src/rmp/app.cpp when it is compiled by a build that does not define that macro. CMake, Gradle and the generated Xcode project all do; a build of your own has to as well.

Raw OpenGL links on the desktop and not in the tests

rmp test render and CI's render checks build the game against raylib's software renderer, which links no OpenGL library, so a direct glClear() in a game links on a Linux desktop and fails there as an undefined symbol. See rlgl and OpenGL.

Assets

A release build finds nothing

A debug build reads resources/ by its absolute path. A desktop release reads ./resources/, and moves into the executable's folder first when that folder has a resources/, so it finds the one shipped next to it wherever it is started from. Finding no pack where it looks, it logs ASSETS: No resource pack found, using loose files from …, and with no loose files there either, every texture comes back empty. The line before that one says why it looked there:

  • ASSETS: no … next to the executable; reading the working directory's, … — there is no resources/ beside the executable. Put it there, the way the archive does, or start the game from a folder that has one: the release rmp build release leaves in build/ reads the project folder's when it is started from the project folder.
  • ASSETS: this system does not say where the executable is, so … is read from the working directory, … — OpenBSD and NetBSD, where raylib cannot say where the executable is. Start the game from its own folder there.

An asset failed to load

Every run logs a line beginning RAY_TEST_BOOT_OK with assets_failed= and assets_requested=, and a checked run — rmp test smoke, and every boot test in CI — does not pass with a failed asset: FAIL: the game did not boot, or an asset failed to load. An asset failed when an rmp::assets load found its name neither in the pack nor in resources/, or found a file there that does not decode. Look for:

  • A misspelt name. Names are file names: "player.png", not a path.
  • A file in a subfolder. The pack holds the files directly in resources/ and does not reach into folders, and a release configure warns when it finds one. Move the file up.
  • A file that is there and does not decode. A picture, a font or a sound cut short, or in a format raylib does not read, counts as failed the same as a missing one, and says once ASSETS: '…' is in … but could not be decoded; a font is not replaced by raylib's built-in one under its name, it comes back empty. A song rmp::audio::music() cannot stream counts too, and says AUDIO: "…" is in resources/ but could not be streamed.
  • A pack that does not match the game. A packed picture that will not unpack says ASSETS: Failed to unpack '…' (code …, wrong password?) and then ASSETS: '…' not usable from pack, falling back to loose file; a packed sound or font says only the second, after rres's own warning that the decryption failed. That is a pack made with a different [resources] rres_password. rmp pack makes it again, or rmp unpack goes back to loose files. A name the pack does not hold says the second line too for a sound or a font, and ASSETS: '…' not found in pack, falling back to loose file for a picture.

Only loads through rmp::assets are counted. rmp::audio loads through it once it has found a file, so a sound or a song whose file is there and does not decode or stream counts too. A name that matches no file at all does not: rmp::audio says so once, below, and counts nothing — a missing sound does not fail the boot check. And on a machine with no sound device rmp::audio loads nothing, so none of its files are counted there. A LoadTexture() of your own that fails is not in the number, and leaves an empty texture all the same.

A sound does not play

rmp::audio finds a sound by its name. A name that ends in an audio extension — "coin.ogg" — is looked for as it is; a bare one — "coin" — as coin.wav, coin.ogg, coin.mp3 and coin.qoa, in that order. When there is nothing it says once AUDIO: no sound called "…" in resources/ (looked for …), naming the files it tried, and a file that is there and does not decode says AUDIO: "…" is in resources/ but could not be decoded (raylib here reads .wav, .ogg, .mp3 and .qoa). On a machine with no sound device it says AUDIO: no sound device on this machine; sound is off and every rmp::audio call is a silent no-op from here on, and the game runs on, silent. In a browser, sound waits for the player's first click, touch or key — see Web.

A window with nothing in it

The game booted and drew nothing

rmp test smoke says FAIL: the game booted and drew nothing when the frame it reads back is blank. Things that come to that:

  • Every texture is empty because the assets were not found — see above. An empty texture draws nothing rather than crashing: a hole in the picture, not a dead process.
  • The last scene was popped. The framework refuses, and says SCENE: pop() with … scene(s) on the stack would leave nothing to draw; ignoring. Did you mean rmp::app::quit()?
  • The interface hit its ceiling. UI: more than max_elements (…) elements in one frame. The interface will not lay out again until the game is restarted. Raise [ui] max_elements, or draw less at once.
  • Drawing in the wrong space. A scene's _draw() is in screen pixels, and objects are drawn through the camera. On a window that is not the design size, world coordinates drawn in _draw() without opening the camera land somewhere else — see raylib in your game.
  • The web build ran out of memory. The tab stops with Emscripten's "Cannot enlarge memory arrays". Raise [web] memory.

A key does nothing

An action read by a name nobody defined reads as false, and says so once: INPUT: no action called followed by the name and how to define it. An action that is defined can still be silent on purpose: a mouse action while the interface wants the pointer, a key action while the interface wants the keyboard, and every action in a scene whose input a scene above it has taken.

Escape does not close the window

On purpose. raylib makes Escape the key that closes the window, and the framework takes it back with SetExitKey(KEY_NULL) once the window is open, because in a game Escape is "back" and "pause": rmp::ui goes back on it. The window's close button still quits. To quit on Escape, call rmp::app::quit() when the game reads it — see Escape is the game's key.

On one platform only

Linux: "version GLIBC_… not found"

The binary was built against a newer glibc than the machine has. CI's builds honour [linux] glibc, the oldest glibc the binary may need; rmp build release on your own machine uses your machine's. See Desktop for the floor, and for the targets it does not apply to.

Linux on Wayland: the window has no position

With [linux] wayland = true, GetWindowPosition() and SetWindowPosition() do nothing, and GLFW warns the first time. That is Wayland's design: a window does not know where it is.

Windows: the executable is quarantined

An unsigned .exe compressed with UPX looks like malware to Windows Defender on some machines. Windows is left out of [upx] by default for that reason; if you added it and do not sign your builds, take it out again.

Web: a blank page, or no build at all

Opened as a file, the page cannot fetch the rest of the game — rmp web says serve it, do not open the file directly. Serve the folder over HTTP. Without the Emscripten SDK activated, rmp web stops at once with the web build needs the emsdk: activate it first (source emsdk_env.sh, or emsdk_env.ps1 on Windows), so that EMSDK is set.

Android: the sources changed after a build

The Android build rewrites raymob's package name in a few of its sources and puts it back at the end. A build that was killed half way leaves them rewritten, and the next build restores the wrong thing. After an interrupted Gradle build, check thirdparty/raymob/ and raymob/app/ for changes and put them back with git. Gradle also stops at once when raymob/generated.properties is missing; python3 tools/configure.py writes it.

iOS: Quit does nothing

On purpose: APP: quit() does nothing on iOS — Apple rejects apps that terminate themselves (QA1561). Ignoring. See iOS for why, and for hiding the button there.

OpenBSD and NetBSD: portable saves are not portable

SAVE: [save] portable: this system does not say where the executable is; saving in the user's folder instead — raylib cannot tell where the executable is on those two, so there is no "next to the executable" to save in.

In CI

There is no remote to push to

FAIL: there is no remote to push to. Make the repository on GitHub, then: … — a game made with rmp new is a git repository with no remote. Make an empty repository on GitHub, add it with git remote add origin and its URL, and run rmp push again. The first push of a branch sets its upstream on origin, so plain rmp push is all it takes from then on. rmp deploy on a branch that was never pushed says the same thing the other way round: push it first, with rmp push.

A run was cancelled

A push cancels the run already going on the same branch. rmp push refuses while one is in flight and names it; rmp push force is for when cancelling it is what you meant.

A BSD job failed, and nothing you changed explains it

The BSD jobs install their build tools from each system's package mirrors, which publish no dated snapshots, so what they install is not pinned and changes without a commit of yours. Suspect the mirror first, and run the job again.

The Android bundle is called NOT-FOR-PLAY

CI signed it with a throwaway key because the signing secrets are not set. See Android for the four secrets that make it a bundle Google Play accepts.

The iOS app is built but never started

Starting it in the simulator runs only when the repository variable IOS_SIMULATOR_TEST is true, because the simulator on the hosted runners does not boot reliably.
