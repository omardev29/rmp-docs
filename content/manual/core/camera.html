Camera

Every scene has a camera, an rmp::Camera, which decides what part of the scene's world is on screen. A scene that never touches it draws exactly as if it were not there, so a one-screen game never notices it; a level bigger than the screen is three lines.

auto &player = spawn({ .position = { 400, 300 }, .size = { 16, 24 } });
camera.follow = player.handle();
camera.smoothing = 10;
camera.limits = map.bounds();      // never show the void outside the level

Where it starts

The camera starts centred on the design resolution — half of [window] width and height — with no zoom and no rotation. At the design size that is the identity: a world unit is a pixel, and an object at { 100, 50 } is drawn 100 pixels from the left and 50 from the top, as raylib would draw it.

What it frames

Each frame, the scene draws its map and its objects through its camera, and then runs its own _draw() outside it, in screen pixels. So everything in the world moves with the view, and a HUD or a pause menu drawn in a scene's _draw() stays where it is while the player moves — which is why the interface in a scene's _draw() never drifts with the camera. An object's own _draw(), and its behaviors', run inside the camera, in world units like the object.

The window is not the design size

The window can be resized, and a phone's screen is whatever it is. The camera always fills the real window: what it shows, view(), is the window's size divided by the zoom, centred on position. So at a zoom of 1 a bigger window shows more of the world, not a bigger picture of the same part.

A game that wants the same slice of the world on every screen sets the zoom from the window, every frame, so a resize is followed at once:

if (GetScreenHeight() > 0) camera.zoom = static_cast<float>(GetScreenHeight()) / VIEW_HEIGHT;

That keeps 180 world units of height on screen whatever the window, and lets the width follow the shape of the screen. rmp::ui scales menus from the design resolution on its own; the world is scaled by the zoom you choose, because only the game knows whether a wider screen should show more of the level.

Following

With follow set to an object's handle, the camera centres on that object every frame — after the objects have moved and the collision pass has had its say, so it frames where things ended up and not where they were heading. It is a handle, so a target that is destroyed simply stops being followed, and the camera stays where it was. An empty handle leaves the camera wherever you put it.

Changing follow to a different object snaps to it instead of gliding across the level: a scene that opens with the camera drifting in from the middle of the screen is the other half of the classic smoothing bug.

Smoothing is a rate

smoothing is how fast the camera catches up, as a rate per second: 0, the default, is a snap, which is what a one-screen game wants; 5 is a gentle drift; 20 is nearly a snap.

It is a rate and not the fraction-per-frame that tutorials write — position += (target - position) * 0.1f every frame — because that version depends on the frame rate: at 120 frames a second it takes twice as many steps a second, and follows twice as fast as at 60. Here the fraction of the distance covered in a frame is 1 - exp(-smoothing × delta), with the frame's time in the exponent, so two frames of half the time land exactly where one frame of the whole time does, and the camera feels the same at 30 frames a second and at 144.

Limits

limits is a rectangle of the world the view never leaves. Near the edge of the level the camera stops and the player keeps going, instead of the screen showing a black strip past the end of the map. Limits win over following, and over smoothing too: they are applied after both, so a smoothed camera still never shows the void.

camera.limits = map.bounds();                          // the level, whatever its size
camera.limits = { 0, 0, 0, RMP_WINDOW_HEIGHT };        // a runner: free across, pinned top to bottom

Each axis is limited on its own, and a zero width or a zero height means that axis is not limited at all — which is exactly what an endless runner wants. A level narrower than the view, on an axis, centres the view on it rather than showing the void on one side. The limits apply to a position you write by hand as well, so a camera you move yourself — a title screen panning across the level — needs no arithmetic about the window to stay inside it.

Zoom and rotation

zoom scales the view about its centre: 2 shows half as much of the world, twice as big. Limits are worked out on the zoomed view, so a camera zoomed in can travel closer to the edge.

rotation turns the picture, in degrees clockwise. view() and limits ignore it: they describe the unrotated rectangle, and a rotated view can show a little past the limits at its corners.

Shake

camera.shake(8, 0.35f);   // up to 8 world units, fading out over 0.35 seconds

That is Breakout's, when a ball is lost.

shake(strength, seconds) shakes the view by up to strength world units, fading to nothing over seconds, 0.3 if you leave it out: a hit, an explosion, a landing. The fade goes with the square of the time left, so it reads as a jolt that settles rather than a buzz that stops, and the motion is a fixed pattern of waves rather than random numbers, which would change direction every frame and look like a broken monitor.

The shake never touches position or view(). It is an offset applied only to what is drawn, and to the two conversions below — so an object clamped to the view does not jitter, there is nothing to restore when it ends, and a click during a shake still lands on what is under the pointer, because the pointer is converted through the same shaken camera that drew the frame. The drawn view is kept inside limits too, so a shake near the edge of the level shakes inwards.

Shaking again while a shake is running keeps the stronger of the two, measured against what the running one is doing now rather than what it started at, instead of adding them up: a burst of hits in one frame cannot build a shake that throws the screen across the room. A short strong hit on top of a long shake lasts at least as long as the long one had left. A strength or a duration that is not a positive number is ignored. shake_offset() is how far the shake is moving the view right now.

The camera is moved, smoothed and shaken in its scene's update, so the camera of a scene frozen under a pause menu stands still, shake included, until the scene runs again.

World and screen

CallGives
to_world(screen)The world point under a point of the screen, in pixels from its top-left corner.
to_screen(world)Where a world point is on the screen.
view()The rectangle of the world that is visible, ignoring rotation.
raylib()The raylib Camera2D this camera is, shake included, for BeginMode2D().

The pointer is the commonest thing to convert, and it is already done: rmp::input::pointer() is the pointer in world units, through the current scene's camera, ready to compare with an object's position. An object's on_click is tested the same way. The other direction places something drawn in screen space over something in the world — a marker over the player's head, in the scene's _draw():

rmp::Handle<rmp::Object> _player;

void _draw() override {
    if (!_player) return;
    const Vector2 above = camera.to_screen({ _player->position.x, _player->position.y - 30 });
    DrawText("!", static_cast<int>(above.x), static_cast<int>(above.y), 20, YELLOW);
}

Drawing in world units yourself

A scene's _draw() is in screen pixels. To draw part of it in the world instead — a net across a court, a line from the player to its target — open the camera for the lines that need it:

void _draw() override {
    BeginMode2D(camera.raylib());
    DrawLineV({ 400, 0 }, { 400, 450 }, GRAY);    // in the world, moving with the view
    EndMode2D();

    DrawText("SCORE", 10, 10, 20, WHITE);         // on the screen, staying put
}

Drawing world things without it is right only while the window is the design size and the camera has not moved, which is exactly when the difference does not show — and on the first other window, the net ends up somewhere the court is not. Pong draws its net this way for that reason.

What reads the camera

Besides drawing, four things in the framework take the camera into account, so they follow it without anything written:

  • an object's edges, when its bounds are empty and the scene has no map, use the camera's view as the edge of the world;
  • on_click and on_drag find the object under the pointer through it, and on_drag hands over the movement through it, in world units, so a dragged object stays under the finger at any zoom;
  • rmp::input::pointer() answers in world units through it;
  • the Parallax behavior scrolls each layer by how far the view has moved.

Each scene has a camera of its own. A pause menu pushed over a level draws through its own camera, which nobody has moved, while the level underneath keeps its framing.
