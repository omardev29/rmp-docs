The app

The app is what runs a game: it opens the window, runs one frame after another, and closes everything in the right order on the way out — on a desktop, in a browser, on a phone. A game written with scenes meets it once, in the last line of src/main.cpp, and after that only when it wants to quit or keep something across scenes.

The entry point

This is the whole of src/main.cpp in a new game:




RMP_GAME takes the type of the first scene. It opens the
window from [window] in raylib_multiplatform.toml, puts that scene on the
stack, runs the stack every frame, and shuts everything down when the game ends. There is no
InitWindow(), no frame loop and no unloading in the game, because those were the same
lines in every game and none of them was ever yours to get right.



It also writes the entry point the platform expects, and the platforms do not agree on what that
is. The difference between them is who owns the frame loop:





PlatformWhat RMP_GAME writes



Windows, Linux, macOS, the BSDs, AndroidA main() with the frame loop in it: the game owns the loop. On Android, raylib's own entry point calls that main().


The webA main() that hands each frame to the browser: the browser owns the loop.


iOSThe three callbacks UIKit calls instead of a main(): UIKit owns the loop, and there is nothing to return to.






The web is a loop the browser runs and not a while loop for a reason that costs real
bytes. A loop that never returns would freeze the page, and the only way to run one there is
Emscripten's ASYNCIFY, which instruments every function that might be on the stack —
most of them — and makes the whole program larger and slower whether or not it ever waits. Handing
each frame to the browser is what lets the web build go without it.



Why the first scene is named in code



Naming the first scene in the .toml would mean looking it up by a string, and a
string-to-type lookup in C++ is built from objects that register themselves when the program starts.
In a static library, and in the prebuilt framework iOS links, the linker throws away any object file
nothing refers to — and a self-registering object is exactly that. It would not fail to compile; it
would work on your desktop and find no scenes on the phone. So the scene is named where a C++
program starts, in main.cpp, where the linker can see it.



A program with no entry point, or with two, is a link error that names the symbol
rmp_entry_point_is_declared_exactly_once: missing, or defined twice. That is clearer than
the linker's own complaint about main, which does not say what to write or which file
to look at.

The frame



Every frame runs the same steps in the same order, and the order is the contract — it is what
every property of the scene stack is built on:



    

  1. Input. The keyboard, mouse, touch and gamepads are read once, and the UI starts
its frame. Reading once is what stops two scenes in the same frame disagreeing about what is held
down.
    2. 

  2. Update, from the bottom of the stack upwards, for every scene that is running.
For each one: the pointer is offered to its objects (on_click,
on_drag), then the scene's
_update() runs, then its
objects update and move, then the
collision pass resolves where they ended up, and last the
camera follows.
    3. 

  3. Draw, from the bottom upwards, for every scene that is visible. The screen is
cleared with the background of the lowest of them; then for each scene its map and its objects are
drawn through its camera, and its own _draw() runs
after, in screen space.
    4. 

  4. Present. The frame goes to the screen and the UI ends its frame.
    5. 

  5. Deferred work. Objects destroyed during the frame are freed, and the scene changes
asked for during the frame are applied, in the order they were asked for.
    6. 




After each frame the music that is playing is fed, whatever else is going on — under a pause
menu too, since a streamed track that is not fed stutters.



delta



Every _update(float delta) receives the seconds the last frame took. Real time has no
ceiling: drag the window, stop at a breakpoint, let a disk stall, and a frame comes back half a
second long. A bullet moving 900 units a second then moves 450 units in one step, straight through a
wall it never overlapped.



So delta is clamped to [app] max_delta, a twentieth of a second by
default. A frame that really took longer arrives as that, and the game runs a moment of slow motion
instead of teleporting through the level: nobody minds a hitch, and everybody minds falling out of
the world. Setting max_delta = 0 switches the clamp off. A negative reading, which a
clock can produce across a suspend, arrives as 0.



The first frame's delta is 0, because raylib has no previous frame to measure from.



The frame rate



With [window] vsync on, the default, each frame waits for the screen's refresh, which
paces the game at the display's rate. [window] fps caps it, for a desktop without
vsync. The browser and iOS pace the frame themselves and ignore fps; never call
SetTargetFPS() in a game that builds for the web, where a wait inside the browser's frame
would only stall it.



Quitting



if (rmp::ui::button("Quit")) rmp::app::quit();




rmp::app::quit() can be called from anywhere — a
menu, a callback, ten calls deep in your own code — and it returns. It raises a flag that
the app checks before the next frame, so the frame you are in finishes normally, and then the game
shuts down exactly as it does when the window's close button is pressed. A second call does
nothing.



That is the reason not to call std::exit() instead: it ends the process on the spot,
so nothing is shut down, the window is not closed properly, and on Android the app's activity is left
behind while its process disappears. It is not an exception either. Exceptions are switched off in
plenty of game builds, unwinding through raylib's C code is undefined, and throwing in the middle of
a frame would leave a frame and a UI pass half open. A flag costs one check a frame and cannot leave
anything half done.



rmp::app::quit_requested() says whether it
has been called, for code that wants to skip work on the way out.



Per platform





PlatformWhat quit() does



Desktops and the webThe frame loop ends after this frame, and the game shuts down.


AndroidThe same, and the app's activity is finished, so that it goes away instead of leaving an empty task in the recent apps.


iOSNothing. It logs a warning, once, and returns.






iOS is not an oversight. Apple's guidance is that an app which ends itself "will appear to the
user to have crashed", App Review rejects apps that crash or appear to, and a quit control fails
Apple's interface guidelines by itself. So the same code ships everywhere, and on an iPhone the call
is inert and says so: APP: quit() does nothing on iOS … Apple rejects apps that terminate
themselves (QA1561). Ignoring. If a dead button bothers you, leave it out of the iOS build —
which is what the menu of a new game does:



#if !defined(PLATFORM_IOS)
if (rmp::ui::button("Quit")) rmp::app::quit();
#endif




iOS has the rest of what is different there.



The Escape key



On a desktop, the window closes when its close button is pressed, and also when raylib's exit
key is pressed — Escape, unless the game says otherwise. The framework leaves raylib's default as it
is. A game that wants Escape for something else, such as a pause menu, turns the exit key off once,
in its first scene:



SetExitKey(KEY_NULL);




The way out



However the game ends — quit(), the close button, the exit key — the shutdown is the
same, and its order matters, because a texture released after the window is closed is a write into a
graphics context that no longer exists:



    

  1. Every scene leaves the stack, top down, getting its _end(),
and its objects are destroyed after it, each getting theirs.
    2. 

  2. Every global is destroyed, in the reverse of the order they were first
used.
    3. 

  3. The UI's font, the sounds that are playing, and every texture, font and sound still held are
released.
    4. 

  4. The window closes.
    5. 

  5. The sound device and the asset pack, which own nothing on the graphics card, close last.
    6. 




Everything that owns something on the graphics card goes while the window is still open, so a
scene or a global that holds an rmp::Texture as a member
releases it safely without anyone writing an unload.



State that outlives a scene



A scene owns its state and loses it when it leaves the stack. That is exactly right for the
enemies of a level and exactly wrong for the player's best score. The second kind has one home,
rmp::global<T>():






rmp::global<Progress>().runs++;

Progress &progress = rmp::global<Progress>();
if (score > progress.best_score) progress.best_score = score;




The scene-stack example keeps its best score this
way, across a menu, a game and a pause overlay.



There is one instance per type, built the first time it is asked for and destroyed by the
framework on the way out, before the window closes. The type is the key: there is no registration,
no name and no lookup, and the type knows nothing about it — no instance() method, no
private constructor, no macro. Any type with a default constructor works, including a plain struct
written a minute ago.



It is called global because that is what it is, and a softer name would get used for
things that should have been passed as arguments — to a scene's constructor, for instance, which is
how a level number crosses a
transition. Reaching for it should be a decision, not a habit.



A global lives in memory for as long as the app runs; it is not saved anywhere. Keeping the best
score between launches is the job of rmp::save; see
Saving.



A global first asked for while the globals are being destroyed — by a destructor that reaches for
one late in the shutdown — is still a working object, but it is never destroyed by the framework, and
the log says so once: GLOBAL: a global was created while the globals were being destroyed; it
will not be destroyed by the framework.



Without scenes



RMP_GAME is built on a lower-level entry point, RMP_ENTRY_POINT,
which takes three functions of yours instead of a scene and runs them on the same platform runners:



static void on_ready() {
    SetConfigFlags(FLAG_WINDOW_RESIZABLE); // before InitWindow, or it is ignored
    InitWindow(RMP_WINDOW_WIDTH, RMP_WINDOW_HEIGHT, RMP_WINDOW_TITLE);
}

static void on_frame(float delta) {
    BeginDrawing();
    ClearBackground(RAYWHITE);
    DrawText(TextFormat("%.1f ms", delta * 1000), 20, 20, 20, DARKGRAY);
    EndDrawing();
}

static void on_exit() { CloseWindow(); }

RMP_ENTRY_POINT(on_ready, on_frame, on_exit);




There is no scene stack and no objects, and the window and the drawing are yours: the hooks are
on_ and not _ because they are functions you hand over. What the platform
runners do around them is the same as for RMP_GAME — the asset pack opened before
on_ready and closed after on_exit, the same clamped delta, the
same quit(), the music fed every frame. What RMP_GAME adds is the part that
reads [window]: with RMP_ENTRY_POINT, vsync and the frame cap are yours to
set, like the window.



The UI examples are written this way, because a menu needs no scene. Plain C is one step further
down: Plain C is a game with its own main(),
raylib, and none of the framework at all.
