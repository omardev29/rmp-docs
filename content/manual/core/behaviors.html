Behaviors

A behavior is a piece of how an object acts — moving like a platformer character, bouncing like a Pong ball, disappearing after two seconds — that you add to an object instead of writing it again. Add one and the object moves like that game; change its fields and it moves differently, while the game runs.

auto &player = spawn({ .position = { 200, 225 }, .size = { 26, 26 } });
player.add<rmp::behavior::TopDown>({ .speed = 240 });

What a behavior is

A behavior is any struct with a function void _update(rmp::Object &self, float delta). It inherits from nothing, has no virtual functions and is registered nowhere:

struct Spin {
    float degrees_per_second = 90;

    void _update(rmp::Object &self, float delta) {
        self.rotation += degrees_per_second * delta;
    }
};

and it is added to an object with its fields written in braces:

auto &coin = spawn({ .position = { 300, 200 }, .shape = rmp::circle(8) });
coin.add<Spin>({ .degrees_per_second = 180 });

That is the whole model, and leaving out a base class is not a matter of taste. A struct with virtual functions is not an aggregate in C++20, and then { .speed = 320 } no longer compiles against it. The usual way round — a nested options struct and a constructor that takes it — turns every later read into get<TopDown>()->options.speed. Without one, the fields are the configuration.

And the behaviors in rmp::behavior are structs exactly like that one. There is no extension API to learn, because there is nothing to extend: one of yours and one of the framework's are the same kind of thing, added, read and removed the same way.

Adding, reading, removing

CallDoes
add<B>({ ... })Attaches a B made from the braces, runs its _ready if it has one, and returns a reference to it.
get<B>()The object's B, as an rmp::Ref: empty when it has none.
has<B>()Whether it has one.
remove<B>()Takes it off, running its _end if it has one.

The fields stay live after the behavior is added. A power-up is one line:

auto &player = spawn({ .size = { 26, 26 } });
player.add<rmp::behavior::TopDown>({ .speed = 240 });

if (auto walk = player.get<rmp::behavior::TopDown>()) walk->speed = 400;

get() answers with an optional reference, and the if is how you ask it: true when the object has a TopDown, and then -> reaches it. Reaching into an empty one without asking is a mistake in the game: it is said once in the log, and the line writes to a stand-in instead of crashing. The reference add() returns and the one get() returns stay valid for as long as the behavior is attached: a behavior lives in memory of its own and never moves.

An object carries at most one behavior of each type. Adding a type it already has replaces the old one — its _end runs, then the new one's _ready — because two of the same is never what anybody means, and get() could only ever return one of them.

Behaviors run in the order they were added. One added from inside an _update gets its _ready at once and its first _update on the next frame. One removed from inside an _update — its own included, which is what a one-shot effect does — is taken off without costing any other behavior its turn in that frame.

When the object is destroyed, its own _end() runs first and then each behavior's _end, while everything the object owns is still there.

The hooks a behavior can have

The framework finds a behavior's hooks when it is compiled, from their names and arguments, so a hook a behavior does not declare costs nothing at all.

HookRuns
_update(Object &self, float delta)Every frame, before the object's own _update() and before it moves, so it can set the velocity the move will use.
_late_update(Object &self, float delta)Every frame, after the object has moved, been held to its edges and had its animation advanced.
_ready(Object &self)Once, when it is added.
_draw(Object &self)Every frame the object is drawn, after its sprite or shape and before its own _draw(), in world units.
_collision(Object &self, Object &other)Once per frame for each object the object touches, right after the object's own _collision(). The walk stops after any behavior once either of the two is no longer alive: the behaviors after one that destroyed either object hear nothing, and if one was destroyed before the walk began, only the first behavior hears it. See Collision.
_end(Object &self)When it is removed, replaced, or the object is destroyed.

A behavior needs _update or _late_update; every other hook is optional. _late_update exists because behaviors run before the move, which is what lets them write the velocity — so a behavior whose job is to correct where the object ended up needs a place after it. GridSnap is that: rounding the position the object had before it moved would round the wrong number.

A struct with neither, or one with virtual functions, is refused with a sentence that says why:

auto &coin = spawn({ .size = { 8, 8 } });
coin.add<Score>({ .points = 10 });

What a behavior keeps: ours

A behavior that has to remember something between frames — the time since a jump was pressed, whether it is standing on the ground — keeps it in one public member called ours:

struct Blink {
    float every = 0.5f;   // seconds between switches

    void _update(rmp::Object &self, float delta) {
        ours.elapsed += delta;
        if (ours.elapsed >= every) {
            ours.elapsed -= every;
            self.visible = !self.visible;
        }
    }

    void _end(rmp::Object &self) { self.visible = true; }

    struct {
        float elapsed = 0;
    } ours;
};

It is public and not private because a struct with a private member is not an aggregate, and then { .every = 0.2f } stops compiling — which is the whole design. The name is the fence: you can read what is in ours, and it is not yours to write. The catalogue follows the same rule, and where a value in it is worth reading it has a function that says so — Platformer::grounded() reads ours for you. rmp::Sprite keeps its animation state the same way.

None of them chooses for you

A behavior contributes how something moves, not what the game intends. Which way the Pong ball is served is a rule of the game, so a Ball starts still; a Projectile travels the way you pushed it; a Follow chases the handle you give it; and the character behaviors read the input actions you name, or the standard ones when you name none — the actions example shows how one is defined.

Some things are deliberately not in the catalogue, because they are already in it: a patrol is a Tween of a position with ping_pong on, a magnet is a Follow, and dragging is an object's on_drag.

The catalogue

Each one has a page in the reference with every field and its default. All of them come with rmp/behavior.h.

TopDown

auto &hero = spawn({ .size = { 16, 16 } });
hero.add<rmp::behavior::TopDown>({ .speed = 180, .eight_way = false });

TopDown walks in eight directions, seen from above, at speed units per second, reading the standard move_left, move_right, move_up and move_down actions unless you name others. Going diagonally is not faster, because the input it reads is normalised. With eight_way = false it walks in four, and the direction pushed harder wins. acceleration, 0 by default, is instant; a value is how fast it reaches its speed, in units per second squared. direction() is the last way it moved, for aiming a weapon where the character looks.

It also picks the animation. With a sheet on the object's sprite, moving plays walk_<direction> when the sheet has such a tag and walk mirrored with flip_x when it does not, and standing still plays idle. So a sheet drawn in two, four or eight directions works with nothing configured. The names are yours — they are the tags in your file — and idle, walk and the direction suffixes are fields you can change. Without a sheet it only sets flip_x.

The mirroring assumes one thing about your art: what has no direction of its own faces right. flip_x is set while the object faces left, so a plain walk, idle and a sprite with no sheet must be drawn facing east to come out facing west. A tag with a direction suffix is drawn for that direction, so it plays unflipped: walk_w is your west-facing art, shown as you drew it.

Platformer

auto &hero = spawn({ .size = { 14, 22 } });
hero.add<rmp::behavior::Platformer>({ .speed = 200, .jump = 650, .air_jumps = 1 });

Platformer runs left and right, falls, and jumps, reading move_left, move_right and ui_accept unless you name others. jump is the upward speed a jump starts with, gravity its own pull while in the air, and air_jumps = 1 is a double jump. It makes the object solid when it is added, and applies its own gravity instead of the scene's, so a jump reaches the same height whatever the scene's gravity is.

That is why adding it sets the object's gravity_scale to 0. A heavier character is its own field, get<rmp::behavior::Platformer>()->gravity = 3000; setting gravity_scale again afterwards does not replace the behavior's gravity but adds the scene's on top of it, and the character falls with both.

Two fields separate a platformer that feels right from one that does not, and players never name either — they only notice when they are missing. coyote_time keeps a jump available for a moment after walking off a ledge, and jump_buffer remembers a jump pressed just before landing and fires it on landing. grounded() says whether it was standing on something at its last update: a solid object, or a solid cell of the map, just under its feet, while not moving up.

Runner

auto &runner = spawn({ .size = { 20, 36 } });
runner.add<rmp::behavior::Runner>({ .speed = 300, .accelerate = 8, .duck_action = "duck" });

Runner runs forward on its own, faster and faster: speed grows by accelerate every second up to max_speed, and it jumps on ui_accept unless you name another action. distance() is how far it has run — in an endless runner that is both the score and the clock the difficulty hangs off. ducking() says whether duck_action is held, and that is all ducking does here: a smaller collider or another animation is the game's to set. The endless runner is one, with a Spawner measuring by its distance.

Ball

auto &ball = spawn({ .position = { 400, 225 }, .shape = rmp::circle(7) });
ball.add<rmp::behavior::Ball>({ .speed = 340 });
ball.apply_impulse({ 1, 0.35f });   // the serve, and it is the game's

Ball bounces off the edges of its bounds and off whatever it collides with, and keeps its pace: every frame its velocity is set back to speed in whatever direction it is going. That one rule is what makes the serve a single push — only its direction survives — and what makes velocity = {} a stable stop between points. Where it hits a paddle tilts the bounce, up to max_bounce_deg at the very end, which is half of why Pong feels like Pong. speed_up multiplies the speed on every bounce off something solid. It sets the object to bounce at its edges and to be not solid itself, so it never pushes a paddle out of the way. Pong and Breakout are both a Ball.

Projectile

auto &shot = spawn({ .position = muzzle, .size = { 4, 4 } });
shot.velocity = aim;
shot.add<rmp::behavior::Projectile>({ .speed = 600 });

Projectile travels the way it was pushed, at speed — or at whatever velocity it was given, when speed is 0 — and is destroyed when it leaves its bounds and, with destroy_on_hit, when it touches anything it collides with. Which things those are is its layers' business.

Follow

auto &bat = spawn({ .size = { 12, 8 } });
bat.add<rmp::behavior::Follow>({ .target = player_handle, .speed = 90, .stop_distance = 20 });

Follow chases a target at speed, and stops within stop_distance of it. The target is a handle and not a pointer because the thing being chased is exactly the thing most likely to die while being chased: when it is gone, the follower keeps its velocity, the way a homing missile whose target explodes keeps flying.

Tween

auto &lift = spawn({ .position = { 200, 300 }, .size = { 64, 12 } });
lift.add<rmp::behavior::Tween>({
    .property = rmp::behavior::Property::POSITION_X,
    .from = 200,
    .to = 500,
    .seconds = 3,
    .ping_pong = true,
});

Tween moves one property of its object from from to to over seconds, along an Ease: LINEAR, or IN, OUT and IN_OUT, the default, which start slow, end slow, or both. The Property is the x or y of the position, the x or y of the scale, the rotation in degrees, or the alpha of the shape's colour and the sprite's tint, from 0 to 255. loop starts again from from, ping_pong turns back at each end forever, and with neither it stops exactly on to — not a hair short of it, which on a platform is a gap — and finished() turns true. restart() runs it again.

A Tween writes its property every frame it runs, and an object carries one behavior of each type, so one object animates one property with it.

GridSnap

auto &piece = spawn({ .size = { 24, 24 } });
piece.add<rmp::behavior::GridSnap>({ .cell = { 24, 24 } });

GridSnap rounds the object's position to the nearest point of a grid of cell spacing, starting at offset, after everything else has moved it — so a puzzle piece never rests on half a pixel. A cell of 0 on one axis leaves that axis alone.

Parallax

auto &sky = spawn({ .layer = -10 });
sky.add<rmp::behavior::Parallax>({ .texture = "sky.png", .factor = 0.2f });

Parallax draws a background strip that repeats sideways with no seam and scrolls at its own rate as the camera moves. It loads the texture by name from resources/. factor 0 is pinned to the screen, like a far sky; 1 stands still in the world, like the ground; in between, the smaller the farther away it looks. speed adds a drift of its own, for clouds; y is where the top of the strip sits; tint colours it. The object it is on needs no shape of its own, and its layer puts the strip behind or in front of the rest.

Spawner

auto &source = spawn({ .position = { 900, 380 } });
source.add<rmp::behavior::Spawner>({
    .every_seconds = 1.5f,
    .jitter = 0.4f,
    .max_alive = 5,
    .on_spawn = [](rmp::Scene &scene, Vector2 at) {
        auto &rock = scene.spawn({ .position = at, .size = { 30, 30 }, .velocity = { -200, 0 } });
        rock.add<rmp::behavior::Lifespan>({ .seconds = 6 });
    },
});

Spawner calls on_spawn every every_seconds, or every every_distance units travelled, handing it the scene and the position the distance is measured at. Distance is not the same as time, and the difference is why this is not a timer: in an endless runner the speed climbs, so "every two seconds" spaces the obstacles further and further apart and the game gets easier the faster it goes. The distance is measured on the object track names, or on the spawner itself.

jitter moves each interval after the first by a random amount up to that much either way, drawn from rmp::random. Intervals are counted from when the last one was due, not from the frame it fired on, so they do not drift. max_alive caps how many of the objects it made are alive at once — everything on_spawn spawns counts — and alive() says how many that is now. It is a cap and not a quota: when one dies, another can be made. One spawner keeps track of at most rmp::behavior::MAX_SPAWNED objects, and a larger max_alive is reported once and held to that.

Timer

auto &cannon = spawn({ .position = { 100, 100 }, .size = { 20, 20 } });
cannon.add<rmp::behavior::Timer>({
    .seconds = 0.8f,
    .on_timeout = [](rmp::Object &self) { self.rotation += 45; },
});

Timer calls on_timeout every seconds, with the object it is on; with repeat = false it calls once and is spent. A frame longer than the interval calls it once for each interval the frame covered, so a countdown keeps time on a slow machine.

Lifespan

auto &spark = spawn({ .size = { 3, 3 } });
spark.add<rmp::behavior::Lifespan>({ .seconds = 0.5f });

Lifespan destroys its object after seconds: particles, bullets, a message that fades.

Health

auto &hero = spawn({ .size = { 26, 26 } });
hero.add<rmp::behavior::Health>({
    .hp = 5,
    .invulnerable_for = 0.8f,
    .destroy_on_death = false,
    .on_death = [](rmp::Object &) { TraceLog(LOG_INFO, "game over"); },
    .hurt_by = layer::ENEMY,
});

Health is hit points, a window of invulnerability after each hit, and death. damage() takes points off and returns whether it landed — during the window it does not, which is what stops one spike costing three hearts in three frames — and the object blinks blink_hz times a second while the window is open. on_damage is told how much landed; on_death is called once when the points run out, even if two lethal hits land in the same frame, and then the object is destroyed unless destroy_on_death is off. heal() adds points up to max_hp, which is the starting hp unless set, and does nothing after death.

Nothing hurts by default: hurt_by names the collision layers whose touch costs damage_on_hit points, so contact damage is one field instead of an if at the top of every _collision(). A Health with nothing in hurt_by is a counter that only damage() reduces. The top-down game gives its player a TopDown and a Health hurt by the enemies.

Writing your own

A behavior of your own is the same struct as the ones above. Write its configuration as fields with defaults, in the order they will be written in the braces; give it _update, or _late_update when it corrects where the object ended up; add only the hooks it needs; and keep what it remembers in ours. A callback field is an rmp::Callback, so a lambda can go straight into the braces:

#include <cmath>

// Bobs in place until something on one of the `by` layers touches it, then
// tells on_pick who took it and goes away.
struct Pickup {
    unsigned by = 1;                                     // the collision layers that collect it
    rmp::Callback<rmp::Object &, rmp::Object &> on_pick;  // the pickup, and who took it

    void _ready(rmp::Object &self) { ours.rest_y = self.position.y; }

    void _update(rmp::Object &self, float delta) {
        ours.clock += delta;
        self.position.y = ours.rest_y + std::sin(ours.clock * 3) * 2;
    }

    void _collision(rmp::Object &self, rmp::Object &other) {
        if ((other.collision_layer & by) == 0) return;
        on_pick(self, other);
        self.destroy();
    }

    struct {
        float clock = 0;
        float rest_y = 0;
    } ours;
};

namespace layer { constexpr unsigned PLAYER = 1u << 0; }

class Level : public rmp::Scene {
    int _coins = 0;

    void _ready() override {
        auto &coin = spawn({ .position = { 300, 200 }, .shape = rmp::circle(6) });
        coin.add<Pickup>({
            .by = layer::PLAYER,
            .on_pick = [this](rmp::Object &, rmp::Object &) { _coins++; },
        });
    }
};

A behavior is the right shape when the same few lines would otherwise be written into several kinds of object. When something belongs to one kind of object only, its own _update() is simpler.
