The rmp command

rmp is the one command a game needs. It builds the game, runs it, checks it, packs its assets, tags a release and makes new games. It is a single Python file, tools/rmp.py, standard library only, behind three small launchers so that the same word works in every shell.

Every command, with its examples, is in the commands reference, which is read from rmp help itself.

Getting it

Clone the framework once, into your home folder, and put that folder on your PATH:

cd ~
git clone https://github.com/omardev29/raylib_multiplatform
ShellAdd to PATH, once
bash on Linuxecho 'export PATH="$HOME/raylib_multiplatform:$PATH"' >> ~/.bashrc
bash on macOSecho 'export PATH="$HOME/raylib_multiplatform:$PATH"' >> ~/.bash_profile
zshecho 'export PATH="$HOME/raylib_multiplatform:$PATH"' >> ~/.zshrc
kshecho 'export PATH="$HOME/raylib_multiplatform:$PATH"' >> ~/.profile
PowerShell and cmd[Environment]::SetEnvironmentVariable("Path", "$HOME\raylib_multiplatform;" + [Environment]::GetEnvironmentVariable("Path", "User"), "User")

On Windows, PowerShell also has to be allowed to run a local script, once:

Set-ExecutionPolicy -Scope CurrentUser RemoteSigned

Then open a new terminal. Building a game also needs Python 3.11 or newer, CMake, Ninja and a C++ compiler on the PATH, and on Linux the X11 development libraries:

sudo apt install libx11-dev libxrandr-dev libxi-dev libxcursor-dev libxinerama-dev libgl1-mesa-dev

The launchers

The framework's root, and every game's, holds three files that do one thing each: find a Python 3.11 or newer and hand it tools/rmp.py with every argument you typed.

FileFor
rmpPOSIX sh, so it runs as /bin/sh on Linux, macOS and the BSDs and under bash, zsh and ksh. It follows a symbolic link to itself, so ln -s ~/raylib_multiplatform/rmp ~/bin/rmp works too.
rmp.ps1PowerShell, Windows PowerShell 5.1 included.
rmp.cmdcmd.exe.

Each one asks every Python it finds whether it is 3.11 or newer instead of trusting the name: macOS's own python3 is older than that, and on Windows python3 can be the Microsoft Store's placeholder, which exits without running anything. The sh launcher tries python3, then python3.14 down to python3.11, then python, then the py launcher that python.org installs on Windows; the PowerShell and cmd launchers try py -3, python3 and python. When none will do, the command says so and stops:

rmp: needs Python 3.11 or newer on PATH (python3, python or py).

Where it works

rmp works on the project it is standing in: the nearest folder, from the current one upwards, that holds a raylib_multiplatform.toml. So it works from any subfolder of a game. Outside a project, only rmp new and rmp help mean anything, and the others say so.

The project is either a game or the framework itself — the framework is the one that also holds its own test suite. rmp lint and rmp example are the framework's maintenance commands and are refused in a game.

A game keeps its own rmp

Inside a project, the rmp on your PATH does not run its own code: it runs that project's copy of tools/rmp.py. A game therefore keeps the rmp it was made with — its build, its checks, its release steps — when the framework on your PATH moves on. Games made months apart each behave the way they did when they were made.

rmp new is the exception, and by design: it uses the framework that ships the rmp being run, because a new game is made from the framework you have installed, not from the game you happen to be standing in.

One variable in the environment turns the hand-over off, so that the rmp on the PATH runs its own code on the project:

RMP_NO_DELEGATE=1 rmp test

Every day

rmp run               # build (debug) and play
rmp test              # the .toml, the pins, the licences, a frame drawn, a boot
rmp build release     # the release build
rmp web               # or: rmp android
rmp help              # every command; rmp help <command> explains one, with examples

rmp run and rmp build

rmp run builds the game in debug and starts it. Only what changed is compiled again, and only the game's own target is built, not anything else the build folder has configured. When the game exits, rmp exits with the game's code, so a crash is not reported as a success.

rmp build compiles without running and prints where the executable is. rmp build release is the build players get: optimised, with link-time optimisation, and reading its assets from ./resources/, relative to the folder it is started from, rather than from the project.

Debug and release share the build/ folder. Switching between them deletes it first and says so, because the compiler [dev] compiler chose for debug is cached there and would otherwise carry over into the release build — and since switching build type rebuilds everything anyway, nothing is lost.

rmp web and rmp android

rmp web builds the game for the browser with Emscripten, into build/web/. The emsdk has to be activated in the shell first, so that EMSDK is set; rmp refuses with that instruction when it is not. The page has to be served, not opened as a file:

rmp web
python3 -m http.server 8000 --directory build/web

and then localhost:8000/my_game.html in the browser, with the game's name in place of my_game. Web has the rest of the browser target.

rmp android regenerates the Android configuration from the .toml, builds a debug APK with Gradle — which needs the Android SDK and NDK — and prints every APK it finds, marking the one it has just written. adb install -r with that path puts it on a connected phone. Android has the rest.

rmp test

rmp test checks the game, stage by stage, and stops at the first that fails. rmp test smoke runs a single stage. In a game there are three, in this order:

StageWhat it does
configValidates raylib_multiplatform.toml the way every build does, checks that the pinned versions agree with each other, and checks every licence of everything vendored.
renderBuilds the game a second time against raylib's software renderer, which draws into memory with no GPU and no window, runs it for ten frames, and requires that it booted, drew something, honoured [window] vsync and exited cleanly.
smokeBuilds the game in debug, runs it for ten frames for real, and requires that it booted with no asset failing to load and put pixels on the screen.

These are the same checks CI runs on the targets it can start, which is why a game that passes rmp test rarely surprises anyone in CI. A failed smoke stage prints the game's own output and one of two reasons: the game did not boot, or an asset failed to load, or the game booted and drew nothing.

The config stage runs shell scripts, so on Windows it needs a bash; the one Git for Windows installs is the one rmp looks for.

rmp fmt

rmp fmt formats your C and C++ — everything under src/ and include/ except the framework's own folders and generated files — with clang-format, at the version the framework pins. rmp fmt check only reports what would change. A different clang-format version would reformat files that were already correct, so it is worth having the pinned one.

rmp pack and rmp unpack

rmp pack bundles resources/ into one encrypted resources.rres inside it, the way a release ships, so you can see the game run from the pack. From then on the game reads the pack. rmp unpack deletes it, and the game reads the loose files again — which is what you want while you are adding art.

rmp clean

rmp clean deletes build/ and every file generated from the .toml. The next build makes all of it again. It is the answer when a build goes strange. The app icons stay, because regenerating them needs Pillow.

rmp push and rmp deploy

rmp push is git push, refused while a CI run is still in flight: CI cancels the run in progress when a branch receives a new push, so pushing would throw away a run that was half done. It names the run instead, with the command to watch it. rmp push force pushes anyway. Without the gh command installed it cannot ask, says so, and pushes.

rmp deploy 1.2.0 releases a version. It adds the v, and refuses — before tagging anything — when there are uncommitted changes, when the tag already exists here or on the remote, when the branch has not been pushed, or when the commit you are on is not the one on the remote, since CI builds the tag from the remote. It then checks the .toml the way the release will, which refuses placeholder store ids and a version that is not MAJOR.MINOR.PATCH, and only then makes an annotated tag and pushes it. CI builds every enabled target and attaches them to the release. rmp deploy 1.2.0-rc1 is a pre-release.

rmp new and rmp help

rmp new my_game makes a game; rmp new --list prints what a game gets without making one. Project layout explains both.

rmp help lists the commands on one screen. rmp help test explains one, with examples — and for test, its stages. -h or --help after any command prints the same page. rmp help --json prints every command and stage for a tool to read; this site checks every rmp line it shows against it.

What it answers with

Exit codeMeans
0Done, or help printed.
1A check failed, or a precondition did not hold and the command refused.
2The command line was wrong: an unknown command, a wrong argument, a framework command in a game, or no project here.
130Interrupted.

A misspelt command gets the nearest real one suggested back. A command that ran something external, such as CMake, and saw it fail, names what failed and its exit code.

Without rmp

Nothing in a game requires rmp: underneath, it is plain CMake with presets, and the .toml is applied by the configure step itself.

cmake --preset debug           # configures AND generates everything from the .toml
cmake --build build
./build/my_game

The presets a game builds with are debug, release, web and memory, the software-rendered build the render stage uses. debug and release share build/, and configuring a release where a debug configure has pinned the [dev] compiler is refused, with the instruction to run rmp clean first — the same reason rmp build release deletes the folder for you.
