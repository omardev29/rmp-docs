Platforms

One codebase builds for {{count:targets}} targets: {{list:targets}}. A game chooses which of them it ships in one place, [targets] in raylib_multiplatform.toml, and everything downstream — the build files, CI, the release — follows that choice.

The code of a game does not change from one target to another. What changes is how the game is built, packaged and run, and the pages in this section are about those differences:

  • Desktop — Windows, macOS, Linux (glibc, musl, DRM/KMS, RISC-V) and the BSDs.
  • Web — Emscripten, a browser that owns the frame loop, memory, saves and sound.
  • Android — raymob, Gradle generated from the .toml, permissions, signing.
  • iOS — Xcode through XcodeGen, the raylib-iOS fork, and an app that is not allowed to quit.

Every target

A target's name is <os>-<arch>-<libc>-<env>, and each part is only there when it can differ. linux-x64-glibc and linux-x64-musl name their C library because a glibc binary does not start on Alpine and a musl binary does not start on Debian; windows-x64 stops after the architecture because Windows has one C library; macos stops at the operating system because its binary carries both architectures. The last part, the environment, is the windowing system, and it is only written when the binary is limited to one: linux-x64-glibc-drm draws through DRM/KMS, with no X11 and no Wayland.

Families

Each target belongs to one of {{count:families}} families, and the family is which part of CI builds it: linux, windows, apple, web, android and bsd. CI skips a whole family when none of its targets are enabled, so a game that ships only to desktops never starts an Android build.

Choosing a game's targets

[targets] has two lists. enabled names targets and groups; disabled is subtracted from whatever enabled came to. Groups expand and duplicates fold together, so there is no order to think about and nothing to conflict:

[targets]
enabled = ["all"]
disabled = ["ios"]

That is everything but iOS. The same lists take exact target names, and mix them with groups:

[targets]
enabled = ["desktop", "web", "linux-x64-musl"]
disabled = ["windows-arm64"]

The groups:

GroupHolds
allEvery target.
desktopLinux glibc on x86-64, ARM64 and RISC-V; Windows on x86-64 and ARM64; macOS. Not musl, not the DRM targets and not the BSDs.
linuxEvery Linux target: the glibc ones, musl and the DRM ones.
windowsWindows on x86-64 and ARM64.
applemacOS and iOS.
mobileAndroid and iOS.
bsdFreeBSD, OpenBSD and NetBSD, on every architecture built for them.
drmThe Linux DRM/KMS targets.
web, androidThe one target each.

The table above says which groups each target is in. A name that is neither a target nor a group is refused, and so is a pair of lists that leaves nothing to build. So is the most natural typo of all — a group name without the brackets of a list:

[targets]
enabled = "all"

Turning a target off removes it from the build, from CI and from the release. Other settings follow it: [android.admob] switches itself off when Android is not a target, and a non-empty [raylib] disabled_modules warns when iOS is one, because iOS links a prebuilt raylib that it cannot reach.

What CI does with each target

CI runs in two lanes. A push or a pull request gets the fast lane: the targets that catch most mistakes, in about ten minutes. A tag — a release — gets the full lane: every target the game has enabled, and then the release itself. The full lane can also be started by hand, for every target or for one group:

gh workflow run ci.yml -f full=true        # every enabled target
gh workflow run ci.yml -f targets=drm      # one group or target; implies the full lane

Building is not the bar. Wherever there is a machine to run on, the game is started with a frame budget, it must report that it booted with no asset missing, a frame is read back and must have something drawn on it, and the process must exit cleanly when the budget is spent.

TargetLaneWhat CI checks
linux-x64-glibcevery pushBuilt; checked against the [linux] glibc floor; resources packed; booted under a virtual X server, with a frame read back.
webevery pushBuilt; booted in headless Chromium, the canvas measured for pixels, and a save written to IndexedDB and read back.
windows-x64every pushBuilt with the runner's MinGW GCC; its imports checked to be all part of Windows 10; booted on the Windows runner with the compiler off PATH and a software OpenGL placed next to the executable, a frame read back, and a save made in a user folder whose name is not ASCII.
androidevery pushA debug APK built and checked; a release AAB built, signed and its signature verified. Not run, except by the optional Firebase Test Lab job on a release.
linux-arm64-glibcfullBuilt on an ARM64 runner, checked against the glibc floor, booted under a virtual X server.
linux-x64-muslfullBuilt; checked to be a musl binary with no glibc symbol; a software-rendered build of it booted inside Alpine with nothing installed.
linux-riscv64-glibcfullCross-compiled and checked to be a RISC-V executable. Never run: there is no RISC-V runner.
linux-x64-glibc-drmfullBuilt; checked to link libdrm and no X11 or Wayland; booted on a virtual display the kernel provides.
linux-arm64-glibc-drmfullBuilt and checked the same way. Not run: what it is for is a Raspberry Pi's own display pipeline, which a virtual display does not resemble.
windows-arm64fullCross-compiled with MSVC and checked to be an ARM64 executable whose imports are all part of Windows 10. Never run.
macosfullBuilt as one binary with both architectures, and checked for both and for the oldest macOS each asks for; a software-rendered build booted.
iosfullraylib built for iOS, the Xcode project generated, a simulator app built and its bundle checked. Booted in the simulator only when the repository variable IOS_SIMULATOR_TEST is true.
the BSDsfullBuilt in a virtual machine of each system; checked to be an executable; resources packed; a software-rendered build booted inside the machine.

Every push also runs the checks that need no target: the .toml, the pinned versions, the licences, and one frame of the game drawn by raylib's software renderer — most of what rmp test runs on your machine.

A push to a branch cancels a CI run already going on that branch, so a second push can kill a long full-lane run halfway. rmp push refuses while a run is in flight and names it; rmp push force pushes anyway.

What becomes of the builds — the release, its archives, the stores — is the subject of Publishing.
