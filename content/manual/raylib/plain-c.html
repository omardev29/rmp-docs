Plain C

The framework has two halves, and the second can go without the first. One is the runtime layer — rmp::, scenes, the interface, the asset pack. The other is everything around your code: the build for each target, the icons and identifiers generated from raylib_multiplatform.toml, the pinned toolchains, CI and the release. A game in plain C, with its own main() and nothing but <raylib.h>, keeps the second half and gives up the first.

The example

examples/plain_c is that game: one C file, one include, a while loop of its own. Its header is the instructions and the list of what changes:




Careful
The first step in that
header deletes src/rmp/, and at the framework's current source that stops the desktop
build. CMakeLists.txt builds the framework's library from src/rmp/ whether
or not the game links it, and with the folder gone CMake refuses to configure, saying there are no
sources for the target rmp. Delete src/main.cpp and
src/scenes/, and keep src/rmp/: a game whose src/ holds no
.cpp file outside it is linked against raylib alone, and the library is built and left
unused.



How the build tells



Nothing in the configuration says "this is a C game". The build looks: when the game's
src/ has no .cpp file — src/rmp/ aside — the game is compiled
as C99 and linked against raylib and nothing else; no entry point of ours is compiled in, and no
library of ours is linked. Put one .cpp file back and it is a framework game again,
with the framework's entry point and library.



Both values the build defines for every game are still there:
RMP_RESOURCES_PATH, with the folder the loose files are read from, and RMP_PRODUCTION_BUILD,
0 or 1. So is everything raylib_multiplatform.toml sets,
through the one header of ours that is plain #defines and works in C:



int main(void) {
    InitWindow(RMP_WINDOW_WIDTH, RMP_WINDOW_HEIGHT, RMP_WINDOW_TITLE);
    while (!WindowShouldClose()) {
        BeginDrawing();
        ClearBackground(RAYWHITE);
        DrawText(RMP_PROJECT_NAME, 20, 20, 20, DARKGRAY);
        EndDrawing();
    }
    CloseWindow();
    return 0;
}




A file that includes rmp/config.h has the window's size and title from the
.toml, so renaming the game is still one line in one file.

What you give up





Given upWhat it means



Everything under rmp::Scenes, objects and behaviors, the interface, named input, audio by name, saves, random, ads. Your code is raylib's API and your own.


The entry pointYour main() owns the loop, which is exactly what the web and iOS do not allow (below). No [app] max_delta clamp on GetFrameTime(), and no rmp::app::quit(): the loop ends when your condition says so.


The asset packReading resources.rres is the framework's runtime, and raylib alone cannot. A plain C game reads loose files only — and see the release packages, which assume otherwise.


The boot and render gates, until you call themSee the smoke test.






Which targets run it



The file's own header says it, and the reason is the while loop: it assumes your
code owns the frame loop, and on the web and iOS it does not.





TargetThe file as it stands



Windows, Linux, macOS, the BSDsRuns.


AndroidRuns, by the file's own account: raylib's Android glue calls main(). The Android build compiles every .c and .cpp under src/ into the game's library — src/rmp/ with it, when it is there.


WebDoes not. The browser owns the loop and calls the game back once per frame; a while loop there needs -s ASYNCIFY, which this build deliberately does not have.


iOSDoes not. UIKit never calls main(): raylib's iOS backend calls three functions instead, and they are what the framework's entry point exists to provide.






A plain C game should say so in its configuration, so CI does not build the web and iOS, which it cannot
run:



[targets]
enabled = ["all"]
disabled = ["web", "ios"]




To have the web or iOS back, keep the framework's entry point: one include and one line of C++,
RMP_ENTRY_POINT with three functions of yours, which
writes the right loop for every target and costs nothing else. Or write those two runners
yourself.



The smoke test



CI does not take a build's word for it. It starts the game with RAY_TEST_MAX_FRAMES
set, and requires three log lines: RAY_TEST_BOOT_OK with no failed asset,
RAY_TEST_RENDER_OK for a frame read back with something on it, and
RAY_TEST_DONE_FRAMES for a clean exit when the budget is spent. rmp test
render and rmp test smoke ask for the same.



The example prints the first line by hand and nothing else, and its loop does not look at the
frame budget: started that way, it runs until something kills it. A plain C game that has to pass
the gates calls the hooks the framework's entry point calls, from the header-only
tests/smoke_test.h, which is written to compile as C:



int main(void) {
    SetConfigFlags(FLAG_WINDOW_RESIZABLE | (RMP_WINDOW_VSYNC ? FLAG_VSYNC_HINT : 0));
    InitWindow(RMP_WINDOW_WIDTH, RMP_WINDOW_HEIGHT, RMP_WINDOW_TITLE);
    SmokeTest_Begin(); /* reads RAY_TEST_MAX_FRAMES; does nothing outside a test */

    Texture2D rabbit = LoadTexture(RMP_RESOURCES_PATH "rabbit.png");
    SmokeTest_ReportBoot(rabbit.id == 0 ? 1 : 0, 1); /* failed, requested */

    while (!WindowShouldClose() && !SmokeTest_Done()) {
        BeginDrawing();
        ClearBackground(RAYWHITE);
        DrawTexture(rabbit, GetScreenWidth() / 2 - rabbit.width / 2,
                    GetScreenHeight() / 2 - rabbit.height / 2, WHITE);
        SmokeTest_CaptureFrame(); /* after the last draw, before EndDrawing() */
        EndDrawing();
        SmokeTest_Tick();
    }

    UnloadTexture(rabbit);
    CloseWindow();
    return 0;
}




Built from a game made with rmp new, that file passes the software render check
that rmp test render runs. Three details in it are there because a gate checks them:



    

  • The include is by relative path. A plain C game's include path is its own
include/ and raylib's, and tests/ is on neither, so
<smoke_test.h> is not found; "../tests/smoke_test.h" is, from
src/.
    • 

  • The vsync flag follows the .toml. The boot line reports whether the
window asked for vsync, and the render check compares that with [window] vsync.
    • 

  • The asset count is yours to say. The framework counts the loads made through
rmp::assets; with raylib's loaders the game reports its own, and
assets_failed must be 0.
    • 




The release packages



CI packs resources/ into resources.rres for the Linux x64 and ARM64
targets — the glibc ones and the DRM ones — for Windows x64, macOS and the BSDs, and those packages
ship the pack and not the loose files. A plain C game cannot read the pack, so on those targets a
release made by CI as it stands has no assets it can open. The package steps live in the workflow
files under .github/workflows/; for a plain C game, they have to ship the
resources/ folder instead of the pack. The other targets already ship loose files: the
web and Android copy the folder, and Linux RISC-V, Linux musl and Windows ARM64, whose packer cannot
run on the machine that builds them, ship it with a note saying so.
