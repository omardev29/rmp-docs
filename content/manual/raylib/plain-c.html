Plain C

The framework has two halves, and the second can go without the first. One is the runtime layer — rmp::, scenes, the interface, the asset pack. The other is everything around your code: the build for each target, the icons and identifiers generated from raylib_multiplatform.toml, the pinned toolchains, CI and the release. A game in plain C, with its own main() and raylib, keeps the second half and gives up the first.

The example

examples/plain_c is that game: one C file, raylib, the framework's headers that are plain C — <rmp/config.h> and <smoke_test.h> — and a while loop of its own. Its header is the recipe and the list of what changes:




The recipe, from the folder of a game made with rmp new:



rm src/main.cpp && rm -r src/rmp/ src/scenes/
cp <the framework>/examples/plain_c/src/main.c src/
rmp run




The
framework's CI follows it on every commit, in a copy of a game freshly made with
rmp new: it reads the first line out of the example and runs it, copies the file in as
the second line says, and then, in place of rmp run, runs that game's render check —
rmp test render — which has to build it, boot it with its one asset loaded, see a frame
drawn and see it exit cleanly. The examples job boots the example itself like every other one.



How the build tells



Nothing in the
configuration says "this is a C game". The build looks: when the game's src/ has no
.cpp file outside src/rmp/, the game is compiled as C99 and linked against
raylib and nothing else — no entry point of ours, no library of ours. With src/rmp/
gone, CMake builds no framework library at all, and its configure says
=== NO src/rmp/: no framework library, a plain C game ===.



The recipe deletes src/rmp/ rather than leaving it unused, because two other parts
of the pipeline look at the folder itself. Android's build compiles every .c and
.cpp under src/ into the game's library, src/rmp/ with it when
it is there. And a release decides by it what to ship in resources/: the pack while the
folder is there, the loose files once it is gone (below).



Put a .cpp file back without src/rmp/ and the configure stops, naming
the problem: … has C++ sources and there is no src/rmp/, so no framework to link …. A
C++ game keeps src/rmp/, and with it the framework's entry point and library.



Both values the build defines for every game are still there: RMP_RESOURCES_PATH, the folder the
files are read from — an absolute path to resources/ in a debug build,
./resources/ in a release, and empty on Android, where the files sit at the root of the
APK's assets — and RMP_PRODUCTION_BUILD, 0 or 1.
So is everything raylib_multiplatform.toml sets, through rmp/config.h, the
one header of ours that is nothing but #defines. A plain C game's include path is
raylib's, the game's include/, where rmp/config.h is, and
tests/, where smoke_test.h is:



int main(void) {
    InitWindow(RMP_WINDOW_WIDTH, RMP_WINDOW_HEIGHT, RMP_WINDOW_TITLE);
    while (!WindowShouldClose()) {
        BeginDrawing();
        ClearBackground(RAYWHITE);
        DrawText(RMP_PROJECT_NAME, 20, 20, 20, DARKGRAY);
        EndDrawing();
    }
    CloseWindow();
    return 0;
}




Renaming the game, or resizing its window, is still one line in one file.

What you give up





Given upWhat it means



Everything under rmp::Scenes, objects and behaviors, the interface, named input, audio by name, saves, random, ads. Your code is raylib's API and your own.


The entry pointYour main() owns the loop, which is exactly what the web and iOS do not allow (below). No [app] max_delta clamp on GetFrameTime(), and no rmp::app::quit(): the loop ends when your condition says so. Escape stays raylib's exit key and closes the window, unless your code calls SetExitKey(KEY_NULL).


Starting a release from anywhereThe framework's entry point moves a desktop release into the executable's folder, so that ./resources/ is the one next to it. In plain C that is yours, and the example does it in a release with ChangeDirectory(GetApplicationDirectory()).


The asset packReading resources.rres is the framework's runtime, and raylib alone cannot. A plain C game reads loose files only, and its release ships them — see the release packages.


The boot and render reportsThe entry point prints what CI looks for; a plain C game calls the same hooks itself. See the smoke test.






Which targets run it



The file's own header says it, and the reason is the while loop: it assumes your
code owns the frame loop, and on the web and iOS it does not.





TargetThe file as it stands



Windows, Linux, macOS, the BSDsRuns.


AndroidRuns, by the file's own account: raylib's Android glue calls main().


WebDoes not. The browser owns the loop and calls the game back once per frame; a while loop there needs -s ASYNCIFY, which this build deliberately does not have.


iOSDoes not. UIKit never calls main(): raylib's iOS backend calls three functions instead, and they are what the framework's entry point exists to provide.






A plain C game should say so in its configuration, so CI does not build the web and iOS, which it cannot
run:



[targets]
enabled = ["all"]
disabled = ["web", "ios"]




To have the web or iOS back, keep the framework's entry point:
RMP_ENTRY_POINT with three functions of yours, which
writes the right loop for every target. It is C++, and that brings the rest of the framework back
with it: a .cpp file in src/ needs src/rmp/, the framework's
library is built and linked again, and a release ships the pack instead of the loose files — which
raylib's own loaders then read through the framework. Or write those two runners yourself.



The smoke test



CI does not take a build's word for it. It starts the game with RAY_TEST_MAX_FRAMES
set, and requires three log lines: RAY_TEST_BOOT_OK with
assets_failed=0, RAY_TEST_RENDER_OK for a frame read back with something
on it, and RAY_TEST_DONE_FRAMES for a clean exit when the budget is spent.
rmp test render asks for the same three. rmp test smoke asks for the
first two only: it does not look for RAY_TEST_DONE_FRAMES.



The
framework's entry point calls the hooks that print them. A plain C game calls them itself, from
<smoke_test.h>, which is written to compile as C. Every hook but one does nothing
unless RAY_TEST_MAX_FRAMES is set; SmokeTest_ReportBoot prints its line on
every run. The example shows where each one goes:



    

  • SmokeTest_Begin once, first: it reads the frame budget.
    • 

  • SmokeTest_ReportBoot, with how many assets failed and how many
were asked for, once the window is open and the assets are loaded. The framework counts the loads
made through rmp::assets; with raylib's loaders the game counts its own, and the failed
count must be 0. The line also says whether the window asked for vsync, and the render check
compares that with [window] vsync — which is why the example passes
FLAG_VSYNC_HINT only when RMP_WINDOW_VSYNC says so.
    • 

  • SmokeTest_CaptureFrame after the last draw call and before
EndDrawing(): the frame it reads back is the one about to be shown.
    • 

  • SmokeTest_Tick after EndDrawing(), and
SmokeTest_Done in the loop's condition, so that the budget ends the
loop the way the window's close button does.
    • 




The release packages



What goes in a release
archive's resources/ is decided by one script, tools/ship_resources.sh,
which the packaging steps of the targets that pack call — the Linux glibc and DRM ones, macOS and
the BSDs — and which the windows-x64 job repeats in PowerShell. While
src/rmp/ is there it ships resources.rres alone, which the framework reads.
Without it, it ships the loose files of resources/, the pack left out, and a
PACK_SKIPPED.txt saying that this game is plain C and raw raylib cannot read the pack.
Android copies the folder into the APK whatever the game is, and the targets whose packer cannot run on
the machine that builds them — Linux RISC-V, Linux musl and Windows ARM64 — ship loose files with a
note of their own.
