Assets

A game's pictures, sounds, fonts and levels live in one folder, resources/, and are loaded by their file name. What comes back is a handle that knows how many copies of it exist and frees what it loaded when the last one goes. The same call reads the loose files while you work and a single packed, encrypted file in a release, and the game never has to know which.

Loading by name

Everything in rmp::assets takes the name of a file in resources/, not a path. A scene loads what it needs in _ready(), keeps the handle as a member, and hands it to raylib wherever raylib wants the picture:

class TitleScene : public rmp::Scene {
    rmp::Texture _logo;

    void _ready() override { _logo = rmp::assets::load_texture("logo.png"); }
    void _draw() override { DrawTexture(_logo, 40, 40, WHITE); }
};

There is nothing to unload. When the scene ends, _logo goes with it, and with it the texture — unless something else still holds the same one.

One loader per kind of thing, each returning its own handle:

CallReturnsFor
load_texture(name)rmp::TextureA picture on the GPU, to draw.
load_image(name)rmp::ImageA picture in memory, to read pixels from or make a texture out of.
load_font(name, size)rmp::FontA .ttf or .otf, baked at one size.
load_sound(name)rmp::SoundA short sound, decoded into memory. Most games play sounds by name with rmp::audio instead.
load_sheet(name)rmp::SpriteSheetAn Aseprite file, with its frames and tags. See Sprites.
load_map(name)rmp::TilemapA level made in LDtk or Tiled. See Tilemaps.

rmp::Image mask = rmp::assets::load_image("mask.png");
rmp::Font title = rmp::assets::load_font("title.ttf", 48);
rmp::Sound jump = rmp::assets::load_sound("jump.wav");
rmp::SpriteSheet hero = rmp::assets::load_sheet("hero.aseprite");
std::vector<unsigned char> dialogue = rmp::assets::load_data("dialogue.json");

A name is a file name

The name is the file's name inside resources/ — "jump.wav", never "resources/jump.wav" and never an absolute path. The folder where those names are looked up is set by the build, so the same name works however the game was started.

Keep every file directly in resources/. The pack described below stores files by their bare name and does not look into subfolders, so a file in a subfolder loads while you develop and is missing from the release that ships the pack. A release configure that finds a subfolder in resources/ warns about it for that reason.

The fonts are baked at a size

A font is turned into a texture of glyphs at the size you ask for, and the size is part of what identifies it: load_font("ui.ttf", 16) and load_font("ui.ttf", 32) are two fonts, two textures. Ask for the size you draw at.

The handles

rmp::Texture, rmp::Image, rmp::Font, rmp::Sound and rmp::SpriteSheet are the same thing for different raylib types: a counted reference to one loaded resource. Each converts to the raylib struct it wraps, so every raylib function that takes a Texture2D takes an rmp::Texture.

Copies share

Loading a name that is already loaded does not load it again. The name is the key, and the second load hands back the resource the first one made, with one more reference to it. A copy of a handle is one more reference too:

rmp::Texture a = rmp::assets::load_texture("enemy.png");
rmp::Texture b = rmp::assets::load_texture("enemy.png"); // the same texture, loaded once
rmp::Texture c = a;                                      // and one more reference to it

That is what lets a hundred enemies each hold their picture without anyone deciding who owns it: each holds a handle, the texture is on the GPU once, and it goes when the last enemy does. A move takes the reference over and leaves the moved-from handle empty.

When they free

A resource is unloaded when the last handle to it goes out of scope — a scene ending, an object being destroyed, a member being assigned something else. Whatever is still held when the game ends is released by the framework before the window closes, because a texture freed after the GPU context is gone is a crash. A handle that outlives that, such as a static one, is simply empty from then on.

Since a handle is the owner, there is one mistake the types refuse: keeping the raylib struct and letting the handle go.

Texture2D player = rmp::assets::load_texture("player.png");

If that compiled, the handle would be a temporary that died at the end of the line, taking the texture with it, and player would be a texture that had already been unloaded. Only a handle that is still alive converts; keep the rmp::Texture and pass it to raylib where raylib wants the picture.

Loading in _ready() and keeping the handle is the shape to use. Loading in _draw() every frame is a search of the loaded resources every frame, and if no other handle holds the resource it is loaded and freed again each time.

Handles that are empty

A handle can hold nothing: one that was never assigned, one that was moved from, and one whose load failed. valid() says which, and so does the handle in an if:

rmp::Texture logo = rmp::assets::load_texture("logo.png");
if (!logo) TraceLog(LOG_WARNING, "no logo: the title is drawn as text");

An empty handle converts to a zeroed raylib struct, and raylib draws nothing for one of those. A missing picture is a hole in the frame, not a crash.

What is not a handle

The handles come from the loaders. A texture you make yourself with raylib — LoadTextureFromImage(), LoadRenderTexture(), a model from LoadModel() — is a plain raylib struct, under raylib's own rule: what you load, you unload. The types rmp::Music, rmp::Shader and rmp::RenderTexture exist, but nothing in rmp::assets returns one; music is played by name through rmp::audio.

An rmp::Image is read through its handle and not changed: the image belongs to every handle that loaded the same name. Making a texture from it is the usual use.

Any other file: load_data

A level in your own format, a shader's source, a JSON table of items: load_data() returns the bytes, as a vector that frees itself. It is not cached, so each call reads the file again, and it is empty when the file is not there.

const std::vector<unsigned char> bytes = rmp::assets::load_data("intro.txt");
const std::string intro(bytes.begin(), bytes.end());

It reads from the pack in a release exactly as the other loaders do. The Aseprite and map loaders are built on it.

Plain raylib works too

The rmp::assets functions are the short way, not the only one. When a pack is in use, raylib's own file loading is routed through it, so a raylib loader given a path inside resources/ finds the packed copy:

Model ship = LoadModel(RMP_RESOURCES_PATH "ship.obj"); // in a release, read from the pack
// ... and raylib's rule for what raylib loads:
UnloadModel(ship);

That covers models and the files they pull in behind your back — an .obj's .mtl and the textures it names — as well as shaders, fonts and textures loaded through raylib directly. The path has to start with the macro the build defines for the folder, RMP_RESOURCES_PATH: only files inside it are answered from the pack, so a save file elsewhere on disk that happens to share a name with a packed one is never mistaken for it.

The exception

raylib's LoadMusicStream() opens the file itself and never sees the pack, so a song loaded that way exists only as a loose file. rmp::audio::music("song") reads it through the pack like everything else.

Where resources/ is

The build tells the game where its folder is. A debug build reads the absolute path of the project's resources/, so the game finds its files whichever folder it is started from. A release build (rmp build release) reads ./resources/, which is where the released archive puts the folder, beside the executable: start a release from the folder it is in.

An example with a resources/ of its own reads that one and not the game's; one without reads the game's.

The pack

A release does not have to ship a folder of loose files. rmp pack bundles every file directly in resources/ into one file, resources.rres, inside that same folder, encrypted. The container format is rres, by raylib's author, and the packer is part of the framework, so nothing has to be installed or bought.

rmp pack      # resources/ into resources/resources.rres
rmp run       # the game now reads the pack
rmp unpack    # delete the pack: the game reads the loose files again

At startup the framework looks for resources.rres in the game's resources folder. If it is there, every load asks the pack first; if not, the loose files are read. The log says which:

  • ASSETS: Using resource pack … (… entries)
  • ASSETS: No resource pack found, using loose files from …

rmp::assets::using_pack() answers the same question in code. There is no call to make for any of it: the entry point calls rmp::assets::init() before the first scene, which finds the pack, and rmp::assets::shutdown() after the last.

The loose files are the fallback

A name the pack does not have — a picture you added after packing — is read from the loose files instead, with a warning such as ASSETS: '…' not found in pack, falling back to loose file. In development that means you can keep working after rmp pack without packing again. In a release that ships only the pack there is no loose file to fall back to, and the load fails, which is what the warning is there to tell you before a player does.

Which releases ship it

The release jobs build the pack where the packer can run on the machine that builds the game:

ReleaseWhat its resources/ holds
Linux on glibc (x64, arm64, and both DRM builds), Windows x64, macOS, FreeBSD, OpenBSD, NetBSDresources.rres alone.
linux-x64-musl, linux-riscv64-glibc, windows-arm64The loose files, and a PACK_SKIPPED.txt saying why: these are cross-compiled, and the packer they build cannot run on the machine that builds them.
Web, iOSThe loose files: the folder is preloaded into the page, or copied into the app.
AndroidThe loose files, copied into the APK's assets. A resources.rres is left out of the APK, because the pack cannot be opened from inside one.

The game does not care: a folder with a pack is read through the pack, and one without is read file by file.

The password

The pack is encrypted with AES, under a key derived from one password, which is set in the .toml and reaches both the packer and the game from there:

[resources]
rres_password = "a phrase of your own"

An empty password is refused, because it would ship a pack encrypted with a key of nothing rather than one with no encryption:

[resources]
rres_password = ""

Each file read from the pack derives its key again (Argon2i, 16 MiB, three passes). That is a cost paid when something loads, never while the game runs.

What the encryption is for

It stops someone opening your game's folder and copying the art out of it. It does not stop someone determined: the password is inside the executable you give them, the names of the files in the pack are stored in the clear, and on the releases that ship loose files there is no encryption at all. It is a lock on the door, not a safe.

rmp new writes a random password into the new game's .toml, so each game has one of its own. Leave the key out and the framework's default applies, which is the same for everyone.

When a load fails

A load that finds nothing returns an empty handle, and the game keeps running. A missing texture is a gap on the screen; a missing font, sound or sheet is empty in the same way. Nothing throws: the framework has no exceptions anywhere.

The failure is still counted. requested_loads() is how many loads the game asked for, and failed_loads() how many of them failed, which means:

  • a name that is neither in the pack nor in the folder;
  • an .aseprite file that cannot be read as one;
  • a map file that does not parse, or a Tiled map whose tileset file cannot be read.

A file that is there and does not decode — a broken PNG, say — is an empty handle and a line from raylib in the log, and is not in the count.

How CI notices

When the game boots under the smoke test, the framework prints one line once the first scene is ready:

RAY_TEST_BOOT_OK assets_failed=0 …

rmp test smoke on your machine requires assets_failed=0, and so do the CI boots of the Linux x64 and arm64 builds and of Windows x64, and the boot of every example: a game that asks for a file it does not ship fails the build instead of reaching a player as a blank sprite. The other boots in CI check that the game started and drew, not this count.

The count covers what is loaded by the time the first scene's _ready() has run. A file loaded later, by a level the boot never reaches, is outside it.
