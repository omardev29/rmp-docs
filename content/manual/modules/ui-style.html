Interface style

No button, line of text or control in rmp::ui takes a colour. A control says what it means — primary, danger, a muted line of text — and how important it is — small, medium, large — and the theme decides what that looks like. Restyling a game is then one theme, and no call site is revisited. The few colours a call can be given belong to boxes and pictures — a panel's background and border, a progress bar's fill and track, an image's tint — and a panel or a bar left without one takes the theme's.

rmp::ui::button("Start game", { .style = rmp::ui::Variant::PRIMARY, .size = rmp::ui::Size::LARGE });
rmp::ui::text("v1.0.2", { .color = rmp::ui::ColorRole::MUTED, .size = rmp::ui::Size::SMALL });

Themes

A rmp::ui::Theme is plain data: every colour the widgets are drawn with, as raylib's Color, and every metric, in design units. There is no inheritance, no cascade and no stylesheet. Customising one is assignment — copy it, change what you want, set it back:

rmp::ui::Theme theme = rmp::ui::current_theme();
theme.primary = GOLD;
theme.primary_hover = YELLOW;
theme.primary_press = ORANGE;
theme.corner_radius = 0; // square corners
rmp::ui::set_theme(theme);

current_theme() returns the one theme in use, and set_theme() copies a new one over it. Anything drawn after the call uses the new one, in the same frame. Both work at any time, before the window exists too.

Two themes come with the framework, theme_dark() and theme_light(). Each returns a copy, so the same copy-modify-set works on top of either. Which one the game starts with is [ui] theme:

[ui]
theme = "light"

Only those two names exist, and a typo is refused when the configuration is read instead of falling back to dark at runtime:

[ui]
theme = "blue"

After that it is a runtime call, so an appearance setting in the game is one line:

if (rmp::ui::checkbox("Light theme", &light))
    rmp::ui::set_theme(light ? rmp::ui::theme_light() : rmp::ui::theme_dark());

The dark theme is a default-constructed Theme; its values are the member initialisers in include/rmp/ui.h. The light one is not the dark one with the numbers flipped. A dark interface separates its surfaces with their own shadows and a light one has none, so the light theme sets border_width to 1, and normal buttons and panels get an outline that keeps a pale button on a pale page a button. Its accents are darker, because the blue that reads as bright on near-black looks washed out on near-white, and white text on it stops being legible.

Colours

Each colour of the theme has a job, and these are all of them:

FieldPaints
backgroundBehind the interface. No widget paints it: a game of scenes is cleared with it every frame unless the scene sets its own background; a loop of your own passes it to ClearBackground().
panelA panel, and a dropdown's open list.
surfaceA normal button at rest, the field of a dropdown and of a text field, a slider's rail, an unticked checkbox, the track of a progress bar.
surface_hover, surface_pressA normal, outline or ghost button under the pointer, and while the pointer is held down on it; also a checkbox's row, a dropdown's field and the items of its open list.
borderAn outline button, an unticked checkbox, a dropdown's open list; and normal buttons and panels when border_width is above 0.
textText, the labels of normal, outline and ghost buttons and of every control.
text_mutedMuted text, a slider's percentage, a text field's placeholder.
text_on_accentThe label of a primary or danger button, and the dot of a ticked checkbox.
primary, primary_hover, primary_pressA primary button in its three states; also primary text, a ticked checkbox, the filled part of a slider and of a progress bar.
danger, danger_hover, danger_pressA danger button in its three states; also danger text.
disabled, disabled_textThe fill and the label of a button or control whose enabled is false: the fill is a button's, a checkbox's box, a slider's filled part and a text field's field. A disabled dropdown keeps surface for its field and greys only its label and value.
focusThe ring around whatever the keyboard or gamepad is on. A controller build cannot be used without it, which is why it is the theme's and not each widget's.

Text picks one of four of these through a ColorRole, never a colour of its own: TEXT is text, MUTED is text_muted, PRIMARY is primary and DANGER is danger.

Variants

A button's style is a Variant: what the button is for, not what colour it is.

VariantForLooks
NORMALMost buttons; the default.A filled surface.
PRIMARYThe one thing you want pressed on this screen.primary, with text_on_accent.
DANGERSomething destructive, which should look it.danger, with text_on_accent.
OUTLINEA secondary action.An outline and a label; it fills in under the pointer.
GHOSTToolbars, "back" links.The label alone, in either theme, until the pointer is on it.
 
rmp::ui::row({ .grow_x = true }, [&] {
    rmp::ui::button("Start game", { .style = rmp::ui::Variant::PRIMARY });
    rmp::ui::button("Load");
    rmp::ui::button("Settings", { .style = rmp::ui::Variant::OUTLINE });
    rmp::ui::button("Back", { .style = rmp::ui::Variant::GHOST });
    rmp::ui::button("Delete", { .style = rmp::ui::Variant::DANGER });
});

Being disabled is not a sixth variant, because it can happen to any of them: it is the enabled flag, and a disabled button of any variant is drawn in disabled and disabled_text.

Sizes

Anywhere a size is asked for — a button's, a text's — the same field takes one of three steps of the theme's type scale, or a plain number of design units:

rmp::ui::button("Play", { .size = rmp::ui::Size::LARGE });
rmp::ui::text("Chapter One", { .size = 34 });
StepTheme fieldDefault
Size::SMALLfont_size_small0.8 × [ui] font_size
Size::MEDIUMfont_size[ui] font_size, 20 unless set
Size::LARGEfont_size_large1.4 × [ui] font_size

The steps are what to reach for almost always: they come from the theme, so they stay in proportion when someone changes the type scale. A number is the escape hatch — for a title, not for a button. It is one field that takes two spellings rather than two fields that could disagree.

On a button the step moves the type, the padding and the minimum height together, so a large button is large all over and not a normal one with bigger letters. The one exception is a touch screen: on Android and iOS no button is shorter than min_touch_size, small ones included. The labels of checkboxes, sliders, dropdowns and text fields are always at font_size.

The three type sizes are three fields of the theme. Changing font_size moves the medium step only, so making all the text bigger is all three:

rmp::ui::Theme theme = rmp::ui::current_theme();
theme.font_size *= 1.15f;
theme.font_size_small *= 1.15f;
theme.font_size_large *= 1.15f;
rmp::ui::set_theme(theme);

Transitions

Controls fade between their colours — at rest, under the pointer, pressed — instead of snapping, and a checkbox's box fills in instead of switching. There is nothing to opt into and one knob, transition, the time a change takes. A control seen for the first time starts at the colour it should have, so nothing fades in from nowhere.

Only colour moves. Nothing about the layout is animated, so a control is always exactly where it was drawn and an animation can never make the player miss what they aimed at. transition = 0 turns it off — every control takes its new colour on the frame it changes — which is what a "reduce motion" setting does:

rmp::ui::Theme theme = rmp::ui::current_theme();
theme.transition = reduce_motion ? 0.0f : 0.12f;
rmp::ui::set_theme(theme);

Breakpoints and scale

Two mechanisms make an interface fit a screen, and knowing which to reach for is most of the skill. The scale makes everything bigger or smaller together; it is automatic, and you rarely touch it. A breakpoint changes the shape of a layout, which no amount of growing, fitting or fixing can do: on a phone held upright, a sidebar beside the content has to go above it.

if (rmp::ui::compact()) {
    rmp::ui::column([&] { sidebar(); content(); });
} else {
    rmp::ui::row([&] { sidebar(); content(); });
}

current_breakpoint() classifies the screen by its aspect ratio, width over height, and compact() is the case that comes up:

BreakpointWidth ÷ heightIn practice
COMPACTbelow 1A phone held upright, a narrow window.
MEDIUM1 up to 1.6A tablet, a small desktop window, 4:3.
EXPANDED1.6 and widerAn ordinary desktop, a TV, a phone on its side.

Aspect ratio and not pixels, deliberately: a pixel threshold would call a phone 1080 pixels wide a desktop, and the scale has already dealt with how big everything is. What is left — the only thing that decides whether a row still fits — is how wide the screen is next to how tall. It reads the window's size when it is called, so it needs no begin() first; a window with no height yet is MEDIUM.

Reach for a breakpoint when the layout has to become a different layout. Using one to pick a size undoes the work the scale already did, and is how a layout ends up right on exactly one machine. The responsive example turns a sidebar and its content from a row into a column as the window is resized.

Fonts

The interface draws all its text in one font, named by [ui] font, at sizes measured from [ui] font_size.

Text is drawn at the pixel size the layout asks for: its size in design units — a step or a number — times the scale.

Left empty, the default, the font is raylib's built-in one: no file, no licence, and it works on every platform. It is a bitmap 10 pixels tall, stretched to whatever size the text asks for.

A font of your own is a file in resources/, named relative to it:

[ui]
font = "ui.ttf"
font_size = 24

It is loaded through rmp::assets::load_font, so it works the same loose in resources/ and packed in a release. A font file is only sharp at the size it was rasterised at, so the interface rasterises it once for every pixel size it draws — SMALL, MEDIUM, LARGE and every number, each times the scale — and keeps each of those faces until the interface shuts down. Text is then drawn from a face made at exactly its size, so it stays sharp at any scale. Eight faces are kept at once; a ninth size makes room by letting go of the face used longest ago, never of one drawn in the same frame, whose glyphs may still be waiting to be drawn. A frame that draws more than eight sizes draws the extra ones from the nearest face, stretched.

A font file that is missing or cannot be read does not switch the interface off: it falls back to the built-in font and says so once, UI: [ui] font '…' could not be loaded; using the built-in font.

font_size is the medium step in design units, a whole number from 6 to 200; the small and large steps start at 0.8 and 1.4 times it.
