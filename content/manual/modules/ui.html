Interface

rmp::ui is the interface layer: menus, HUDs, dialogs and settings screens. A main menu is three calls between a begin() and an end(), and it comes out centred, sized for the screen it is on, and playable with a mouse, a finger, a keyboard or a gamepad without a line about any of them.

rmp::ui::begin();
if (rmp::ui::button("Play")) play();
if (rmp::ui::button("Quit")) quit();
rmp::ui::end();

No coordinates, no sizes, no fonts and no hit boxes. Everything else on these pages is what you reach for when the default is not what you want, and you only meet it when you do:

  • Interface layout — rows, columns, panels, grids, scrolling lists, and how big each thing is.
  • Interface controls — checkboxes, sliders, dropdowns and text fields, which write straight into your variables.
  • Interface style — themes, variants, sizes, breakpoints and fonts.

Immediate mode

There are no widget objects. A call to button() both draws the button for this frame and answers whether it was pressed, and the next frame asks again. What persists from one frame to the next is your data; what is rebuilt every frame is the picture. So a menu that depends on the game's state is an if, and a label that changes is a string you build where you call it:

rmp::ui::begin();
rmp::ui::text("Score: " + std::to_string(score));
if (has_save && rmp::ui::button("Continue")) load();
rmp::ui::end();

A temporary string is safe there. Every string handed to the interface is copied the moment it is passed, into memory that lasts until the frame is drawn, so std::to_string(score) dying at the end of the line changes nothing. That memory is a few kilobytes per frame; a frame that somehow needs more has its labels cut short and the log says so once: UI: text arena full (… bytes); labels are being truncated.

Where it goes

In a game made of scenes, a scene's interface goes in its _draw(). That hook runs in screen space after the scene's map and objects have been drawn, so the interface sits on top of the world and stays put while the camera moves:

class PauseScene : public rmp::Scene {
    void _draw() override {
        rmp::ui::begin();
        rmp::ui::text("Paused");
        if (rmp::ui::button("Resume")) rmp::Scene::pop();
        rmp::ui::end();
    }
};

The frame is cleared for you with the theme's background colour, unless the scene sets background itself. A scene underneath another one keeps drawing its interface when the scene on top lets it (see what a scene lets through), and the framework treats every scene's begin()/end() pair as part of one frame.

A game that runs its own loop with RMP_ENTRY_POINT calls the pair between BeginDrawing() and EndDrawing(), after whatever the interface should sit on top of, and clears the screen itself:

BeginDrawing();
ClearBackground(rmp::ui::current_theme().background);
draw_world();
rmp::ui::begin();
if (rmp::ui::button("Quit")) rmp::app::quit();
rmp::ui::end();
EndDrawing();

There is nothing to start and nothing to stop. The interface starts itself on the first begin() — by which time there is a window — so a game that never draws an interface never allocates one, and the entry point shuts it down for you while the window is still open. A begin() after rmp::ui::shutdown() starts it again, the same way the first one did.

The three rules

That is all of them.

  1. end() draws. Everything between begin() and end() is laid out and drawn when end() runs, so the pair goes where the drawing is: in _draw(), or between BeginDrawing() and EndDrawing().
  2. One pair at a time. Pairs do not nest: a second begin() before the end() of the first is ignored, with UI: begin() called twice without end(); ignoring the second one in the log. A widget called outside any pair draws nothing and returns false. In a game of scenes each scene can have its pair in the same frame; in a loop of your own, it is one pair per frame.
  3. Interaction uses the previous frame's layout. When button("Play") has to answer, this frame's layout does not exist yet — it is computed in end() — so the button is hit-tested against where it was last frame. A control cannot be clicked on the very first frame it appears, which is 16 ms at 60 frames a second, and while the interface is moving the place you can click trails what you see by one frame.

The third rule is the cost of immediate mode, and the alternative is worse. Laying the interface out twice per frame would mean running your code twice, and a score++ inside a button's if would count double.

Buttons and text

rmp::ui::button returns true on the frame it is pressed: the pointer released over it, having been pressed on it — press, drag off and let go, and nothing happens — or, while it has the focus, Enter, Space or the gamepad's bottom face button. It reads the way it looks:

if (rmp::ui::button("Start", { .style = rmp::ui::Variant::PRIMARY })) start_game();
if (rmp::ui::button("Delete save", { .style = rmp::ui::Variant::DANGER, .enabled = has_save }))
    delete_save();

ButtonOptions has four fields, written in this order:

FieldDefaultMeans
styleVariant::NORMALWhat the button means — normal, primary, danger, outline, ghost. The theme decides what that looks like; see variants.
sizethe theme'sSize::SMALL, MEDIUM or LARGE, or a number of design units. See sizes.
enabledtruefalse draws it in the theme's disabled colours; it cannot be pressed and the focus skips it.
idnoneA name that stays the same whatever the label says. See labels are ids.

The order matters, because C++20 requires designated initialisers in declaration order: { .style = …, .enabled = false } is right, and { .enabled = false, .style = … } does not compile. GCC and MSVC refuse it on their own; Clang only warns, so wherever Clang compiles a game the framework adds -Werror=reorder-init-list — in the CMake builds, on Android and in the generated iOS project — and the mistake fails on the machine that made it, not later on another compiler. Every options struct in rmp::ui is ordered the way its fields are most likely to be written, so the order you would write them in is usually the one that compiles; when a compiler complains about designator order, that is what it means.

A button fills the width it is offered. In begin()'s column that is the width of the widest thing in it, which is why the buttons of a menu come out the same width without anyone measuring anything; in a row, the buttons share the row; in a frame opened to fill the window, it is the window's width less the padding. Its height is at least the theme's min_touch_size — 44 design units, a target a thumb can hit — scaled with its type size.

rmp::ui::text draws a string, in one of the theme's colours, at one of its sizes:

rmp::ui::text("Game over", { .size = rmp::ui::Size::LARGE });
rmp::ui::text("Progress since the last save is lost.", { .color = rmp::ui::ColorRole::MUTED });
rmp::ui::text("v1.0.2", { .color = rmp::ui::ColorRole::MUTED, .size = 14, .wrap = false });

TextOptions is color — a ColorRole, not a colour — size and wrap. With wrap on, the default, a line too long for the space it is given breaks between words; off, it is never broken.

Labels are ids

The interface keeps a little state of its own about each control: whether the pointer is over it, whether a press started on it, whether it has the focus, the colour it is fading towards, whether a dropdown is open. It finds that state again every frame by the control's label. Two controls with the same label in one begin()/end() are told apart by their order — the second "Back" is a different control from the first — so the common case needs nothing.

Order is what breaks when the interface is conditional. A control that appears or disappears before others with the same label renumbers them, and the hover, the focus or the fade moves to a different control with nothing in your code having changed. The id field is the escape: a name that is the same control whatever else is on screen.

for (int i = 0; i < 3; i++) {
    if (!slots[i].used) continue;
    rmp::ui::text(slots[i].name);
    std::string id = "erase" + std::to_string(i);
    if (rmp::ui::button("Erase", { .id = id.c_str() })) erase(i);
}

A label that changes is a new control each time it does. A button that reads "Music: on" and then "Music: off" loses the focus when it is pressed from the keyboard, because the control that had it is gone, and the focus goes back to the first control on the screen. An id keeps it the same control:

if (rmp::ui::button(music ? "Music: on" : "Music: off", { .id = "music" })) music = !music;

Containers have no id unless you give them one; see naming a container.

Focus, keyboard and gamepad

Every control is focusable, in the order it is declared, and nothing in your code asks for it. The widgets you already wrote can be played with a keyboard or a gamepad:

DoesKeyboardGamepad
Next controlTab, Downd-pad down, left stick down
Previous controlShift+Tab, Upd-pad up, left stick up
Press, tick, openEnter, keypad Enter, Spacebottom face button
Back out of a text field or an open listEscaperight face button
Move a sliderLeft, Rightd-pad left and right, left stick

Past the last control the focus wraps to the first, and holding a direction walks the list after a short pause. These keys are read by the interface itself, from raylib; they are not rmp::input actions, and redefining an action does not change them. The focus moves between controls of the previous frame, for the same reason hit testing does.

Two controls use the keys a little differently, and their sections say how. A text field types only once it has the keyboard, which is not the same as having the focus, and Tab, Up and Down leave it like any other control. An open dropdown takes Up and Down for its own items. Escape backs out and nothing more: raylib's habit of closing the window on it is switched off by the entry point (see the Escape key).

Nothing to start

A screen that declares something focusable and has nothing focused gives the focus to its first control. A game-over scene with one "Play again" button on it answers Enter and the gamepad's bottom button the moment it appears.

Having the focus and showing it are two things. The focus ring — the theme's focus colour, focus_ring design units wide — appears once the player touches the keyboard or the gamepad, and goes away again on a click. Someone playing with a mouse does not find an outline on the first button of every menu; someone with a controller sees where they are as soon as they reach for it.

Moving it yourself

A screen does not need to put the focus anywhere: its first control already has it. rmp::ui::focus() is for starting somewhere else. It gives the focus to a control by its label or by the id it was given, and shows the ring straight away, because you asked for it; a text field given the focus this way also takes the keyboard. An empty string clears it, and by the rule above the screen's first control then takes it. rmp::ui::focused() names what has it, or gives "".

The place to call it is the scene's _ready(), once. Between frames there is no interface being described to look the name up in, so the name waits: the next frame that draws controls gives the focus to the first one carrying it, in whichever scene draws it. focused() answers with the name at once. If that frame draws controls and none of them has the name, the request is dropped and the screen keeps its own first control, rather than lying in wait for a control with that label to turn up later.

void _ready() override {
    rmp::ui::focus("Continue"); // not the first button: the one the player most likely wants
}

void _draw() override {
    rmp::ui::begin();
    rmp::ui::button("New game");
    rmp::ui::button("Continue");
    rmp::ui::end();
}

Called inside a begin()/end() pair, it looks the label up among the controls of that pair, so it goes before the control it names.

rmp::ui::set_navigation_enabled(false) turns keyboard and gamepad handling off, for a game that drives the focus itself; navigation_enabled() says whether it is on. It starts on. With it off, clicks and taps still work but no control has the focus, so Enter, Space and the gamepad press nothing. A text field still types when it is clicked, and stops on Enter, Escape or a click elsewhere, because those are read whether navigation is on or not.

Scenes on top of scenes

When two scenes draw, the one on top holds the focus. A scene underneath that input cannot reach — the scene above left input_below at false — is drawn exactly as usual, and nothing in it can be hovered, focused or clicked: a HUD under an open pause menu is visible and inert, and neither scene says so.

When the scene on top sets input_below, both scenes' controls are one list: the one underneath can hold the focus, and the arrows walk up out of it into the scene above and back down. A scene whose interface is drawn first does not claim a focus that was on screen last frame, because a scene drawn after it may be about to declare that control; only when no scene does is the focus handed on.

A button in the HUD

The scene the player plays in reads its own keys — and a HUD there with a button on it takes the focus by the rule above. Enter, Space and the bottom face button would then press that button every time the player jumps or shoots with one of them. Turning navigation off while the game is played, and on again for the menu, keeps the button for the pointer. The setting belongs to the interface and not to a scene, so it outlives them: every scene that shows a menu turns it on in its _ready(), and the playing scene turns it off again when it comes back:

class PauseScene : public rmp::Scene {
    void _ready() override { rmp::ui::set_navigation_enabled(true); }
    void _draw() override {
        rmp::ui::begin();
        if (rmp::ui::button("Resume")) rmp::Scene::pop();
        rmp::ui::end();
    }
};

class GameScene : public rmp::Scene {
    void _ready() override { rmp::ui::set_navigation_enabled(false); }
    void _resume() override { rmp::ui::set_navigation_enabled(false); }
    void _draw() override {
        rmp::ui::begin({ .placement = rmp::ui::Align::TOP_RIGHT });
        if (rmp::ui::button("Pause")) rmp::Scene::push<PauseScene>();
        rmp::ui::end();
    }
};

Telling the game to keep its hands off

The interface reads the pointer and the keyboard itself, and the game reads them too. Two functions say when the game should leave them alone:

  • rmp::ui::wants_pointer() — the pointer is over something the interface paints, a slider is being dragged, or a dropdown's list is open.
  • rmp::ui::wants_keyboard() — a text field has the keyboard and is typing. Having the focus is not enough: a field the player pressed Enter on keeps the focus and gives the keyboard back.

"Something the interface paints" is every control, every box with a background colour or a border — a panel, a progress bar, an open dropdown list — every image, and every scroll area, its empty part included but not where it has clipped its rows away. A click on a panel's background is the interface's, and does not fall through to the game behind it. Plain text with nothing behind it is the exception, on purpose: a score drawn over the game does not stop the game being clicked through it.

Each frame's answer stands until the next frame's first begin(), so they read the same in _update() and on the line after end(). In a game of scenes, a frame in which no scene calls begin() answers false to both — a pause menu that pops while the pointer is over one of its buttons does not leave the game's mouse dead — except that a slider being dragged keeps wants_pointer() true until the pointer comes up. A game that reads its actions by name through rmp::input rarely calls them, because such a read already asks them — the subject of who hears a press. Wherever the game reads raylib's input directly, they are the check:

if (!rmp::ui::wants_pointer() && IsMouseButtonPressed(MOUSE_BUTTON_LEFT)) shoot();
if (!rmp::ui::wants_keyboard() && IsKeyDown(KEY_W)) walk();

Touch

raylib reports the first touch as the mouse, so a menu works on Android and iOS with no extra code. Three things change underneath on those two:

  • Hover only while a finger is down. A touch screen has no pointer at rest, and the last place tapped would otherwise stay lit up.
  • No button is shorter than min_touch_size, even a small one: a small button on a phone is still pressed with a thumb.
  • The edges are kept clear. begin() keeps 24 design units free at every edge of the screen, on top of its own padding, for the status bar and the notch — [android.display] into_cutout draws the game behind the notch, which is right for a background and wrong for a menu.

Scale and design units

Every size in rmp::ui — a theme's padding, a panel's width, a text's size — is in design units: pixels at the resolution [window] width and height declare in raylib_multiplatform.toml. That block is the resolution you design for, and the interface is drawn as if the window were that size. One number turns design units into pixels:

scale = clamp(min(window width / [window] width, window height / [window] height), 0.5, 4)

Designed at 800×450 and played at 1920×1080, everything is 2.4 times bigger; in a window of 1280×720, 1.6 times. It is min() and not max() because what does not fit is worse than what is left over: the tighter side wins and the interface stays on screen. The clamp stops the two absurd ends, a window too small to read and a monitor that turns a button into a billboard.

Text follows the same scale: it is drawn at the pixel size the layout asks for, its size in design units times the scale. raylib's built-in font is a small bitmap stretched to that size; a font of your own is rasterised at that exact size, so it stays sharp. See fonts.

rmp::ui::scale() reads the factor in use. rmp::ui::set_scale() pins it — an "interface size" option in a settings screen — and 0 goes back to automatic. A pinned scale is used as it is, without the clamp. [ui] scale pins it from the start; it is 0, automatic, unless you set it:

[ui]
scale = 1.5

Scale makes everything bigger or smaller together. Changing the shape of a layout on a narrow screen is a different tool, the breakpoint, in interface style.

Configuration

The [ui] section of raylib_multiplatform.toml holds five keys, and with all of them at their defaults a menu is still three calls:

KeyDefaultMeans
theme"dark"Which theme the game starts with, "dark" or "light". See themes.
font""A font file in resources/; empty is raylib's built-in font. See fonts.
font_size20The theme's type size, in design units: a whole number from 6 to 200.
scale00 is automatic; a number from 0 to 8 pins it.
max_elements512The most elements the interface lays out in one frame, from 16 to 65536.

max_elements is what sizes the interface's memory, and it is a ceiling, not a guess. Every control is more than one element — a button is its box and its label — so a long list counts quickly. Past the ceiling the interface stops laying anything out until the game is restarted, and says so once, naming the key: UI: more than max_elements (…) elements in one frame. The interface will not lay out again until the game is restarted. Raise it, or draw less at once:

[ui]
max_elements = 1024

What is underneath

The layout engine is Clay, and none of its types appear in rmp/ui.h, so code written against rmp::ui does not depend on it. It is still there to use. Include <clay.h> and write Clay's own elements between begin() and end(): they join the same tree, are laid out in the same pass and drawn by the same renderer. Two things to know before doing it: begin() has already opened two elements — a root that fills the screen and the column inside it — so yours become children of that column; and Clay does not copy strings, so a string built at runtime has to outlive end(). Dropping to Clay has the rest of the rules, and the Clay example does it next to rmp::ui calls in the same frame.

The examples

Every example is a small project the framework builds and boots in CI, and each of these is one idea:

  • Menu — the three-call menu, a confirm screen, a HUD, one screen per file.
  • Layout — rows, columns, panels, stacks, spacers, images and progress bars.
  • Clay direct — Clay's own API next to rmp::ui.
  • Settings — every control, writing into one struct that is saved.
  • Inventory — a grid that works out its columns and a scrolling list.
  • Style — both themes, every variant and size.
  • Responsive — one layout that turns from a row into a column on a narrow screen.
