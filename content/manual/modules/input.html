Input

rmp::input gives what the player presses a name, and decides who gets to hear it. raylib answers "is the space bar down?"; a game wants to know "did the player jump?", and whether that press was meant for the game at all or for the button under the player's finger.

rmp::input::action("jump", KEY_SPACE, KEY_W, GAMEPAD_BUTTON_RIGHT_FACE_DOWN);
if (rmp::input::just_pressed("jump")) jump();

It is one header, #include <rmp/input.h>. The entry point reads the devices once at the top of every frame, before the frame hook runs, so every question asked during that frame gets the same answer. In a game started with RMP_GAME that is before any scene updates, and two scenes in the same frame cannot disagree about what is held down. A game that runs its own frame with RMP_ENTRY_POINT gets the same reading before its on_frame, and reads its actions there exactly as a scene does.

Without scenes

A game written with RMP_ENTRY_POINT and no scenes has no scene stack, so the third rule of who hears a press never applies to it, and the interface's two rules apply as they do anywhere. pointer() goes through the camera of the scene on top, and with no scene there is no camera: there it is pointer_screen(), the position in the window's pixels, and nothing is reported.

Actions

An action is a name and the bindings that press it, as many as you like. rmp::input::action takes the name first and the bindings after it:

rmp::input::action("jump", KEY_SPACE, KEY_W, GAMEPAD_BUTTON_RIGHT_FACE_DOWN);
rmp::input::action("fire", MOUSE_BUTTON_LEFT, KEY_J, GAMEPAD_BUTTON_RIGHT_TRIGGER_1);

Each binding is a plain raylib constant, and its type says which device it belongs to. KeyboardKey, MouseButton and GamepadButton are three different enums in C++, so the framework knows at compile time that KEY_SPACE is a key and MOUSE_BUTTON_LEFT a mouse button. Anything else is a compile error at the call, which is also why there is no string of key names to spell wrong:

rmp::input::action("jump", 32); // an int is not a key

An action with no binding at all does not compile either: there is no version of action() that takes the name alone.

Defining one again replaces it

Calling action() with a name that already exists replaces its bindings; it does not add to them. That is what makes the natural place for these calls safe — a scene's _ready(), which runs every time the player enters the scene:

void _ready() override {
    rmp::input::action("jump", KEY_SPACE, GAMEPAD_BUTTON_RIGHT_FACE_DOWN);
    rmp::input::action("fire", MOUSE_BUTTON_LEFT, GAMEPAD_BUTTON_RIGHT_TRIGGER_1);
}

It is also how a game rebinds a key at runtime: call action() again with the new list. An action holds up to eight bindings; more than that keeps the first eight and says so in the log: INPUT: "…" was given … bindings and the limit is …; the extra ones are ignored.

Reading an action

Three questions, each asked by name:

CallTrue
pressed("jump")Every frame any of its bindings is held down.
just_pressed("jump")The frame one of them goes down.
just_released("jump")The frame one of them comes up.

The edges compare this frame with the one before, and the first frame of the game is compared with itself: a key already held when the game starts does not read as just pressed and fire whatever it is bound to.

An action nobody has defined reads as false, and the log says so once per name — not sixty times a second: INPUT: no action called followed by the name. A misspelt name is the usual reason.

Half of a stick

An analogue stick reads from -1 to +1 and an action is on or off, so a stick binding names one half of an axis. rmp::input::stick is the one place you write something that is not a plain raylib constant:

rmp::input::action("aim_left", KEY_Q, rmp::input::stick(GAMEPAD_AXIS_RIGHT_X, -1));
rmp::input::action("aim_right", KEY_E, rmp::input::stick(GAMEPAD_AXIS_RIGHT_X, 1));

The sign says which half counts: -1 is left or up, +1 right or down. Any negative number is taken as -1 and any other, 0 included, as +1, because a stick has two halves and there is no third thing to mean. The half counts as pressed once the stick is past the dead zone, described below.

Which gamepad

Every gamepad binding reads the first gamepad raylib knows, index 0. A game for several players on one machine reads the others from raylib itself, with IsGamepadButtonDown() and the gamepad's index.

The actions that come with it

Six actions exist before the game defines any, so that movement works with no setup at all. They are ordinary actions: defining one of these names again replaces it like any other.

The interface does not read them: rmp::ui watches its own keys for moving the focus, pressing a button, and backing out of a text field or an open list (see focus, keyboard and gamepad), so redefining ui_accept does not change what presses a focused button.

Moving: vector and axis

rmp::input::vector() is a direction from four actions, and with no arguments it uses the four move_ actions above — the keyboard, the d-pad and the left stick at once:

velocity = rmp::input::vector() * 200;

Three things are decided for you in that line:

  • It is normalised. Holding right and down gives a vector of length 1, not 1.41, so going diagonally is not 41 % faster than going straight. Only a vector longer than 1 is shortened: a stick pushed halfway still gives half.
  • +Y is down, as in raylib's screen coordinates and an object's position, so "up" gives a negative Y and nothing has to be flipped.
  • Opposite directions cancel. Left and right held together give 0, which is what a player mashing both keys expects.

rmp::input::axis() is the same thing on one axis: -1, 0 or +1 from move_left and move_right, or the analogue value in between when a stick is what is moving it. A platformer walks with it:

velocity.x = rmp::input::axis() * 180;

Both take your own actions too, in the order negative then positive:

float aim = rmp::input::axis("aim_left", "aim_right");

rmp::input::action("port", KEY_A);
rmp::input::action("starboard", KEY_D);
rmp::input::action("ahead", KEY_W);
rmp::input::action("astern", KEY_S);
Vector2 boat = rmp::input::vector("port", "starboard", "ahead", "astern");

Each action contributes how far it is pushed, from 0 to 1. A key or a button is all or nothing; a stick is analogue. When an action has several bindings the strongest one wins, so a key held down gives a full 1 even if the stick on the same action is only half pushed.

For a stick's raw reading — a camera that turns with the right stick, say — rmp::input::axis_value() gives one axis from -1 to +1, dead zone applied, and is never routed:

float turn = rmp::input::axis_value(GAMEPAD_AXIS_RIGHT_X);

The dead zone

A stick at rest does not read exactly 0, and a worn one drifts further. The dead zone is the part of the travel that reads as zero, as a fraction of it, and it starts at [input] deadzone in raylib_multiplatform.toml:

[input]
deadzone = 0.25

Past the zone the reading is rescaled so that it starts again from 0: just outside a dead zone of 0.2 the stick reads a little above zero, not a sudden 0.2, and a character does not lurch into motion at a fifth of its speed. Keys and the d-pad have no travel and are unaffected.

The value has to be between 0 and 0.95. Anything else is refused when the configuration is read, before a build starts, with the reason:

[input]
deadzone = 1.0

At runtime, rmp::input::deadzone() reads it and rmp::input::set_deadzone() changes it — what a settings slider calls. A value outside 0..0.95 is clamped rather than refused, so a slider cannot switch the sticks off:

static float deadzone = rmp::input::deadzone();
if (rmp::ui::slider("Stick dead zone", deadzone, 0.0f, 0.5f)) rmp::input::set_deadzone(deadzone);

The pointer

The mouse and a finger are one pointer. raylib already reports the first touch as the mouse, so the same code works on a desktop and on a phone, with no #if:

CallGives
pointer_screen()Where it is, in pixels, from the top-left of the window.
pointer()Where it is in the world, through the camera of the scene on top of the stack: what you compare an object's position with. With no scene on the stack, as in a game on RMP_ENTRY_POINT without scenes, there is no camera, and it is pointer_screen(). The same as pointer_screen() while that camera has not moved and the window is the size [window] width and height ask for. The camera puts its position, which starts at the middle of that size, in the middle of the real window, so in a window of any other size — resized, or a phone's screen — the two differ even when the camera has not moved.
pointer_delta()How far it moved since the last frame, in pixels. Zero on the first frame.
pointer_down()The left button, or a finger, is held.
pointer_pressed()The frame it goes down.
pointer_released()The frame it comes up.

The last three are the left mouse button, read raw: they are not routed, so a press on an interface button reads as pointer_pressed() too. To act only on presses the interface did not take, ask consumed_pointer() first — or bind the button to an action, which asks for you:

if (rmp::input::pointer_pressed() && !rmp::input::consumed_pointer()) {
    spawn({ .position = rmp::input::pointer() });
}

An object that wants to be clicked does not need any of this: its on_click already gives the interface first refusal.

Who hears a press

A finger that presses a button on the HUD must not also fire the gun under it, and typing a name into a text field must not walk the player across the level. Both have to be true without anyone writing an if, so a query by name is routed, and a query by device is not:

if (rmp::input::just_pressed("fire")) shoot(); // routed: quiet while something above has the input
if (rmp::input::pressed(KEY_W)) walk();        // raw: exactly IsKeyDown(KEY_W), always

The argument's type says which of the two you asked for, and you can see it at the call. The raw versions — pressed, just_pressed and just_released given a key, a mouse button or a gamepad button constant instead of a name — are there for when you want to know regardless of who else is listening: a held Shift that makes the player run, a debug key.

The three rules

An action reads as false while something above the code asking for it has taken its device. It is decided binding by binding, so an action on both a key and a mouse button still answers to the key while the mouse is over a button.

  1. Mouse bindings go quiet while the interface wants the pointer: while rmp::ui::wants_pointer() is true. That is while the pointer is over anything the interface paints — a control, a panel or any box with a background or a border, an image, a scroll area, empty part included — while a slider is being dragged, and while a dropdown's list is open. Plain text with nothing behind it does not take the pointer, so a score drawn over the game can be clicked through.
  2. Key and gamepad bindings go quiet while the interface wants the keyboard: while rmp::ui::wants_keyboard() is true, which is while a text field is typing — not merely while it has the focus (see typing is having the keyboard). Gamepad buttons and sticks go with the keyboard.
  3. Every action goes quiet in a scene that another one covers, unless every scene above it set input_below, which is false by default. A covered scene is usually not updated at all; when the one on top sets updates_below — a world that keeps moving under a menu — its _update() runs and every action it reads is false, and neither scene says so. See what a scene lets through.

The interface's answers come from the previous frame. _update() runs before anything draws, so it reads what the interface did last frame — one frame of tolerance, which nobody notices. In a game of scenes, a frame in which no scene draws any interface answers false to both, so a pause menu that pops while the pointer is over one of its buttons does not leave the game's mouse dead. The one exception is a slider being dragged, which keeps wants_pointer() true until the pointer comes up.

For code that wants the reason and not the answer — a different cursor over the HUD, a raw read that should still respect the interface — consumed_pointer() and consumed_keyboard() answer whether anything above the caller is holding that device: a scene on top, or the interface.

What routing does not cover

The interface's own navigation is not an action. Up, Down and Tab — and the d-pad and the left stick, up and down — move the focus between controls, and Left and Right move a focused slider. Enter, Space and the bottom face button press the focused one, and Escape and the right face button back out of a text field or an open list. wants_keyboard() is only about text fields. In a scene that draws a menu and reads move_up, the up arrow moves both. The usual shape keeps them apart: the menu is its own scene, pushed on top, and the game underneath is frozen or, by the third rule, deaf. A HUD in the playing scene can have buttons too; the interface page says what to switch off while the game is being played.

Escape is the game's key

raylib makes Escape the key that closes the window. The entry point takes that away once the
ready hook has returned, in every runner and whoever opened the window, so an action bound to
KEY_ESCAPE — the pause action above, ui_cancel — reads as
pressed and the game carries on. The window's close button still closes it. Because it happens after
the ready hook, a SetExitKey() of the game's own there, a first scene's
_ready() included, is overwritten. A game that quits on a key says so with
rmp::app::quit() (see
the Escape key):


rmp::input::action("quit", KEY_Q, GAMEPAD_BUTTON_MIDDLE_LEFT);
if (rmp::input::just_pressed("quit")) rmp::app::quit();






Dropping to raylib



Nothing here hides raylib. IsKeyPressed(), GetMousePosition(),
GetTouchPointCount(), GetGestureDetected() and the rest work as they always
do, next to rmp::input, and they are what to reach for when the game needs something
this module does not model: several touches at once, a second gamepad, text typed as characters with
GetCharPressed(). They are raw — the routing above does not apply to them — so a raw
read that should leave the interface alone asks
consumed_pointer() or
