Interface controls

Four controls own a value: a checkbox, a slider, a dropdown and a text field. Each one takes a pointer to your variable and writes to it, and that is the whole of their state model — there is no widget object holding a copy, and nothing to keep in sync.

rmp::ui::begin();
rmp::ui::checkbox("Fullscreen", &settings.fullscreen);
rmp::ui::slider("Music", &settings.music, 0.0f, 1.0f);
rmp::ui::dropdown("Quality", &settings.quality, QUALITY, 3);
rmp::ui::text_input("Name", settings.name, sizeof(settings.name));
rmp::ui::end();

The state model

Every control reads your variable and writes it back in the same call, so what is on screen is what is in your struct because it was read this frame. Delete the screen and the settings still exist: they were never the interface's. The struct stays plain data, which is also what makes it easy to save:




Each control returns true on the frame its value changed, so "do something when it
changes" reads the way it sounds:



if (rmp::ui::checkbox("Fullscreen", &cfg.fullscreen)) apply(cfg);




The pointer is yours and is not kept past the call. A null one draws nothing and returns
false.



What the interface does keep is the state that means nothing to your game — whether a dropdown is
open, whether a slider is being dragged — and it keeps it by the control's id, which is its label
unless you give it an id. The rules are the ones for buttons, in
labels are ids.



What they have in common



Each control is a row: its label on the left, the control itself after it. The row fills the width
it is offered and is focusable as one thing, so the focus ring goes around the whole row and the
keyboard and gamepad reach it like a button (see
focus, keyboard and gamepad). The label
is drawn at the theme's font_size.



All four options structs have the two fields buttons have:



    

  • enabled — false draws the control in the theme's
disabled colours; it cannot be changed, and the focus skips it. A control that is unavailable right
now reads better disabled than missing: a menu whose items appear and disappear is a menu nobody can
learn.
    • 

  • id — a name that is the same control whatever its label says, for
two controls that share a label on a screen that changes.

Checkbox



rmp::ui::checkbox flips a bool when
its row is clicked, or when it is pressed — Enter, Space, the bottom face button — while it has the
focus. It returns true on the frame it flipped:



if (rmp::ui::checkbox("Light theme", &light))
    rmp::ui::set_theme(light ? rmp::ui::theme_light() : rmp::ui::theme_dark());




The box is filled with the theme's primary and carries a dot when the value is
true, and is the theme's surface inside a border when it is
false — a difference that reads at a glance without a tick, which the built-in font
does not have. Its size is the theme's
control_size.
CheckboxOptions is
enabled and
id.



Slider



rmp::ui::slider sets a float between a
minimum and a maximum:



if (rmp::ui::slider("Music", &music, 0.0f, 1.0f))
    rmp::audio::set_volume(rmp::audio::Bus::MUSIC, music);
rmp::ui::slider("Sensitivity", &sensitivity, 0.0f, 1.0f, { .step = 0.05f });




    

  • With the pointer, press on the rail and drag: the value follows where the
pointer is along it. The area that takes the press is a little taller than the rail, which is
thinner than a finger. While a drag lasts the slider holds the pointer — wants_pointer()
stays true — even when the pointer leaves the rail.
    • 

  • With the keyboard or a gamepad, while it has the focus, Left and Right — or the
d-pad, or the left stick — move it one step per press, then twelve steps a second while held. A step
is step, or 5 % of the range when there is none, so a controller can move a slider of
any range.
    • 




The value is clamped to the range, and snapped to step when there is one, on every
call — not only when it is touched. A variable that starts outside the range is corrected on the
first frame, and the slider returns true for that frame like for any other change.
Nothing is drawn when max is not above min.



SliderOptions:





FieldDefaultMeans



width0Of the rail, in design units; 0 fills the space available.


step00 is continuous; otherwise the value snaps to min plus a multiple of it.


enabledtrueAs above.


show_valuetrueDraw the position after the rail, as a percentage of the range.


idnoneAs above.






The number show_value draws is where the handle is, not the value: a slider from 0 to
60 standing at 30 shows 50%. A screen that wants the value itself turns it off and draws it with
text().



Dropdown



rmp::ui::dropdown picks one string of an array.
The value it writes is an index into that array:



static const char *const QUALITY[] = { "Low", "Medium", "High", "Ultra" };
if (rmp::ui::dropdown("Quality", &quality, QUALITY, 4)) apply_quality(quality);




A click on it opens the list, which floats over whatever is below instead of pushing it down the
screen. A click on an item picks it and closes the list; a click anywhere else closes it. The return
value is true when a different item was picked. While the list is open it is in front
of everything else in the scene: wants_pointer() is true wherever the pointer is, and a
click on the list does not reach what is behind it.



Pressed from the keyboard or a gamepad, while it has the focus, a dropdown opens and closes its
list; picking an item in the list is done with the pointer.



The index is clamped into the array on every call, so a value read from an old save cannot point
past the end of a shorter list. Nothing is drawn when the array is null or count is not
above 0. The strings are copied as they are drawn, so they only have to live through the call.
DropdownOptions is
width — of the field, in design
units, 0 filling the space available — enabled
and id. Two dropdowns that both have a
"Low" in them are still two lists: an item belongs to its dropdown, not to its text.



Text field



rmp::ui::text_input edits a
char buffer of yours. It writes into it, NUL-terminated, and never past
capacity - 1:



static char name[24] = "";
rmp::ui::text_input("Name", name, sizeof(name), { .placeholder = "your name" });




A click on the field gives it the focus, and so does reaching it with Tab or the d-pad. While it
has the focus, typed characters are added at the end — printable ASCII, the characters from space to
~ — and Backspace removes the last one, repeating while it is held. A blinking
_ marks the end of the text. There is no caret to move, no selection and no clipboard.
Typing arrives through raylib's GetCharPressed(); the field does not open an on-screen
keyboard on Android or iOS.



The return value is true on the frames the text changed.
TextInputOptions:





FieldDefaultMeans



width0Of the field, in design units; 0 fills the space available.


enabledtrueAs above.


placeholdernoneShown in the theme's text_muted while the field is empty and does not have the focus. It is copied, so a temporary is fine.


idnoneAs above.






An empty label draws the field alone. A capacity below 2 — no room for a character and
its terminator — draws nothing.



The keyboard is the field's



While a text field has the focus, rmp::ui::wants_keyboard()
is true, and every rmp::input action reads its keys, gamepad
buttons and sticks as not pressed; only its mouse buttons still count. Typing "Wolf" into a name
field does not walk the player across the level.



The field keeps the focus

A text field holds the focus until the game moves it. While it has it, Tab, the arrows and the
d-pad do not move the focus on, and a click on another control does not take it away — so a player
who reaches the field with a controller stays in it. Give the focus back from code with
rmp::ui::focus(): an empty name clears it, and the screen's
first control takes it. Enter, read from raylib, is a natural moment:


static char name[24] = "";
rmp::ui::text_input("Name", name, sizeof(name));
if (rmp::ui::focused() == "Name" && IsKeyPressed(KEY_ENTER)) rmp::ui::focus("");
