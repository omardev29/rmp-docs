Ship it

The game is finished. What is left is to give it the identity stores will know it by, check it the way CI will, and tag a version: CI does the rest, and builds it for every platform the game has turned on.

Real app ids

rmp new gave the game ids that start with com.example., which a release refuses. Choose real ones, made of a domain you own written backwards and the game's name, and set them in raylib_multiplatform.toml:

[android]
application_id = "com.yourname.coinrabbit"

[ios]
bundle_id = "com.yourname.coinrabbit"

Choose with care: once an app is published on Google Play under an id, that id is its id for good, and changing it means a new listing that starts with no players. The App Store's bundle id is the same kind of promise.

The two kinds of id do not accept quite the same characters. Android takes letters, digits and underscores in each part, and Apple takes letters, digits and hyphens, so the safest id has neither. A hyphen in the Android id is refused, with the line it is on and an id that would work, the moment anything reads the file:

[android]
application_id = "com.yourname.coin-rabbit"

That is the rule for the whole .toml: a value that cannot work stops the build before anything is compiled, and says where.

Check it

rmp test

In a game, rmp test runs three stages, and CI checks the same three things on every push:

  • config: the .toml, the versions the framework pins, and the licence of every library in the game;
  • render: the game built for raylib's software renderer, booted, drawing a frame with something on it, and closing cleanly, with no window and no graphics card;
  • smoke: the game built as you run it, booted for a few frames, checked to have loaded every asset it asked for and drawn something.

A boot only reaches the first scene, so rmp test says the game starts, loads its art and draws its menu. Whether the game is fun is still yours to check, with rmp run.

Put it on GitHub

CI is GitHub Actions, and the workflows came with the game. Commit your work, make an empty repository on GitHub, and push to it:

git add -A
git commit -m "Coin Rabbit"
git remote add origin https://github.com/yourname/my_game.git
rmp push

rmp push is git push with one check in front of it: it will not push while a CI run of the repository is still going, because a new push cancels it. It needs the gh command to ask; without it, it says so and pushes.

Every push to main runs the fast lane: the checks above, and builds for Linux, the web, Windows and Android. Watch it on the repository's Actions tab.

Release

rmp deploy 1.0.0

rmp deploy checks everything a release needs before it makes a tag that cannot be quietly taken back: that every change is committed, that v1.0.0 is not already a tag, that the commit is the one GitHub has, and that the .toml is valid with real ids in it. Then it tags the commit v1.0.0 and pushes the tag.

The tag is the version: there is no version number in the project to keep in step with it. For a tag, CI builds every target that [targets] has turned on, all {{count:targets}} of them unless you turned some off, boots the ones it can, and, when every build has passed, publishes a GitHub release with them attached. It also pushes them to itch.io, if [deploy.itch] names your page there and the repository has the secret butler needs.

The Android build is signed with a throwaway key, which Google Play does not accept, until the repository holds your upload key as a secret. The Publishing section has that, and everything else about where each build goes: releases and versions, itch.io, Google Play and the App Store.

What next

The game you built uses most of what the framework has: scenes, objects, behaviors, input, the interface, assets, audio and saving. The Manual takes each of them further, and the Examples are whole games to read, from Pong to a platformer whose levels are made in an editor.
