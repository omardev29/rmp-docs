Install rmp

One line in a terminal gets the framework and puts rmp on your PATH. It installs into your home folder, as you, and asks for no administrator: nothing in it runs sudo, and nothing in it installs a package.

The line

On Linux and macOS:

curl -fsSL https://omardev29.github.io/rmp-docs/install.sh | sh

The same script, fetched with what each system has. None of the three BSDs has curl in its base system:

wget -qO- https://omardev29.github.io/rmp-docs/install.sh | sh      # Linux without curl
fetch -o - https://omardev29.github.io/rmp-docs/install.sh | sh     # FreeBSD
ftp -o - https://omardev29.github.io/rmp-docs/install.sh | sh       # OpenBSD, NetBSD

On Windows, in PowerShell — Windows PowerShell 5.1 or PowerShell 7:

irm https://omardev29.github.io/rmp-docs/install.ps1 | iex

Then open a new terminal and check:

rmp help

A line that pipes a download into a shell runs whatever is at that address, so read it first if you like: it is install.sh and install.ps1. They are the framework's tools/install.sh and tools/install.ps1, served by this site byte for byte as they are at the commit it documents — this site's own checks fail the day they are not.

What it needs

Two things, and the installer stops and says how to get whichever is missing, having installed nothing: git, which fetches the framework and every update after it, and Python 3.11 or newer, which rmp is written in. It asks every Python it finds for its version rather than trusting the name: macOS's own python3 is older than 3.11, and on Windows python3 can be the Microsoft Store's placeholder. On a Mac, git comes with Apple's command line tools, and without them the installer stops and says xcode-select --install.

Building a game needs more — CMake, Ninja, a C++ compiler, and on Linux and FreeBSD the X11 development headers — and the installer looks for those at the end. What is missing is listed with the command that installs it on this system: apt, dnf, pacman, zypper, Homebrew, pkg, pkg_add or pkgin, and on Windows winget. The command is printed for you to run, as root where the system wants it; the installer never runs it.

The clone is of the framework's main, without the file contents of old commits, so it is the size of one checkout rather than of the whole history.

The startup file is the one your login shell reads, from $SHELL: ~/.zshrc for zsh, in $ZDOTDIR when that is set; ~/.bashrc for bash on Linux and, on macOS, the first of ~/.bash_profile, ~/.bash_login and ~/.profile that exists; ~/.config/fish/conf.d/rmp.fish for fish, under $XDG_CONFIG_HOME when that is set; ~/.cshrc for csh, and ~/.tcshrc for tcsh when there is one; for ksh, the file $ENV names, when it names one; and ~/.profile for any other. The block it adds starts with # added by rmp install: ~/.local/bin on PATH and ends with # end of rmp install, and it is added once however many times you install.

On Windows the folder on PATH holds only that small script, and not the clone itself: in the clone, PowerShell would find rmp.ps1 first, and its default execution policy refuses to run a script from your own disk. So nothing needs Set-ExecutionPolicy, and rmp is the same command in PowerShell and in cmd. Your user PATH is changed in place, keeping every entry it had, and Windows is told, so a terminal opened from now on sees it without logging out; the PowerShell window you installed from has it already.

Running it again, and updating

The same line run again updates instead of installing: when the clone is already there, it runs rmp update in it, and then rmp install, which finds everything in place and changes nothing. Or run the update yourself, from anywhere:

rmp update

It fetches the framework's main and moves the clone forward to it, and says which commit it went from and to. It never merges: a clone with changes of its own, on another branch, or with commits the framework does not have is refused, and told what to do about it.

Your games are not touched. Each game carries its own copy of the framework and of rmp, and keeps the one it was made with; rmp new makes the next game from the updated framework. The rmp command explains why.

From a clone of your own

The installer is a clone and two commands, and the commands are rmp's own. A framework you cloned yourself — to work on it, or into a folder you chose — goes on your PATH the same way, by running its rmp once by its path:

git clone https://github.com/omardev29/raylib_multiplatform ~/raylib_multiplatform
~/raylib_multiplatform/rmp install

On Windows, rmp.cmd install in that folder. rmp install makes the link, or the script on Windows, and says so when it is already there; when another rmp is in the way — a link to some other clone — it refuses and names it, and rmp install force replaces it. rmp update then updates that clone.

Both act on the framework the rmp you typed belongs to, wherever you type them. A game's own copy refuses them: it is not the framework on your PATH, and it is never updated.

Uninstalling

Nothing is installed anywhere else, so removing it is deleting what the table above lists. On Linux, macOS and the BSDs:

rm ~/.local/bin/rmp
rm -rf ~/.local/share/rmp

and, if the installer added one, the block from # added by rmp install to # end of rmp install in your shell's startup file — for fish, the whole of rmp.fish. Other programs install into ~/.local/bin too, so you may want to keep that folder on your PATH anyway.

On Windows, delete %LOCALAPPDATA%\rmp and %LOCALAPPDATA%\Programs\rmp, and take %LOCALAPPDATA%\Programs\rmp out of your user PATH in Windows' "Edit environment variables for your account".

Your games keep working without it: each has its own rmp at its root, ./rmp, rmp.ps1 and rmp.cmd, and its own copy of the framework.
